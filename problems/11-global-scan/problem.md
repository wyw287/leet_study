# 全局前缀和(跨块扫描)

## 题目

给定长度 `n` 的浮点数组 `x`(每个元素都在 `(0,1]` 之间),输出它的 **inclusive 前缀和**:

```
y[0] = x[0]
y[i] = y[i-1] + x[i]        (i > 0)
```

整个数组是**一条**长度为 n 的依赖链 —— 不是很多条短链。这是它和 10 题最大的区别:
10 题的每一行只有 1024 个元素,一个 block 装得下,所以"块内并行"就够了;
现在 n = 3200 万,一个 block 装不下,**必须跨块**。

分段方式由题目规定(因为段的个数要事先知道才能开缓冲):

```
第 b 个块负责 [b*CH, min(n, (b+1)*CH)),  CH = ceil(n / nblk)
```

`nblk` 在用例里是 64 ~ 1024。**所有用例的 nblk 都不超过 1024**,这不是巧合 ——
它意味着"把 nblk 个数塞进一个 block 里扫一遍"这条路是留着的。

## 为什么这道题重要

前缀和是很多算法的地基:数组压缩(先扫一遍才知道每个元素该写到哪)、
基数排序、稀疏矩阵的 CSR 构造、分段求和的偏移……它们都长在"扫描"上。

而这道题真正要教的东西只有一句话:

> **CUDA 里块与块之间没有任何同步原语。**

你没法让块 5 等块 4 算完再开工。能等的只有两样东西:

1. **kernel 边界** —— 前一个 kernel 的所有块都跑完,后一个才开始。这是硬件保证的。
2. **原子操作 + 自己写的 flag / 计数** —— 手动实现"等",代价是要处理内存序(`__threadfence`、
   `volatile`),而且很容易写出"在本机跑得对、换张卡就错"的代码。

10 题你学的所有技巧(块内扫描、共享内存乒乓、`__syncthreads`)到这里都不够用了:
`__syncthreads` 管不了一个 grid,这是整个 CUDA 编程模型里最硬的一道边界。
凡是需要"全局有序"的算法(扫描、排序、压缩),都要在这道边界上做文章。

## 基线慢在哪:25 趟全局读写

基线是 Hillis-Steele 直接铺在整个数组上:

| 第几趟 | 每个元素做的事 |
|---|---|
| 1 | 加上左边 1 个元素 |
| 2 | 加上左边 2 个元素 |
| p | 加上左边 2^(p-1) 个元素 |

趟数 = `ceil(log2(n))`。n = 2^25 时是 **25 趟**。每一趟都要读一遍、写一遍整个数组:

```
25 趟 × (读 134MB + 写 134MB) = 6.7 GB
而两遍法(见「解法思路」)只要   读 134MB × 2 + 写 134MB = 0.40 GB
```

**注意基线不是"写得烂"。** 它的每一趟访存都是合并的,每一趟都跑满了 ~890 GB/s 的带宽,
`if (i < n)` 的边界判断也没问题。它的问题是**总功**:深度(depth)是 O(log n) 很漂亮,
但总工作量(work)被抬到了 O(n log n)。并行算法的教科书里把这两个量分开算,这就是原因 ——
**多开线程只能减少深度,不能减少总功。**

这决定了本题的评分方式:两者的"有效带宽"都是 ~890GB/s,用"占峰值带宽百分比"根本分不出好坏,
所以本题用**加速比**评级。加速比在这里有精确的物理含义:总功之比。

顺带一个为什么用例必须这么大的理由:L2 只有 72MB,而输入是 128MiB。
如果输入装得进 L2,第 2..25 趟就会命中缓存,那个 25 倍的总功优势就凭空消失了。
所以这道题的用例都在 128MiB 量级 —— 测的是真显存带宽。

## 解法思路:三阶段

一条 3200 万长的链拆不开,但可以先把它**缩小**:

**阶段 1:每个块只回答一个小问题。** "我这一段的和是多少?"
这是一个普通的块内归约(04 题做过),输出 `nblk` 个数,写在 `part[0..nblk-1]` 里。
问题从 3200 万个元素缩到了 1024 个数。

**阶段 2:把这 1024 个数扫一遍。** 一个 block 就够了。
扫完得到"每个块的**排他**前缀偏移":块 b 的偏移 = 段 0..b-1 的和。

**阶段 3:每个块回到自己那段,做真正的扫描。** 这次不是求和,是扫描 ——
块内怎么做都行(10 题的路 A / 路 B),扫完之后每个元素再加上 `part[b]`,写出 y。

为什么阶段 2 **必须**是另一个 kernel?因为阶段 1 的所有块必须先写完 `part`,
阶段 2 才能读它。而块之间没有同步原语,唯一现成的全局屏障就是 kernel 边界。
`launcher` 是 host 代码,它可以启动多个 kernel,而且它们之间天然串行 —— 这就是跨块依赖的接法。

**记住这道题的账:3n。** 阶段 1 读 n(求和),阶段 3 再读 n(扫描)+ 写 n = 3n。
第二遍读 x 躲不掉,因为阶段 1 只留下了"段和",段内每个元素的值早就丢了
(128MiB 装不进任何片上存储)。所以本题加速比的天花板是 `50n / 3n ≈ 16x`,不是 25x。

## 陷阱提醒

1. **空段也要写 0。** 如果 `chunk * nblk > n`,最后几个块领到的是空段。
   它们的 `part[b]` 必须写 0 —— scratch 在每次校验前被框架填成毒值(NaN),
   漏写一个,NaN 就会顺着块间偏移污染它后面**所有**的块,而且报错位置离病因很远。

2. **tile 之间的进位,以及那个额外的 `__syncthreads()`。**
   段长 32768 远大于 BLOCK,所以一个块要走很多个 tile。块内扫描只解决"tile 内部"的顺序,
   tile 之间要自己把进位接上:`carry += 本 tile 的总和`。
   最容易错的一处是:本轮 tile 的总和(`sm[BLOCK-1]`)是所有线程都要读的**同一个槽位**,
   读完它之后必须再来一次 `__syncthreads()` 才能进入下一轮 —— 否则持有那个槽位的线程
   可能已经进入下一轮、把它覆盖掉了。这个 bug 只在特定调度下出现,`repeat=3` 就是为了抓它。

3. **原地扫描的读写竞争(阶段 2)。** 线程 t 这一轮要读 `sm[t-s]`,
   而线程 `t-s` 在同一轮里会写 `sm[t-s]`。所以要么"先读进寄存器 → 屏障 → 再写回",
   要么开两块共享内存乒乓。

4. **排他 vs 包含前缀。** 块偏移要的是"我前面那些段的和",不含我自己那一段。
   常规的块内扫描给的是包含前缀,记得把自己那一份减掉。

5. **网格是 nblk 个块,不是 ceil(n / BLOCK) 个块。** 分段是题目规定的(见上),
   别按自己的喜好切;阶段 2 用一个块 + 1024 个线程。

6. **别把"大偏移 + 小增量"交给 f32 累加器 —— 它会静默地算错。**
   一个很自然的写法是让线程 0 从 `part[b]`(约 1670 万)开始,一路 `s += x[i]`
   扫下去。在 big 用例上它会**错**,而且错得没有道理可讲:前缀和一旦越过
   2^24 = 16777216,f32 的 ulp 就从 1 跳到 2,而 x 的元素只有 0.5 的量级 ——
   往上加等于没加。实测最后 5.5 万个元素全错,最大绝对误差 1.64e4,
   远超容差(那里只允许 1677)。
   这不是"浮点累加顺序不同"那种正常误差,是**加法器根本看不见那些增量**。
   两个躲法:
   * 像参考解那样,段内先扫出**小数值**的前缀和(段内总和最多 1.6 万,ulp 还很小),
     最后一次性加上大偏移 —— 只舍入一次;
   * 或者累加器直接上 `double`。
   顺带一句:这正是"树形归约比串行累加更准"的原因,也是 04 题的参考解用 double 的道理。
   (有意思的是 ragged 用例的总和约 1.65e7,刚好在 2^24 **以下**,同一个错误写法
   在那里是能过的 —— 所以别把"某个用例过了"当成"对了"。)

## 评分说明

正确性决定通过与否(与 CPU 参考解对拍),性能只给 S/A/B/C 评级,不卡关。
评级取**所有可评级用例里的最好成绩**;耗时不到 20µs 的小用例(本题的 `tiny`)不参与评级。

加速比的分母是上面那条 Hillis-Steele 基线。天花板是 3n。实测的几档是这样的
(4090,框架自动清 L2,big 用例 128MiB,nblk=1024):

| 实现 | DRAM 流量 | 耗时 | 加速比 | 评级 |
|---|---|---|---|---|
| 单线程串行(grid=1, block=1) | 2n | 1327.9 ms | 0.006x | C |
| 基线:Hillis-Steele 铺在整个数组上(25 趟) | 50n | 7.51 ms | 1.00x | — |
| 三阶段,但段内让线程 0 串行扫 | 3n | 1.730 ms | 4.34x | B |
| 三阶段 + 块内 tile 并行扫描(参考解) | 3n | 0.455 ms | 16.51x | S |
| 参考解,只是 `BLOCK` 从 256 改成 512 | 3n | 0.451 ms | 16.66x | S |

(照抄基线 = 1.00x = C。表里"DRAM 流量"一栏是**下界**,实际流量只会更多 ——
比如单线程那行只搬 2n,是全场最省的,却是最慢的:它证明了流量不是全部,
**在途数据的多少**同样能决定生死。)

| 评级 | 加速比门槛 | 意味着 |
|---|---|---|
| B | ≥ 2.5 | 你已经不在 Hillis-Steele 那条路上了 —— 总功真的降下来了 |
| A | ≥ 8.0 | 结构对了,但某一步的并行度或访存没排好 |
| S | ≥ 12.0 | 贴着 3n 那堵墙(参考解 16.5x 的 73%,余量足够) |

**这题的门槛是台阶,不是斜坡。** Hillis-Steele 的每一趟都正确、每一趟都跑满带宽,
从它出发无论怎么微调(调块大小、把一趟拆成两趟、块内先用共享内存走几步)都只是把
25 这个系数挪动几个点 —— 理论上限也就 1.4x 左右(块内共享内存只能省掉
log2(tile) 那几趟的全局往返)。真正值钱的一步是"认出总功可以从 O(n log n) 降到 O(n)",
一跨就是十倍。B 这条线就画在台阶中间,专门区分"换了个结构"和"在原结构上刮几个点"。

而 4.34x → 16.51x 这一步的差距,值得单独说清楚:**它不是"块内扫得慢",是并行度塌了。**
表中第三行每个段只有 1 个线程在干活(全卡一共 1024 个线程),每个线程同时只有 1 个
未完成的 load。要跑满 1008GB/s 需要约 700KB 的在途数据,它只有 4KB ——
这一阶段的有效带宽掉到 ~170GB/s,这是**延迟受限**,不是带宽受限。
最后两行只差 0.9%(`BLOCK` 256 vs 512)则印证了另一面:**块内怎么扫是噪声**。
所以这道题的分数实际上由两件事决定:

* 结构(切几个阶段、切在哪)—— 决定你是 C 还是 B;
* 并行度(每一段摊给多少线程、访存合不合并)—— 决定你是 B、A 还是 S;
* 段内的扫描写法、`BLOCK` 取多少 —— 噪声。

一句实话:**本题的钱不在块内。**

## 思考题

1. **阶段 2 能不能省掉?** 一个想法是:让阶段 3 里每个块**自己**把 `part[0..b-1]`
   累加一遍,而不是读阶段 2 的结果 —— 那样只需要两个 kernel。
   这笔账怎么算?写出来跑一下,和参考解比一比(提示:多出来的读是 O(nblk²) 次,
   但每个块读的是同一小段内存,它待在 L2 里;而省下的是几微秒的 kernel 启动)。
   什么时候这个交易会变得不划算?

2. **如果 n 再大 100 倍(12.8GB)会怎样?** 说出这个三阶段方案里最先崩掉的那一环。
   提示:至少有三处和规模有关 —— `int` 索引的范围、`part` 假设"一个 block 能扫完 nblk 个数",
   以及"阶段 1 的段和用什么精度累加"。真到那个规模,前缀和通常要写成多级的
   (段 → 段之段 → …),想想为什么。

3. **单遍扫描(decoupled look-back)怎么做到 2n?** 思路是:每个块算完自己的段和之后,
   不写进 `part` 就走人,而是**原地等**前一个块公布它的"包含前缀",拿到之后自己也能公布,
   然后往下传;同时把自己段内的数据留在寄存器/共享内存里,最后一次性写出。
   这样 x 只读一遍。问题是:"等"和"公布"这两个动作在 CUDA 里怎么写才正确?
   为什么普通的读写不够,必须用 `__threadfence()` 和 `volatile`(或者 `atomic` 的
   内存序参数)?想想如果编译器把"读 flag"缓存进寄存器会发生什么。
   (这条路是 CUB / Thrust 里 `DeviceScan` 的做法,想读源码可以搜 `decoupled look-back`。)
