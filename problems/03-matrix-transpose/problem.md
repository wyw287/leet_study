# 03 矩阵转置

> 难度 ●●○○○ · 标签 `2d` `shared-memory` `memory-bound` · 考点:二维索引、内存合并、共享内存分块、bank conflict

## 题目

给定一个 `m` 行 `n` 列的 `float` 矩阵(按行存储,`input[r * n + c]` 是第 `r` 行第 `c` 列),
输出它的转置:一个 `n` 行 `m` 列的矩阵,`output[c * m + r] == input[r * n + c]`。

```cuda
__global__ void transpose(const float* input, float* output, int m, int n);
void transpose_launch(LaunchCtx& ctx);
```

## 为什么这道题值得做

向量加法里你怎么写都是合并访问的,所以感受不到"访存模式"的威力。
转置不一样 —— **它天然有一侧是不合并的**,而这正是共享内存存在的理由。

看一下朴素写法会撞上什么:

```cuda
int c = blockIdx.x * blockDim.x + threadIdx.x;   // 列
int r = blockIdx.y * blockDim.y + threadIdx.y;   // 行
output[c * m + r] = input[r * n + c];
```

- **读是合并的**:同一 warp 里相邻线程的 `c` 相邻 → 读 `input` 里相邻地址 ✓
- **写是跨步的**:相邻线程要写的位置相隔 `m` 个元素 → 每次 warp 写散成 32 个
  独立的显存事务 ✗

一次显存事务搬 32 字节,而一个 warp 需要 128 字节 —— 所以写侧的有效带宽直接掉到
1/4 甚至更低。本题基线实测只跑到 **267 GB/s**,而 4090 的峰值是 **1008 GB/s**。

## 解法思路:分块 + 共享内存

核心想法:**先用合并的方式把数据搬进共享内存,再从共享内存里以转置的次序读出,
最后以合并的方式写回全局内存**。共享内存没有合并访问的概念(只要避开 bank conflict),
所以"跨步"这件事被移到了片上的共享内存里,代价小得多。

```
每个线程块负责 TILE×TILE 的一块(如 32×32)

1. 合并读入共享内存:  tile[ty][tx] = input[(row0+ty) * n + (col0+tx)]
                     ↑ 相邻 tx 读相邻地址 ✓
2. __syncthreads()
3. 转置写出:          output[(col0+ty) * m + (row0+tx)] = tile[tx][ty]
                     ↑ 注意下标反过来了:读 tile[tx][ty],写出去的地址
                       对相邻 tx 是相邻的 ✓
```

## 开始前请先想清楚这几点

1. **`__syncthreads()` 不能漏**。第 1 步写共享内存、第 3 步读共享内存的是**不同的
   线程**,中间必须有同步。漏掉的结果是「有时对有时错」—— 框架的重复执行和
   racecheck 都会抓到,但自己查会非常痛苦。

2. **bank conflict**。共享内存分成 32 个 bank,同一 warp 的线程访问落在同一个 bank
   的不同地址时会串行化。`tile[32][32]` 在转置读出时恰好会踩满冲突;
   把数组声明成 `tile[32][33]`(多一列)就能避开。**这一步改动只有 1 个字符,
   却能再快一截** —— 强烈建议你两种都测一次,亲眼看看差别。

3. **非方阵与边界**。用例里有 `m=4093, n=2047` 这样的质数规模,不能被 TILE 整除。
   共享内存的**读和写都要判边界**,而且要小心:写出时的边界条件用的是 `(n, m)`,
   不是 `(m, n)`。

4. **用例 `tiny` 是 13×7** —— 比一个线程块还小,网格都凑不满一块。
   这类规模最容易暴露边界写错。

## 评分

按**相对基线的加速比**评级:

| 评级 | 加速比 | 意味着 |
|---|---|---|
| B | ≥ 2.0x | 确实用上了合并写 |
| A | ≥ 3.0x | 接近峰值带宽 |
| S | ≥ 3.5x | 逼近理论上限(≈3.8x,由基线 267 GB/s 与峰值 1008 GB/s 之比决定) |

小用例(总耗时不到 20µs)不参与评级 —— 那个量级上测的是启动开销和计时抖动,
不是 kernel 性能。框架会自动跳过。

   时各自落在哪个 bank,就明白了。
