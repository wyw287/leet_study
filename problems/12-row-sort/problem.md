# 12 · 行内排序(值域只有 0..99)

## 题目描述

给定一个 `rows × cols` 的行优先整数矩阵(`ctx.x`,每个值都在 `0..99` 之间),
把**每一行独立地**升序排序,结果写进 `ctx.y`:

```
y[r][0] <= y[r][1] <= ... <= y[r][cols-1]        对每一行 r 都成立
```

行与行之间没有任何关系 —— 第 3 行的排序结果不受第 2 行影响。

`rows` 最大约 33000,`cols` 最大 1024,两个大用例的数据量都是 **33.5M 个 int
= 134MB 读 + 134MB 写**。值落在 `0..99` 之间是**题目契约**(数据由框架填充),
不是巧合 —— 这句话是本题最重要的信息,下面会解释为什么。

| 名字 | 干什么 |
|---|---|
| `__global__ void row_sort(const int* x, int* y, int rows, int cols)` | 干活 |
| `void row_sort_launch(LaunchCtx& ctx)` | 决定启动配置 |

数据已经在显存里了。分配、搬运、计时、对拍、越界检测都由框架完成。

输出是整数,框架要求**逐元素精确相等**,没有容差。而且**每个位置都要写**:
校验前 `y` 会被填成毒值 `0x5EED5EED`,漏写的位置会立刻暴露。

## 为什么这道题重要

前面 11 道题里,输出的位置几乎总是**由线程编号决定的**:`c[i] = a[i] + b[i]`、
`y[r][c] = ...`、`out[i] = ...`。线程知道自己该写哪儿,写之前不用问任何人。

这道题第一次把这个前提打破了:

> **一个元素该写到哪个位置,取决于别的元素是什么值。**

这是 **scatter(散射)** —— 直方图(07)沾过一点边,但那里的散射是"加到某个桶上",
没有顺序;而排序要求**位置本身**是对的。分组、compaction、基数排序、
稀疏矩阵的行压缩……全都建立在这件事上。

而且它顺带把 GPU 排序的核心成本暴露得非常干净。数一下账:

* **DRAM 流量是定死的。** 每个元素读 4 字节、写 4 字节,一共 268MB。
  4090 的峰值带宽 1008 GB/s,下限 **约 266µs**。用什么算法都一样 ——
  排序不会让数据变小。
* **比较排序的每一趟都要一次 `__syncthreads`。** 一趟里,线程之间要交换数据,
  交换完必须让全块都看见才能进入下一趟。屏障是整块线程一起等的,
  而一趟只能把数据挪动一小步。
* 于是这道题的成本几乎就是 **趟数 × 屏障的价钱**。

三种做法搬运的字节数**一模一样**,趟数却差了 256 倍:

| 做法 | 趟数(屏障次数) | 实测(big 用例) | 加速比 |
|---|---|---|---|
| 奇数-偶数换位排序(并行冒泡) | **1024** | 15.643 ms | 1.00x |
| bitonic 排序(GPU 上最经典的比较排序) | **55** | 2.158 ms | 7.24x |
| 计数排序(本题正解) | **4** | 0.242 ms | 64.64x |

看第一行:**15.6 ms 是 DRAM 下限的 59 倍**。基线从来没碰到过带宽 ——
它 100% 的时间都花在屏障和配套的指令发射上。这是"瓶颈可以完全不在显存"
的第二个样本(第一个是 07 的原子冲突)。

## 解法思路

**值域只有 100 种可能的时候,"排好序"和"数一遍再按顺序铺开"是同一件事。**

一排 1024 个数,值都在 0..99:只要知道"每个值出现了几次",
结果就唯一确定了 —— 前 `hist[0]` 个位置全是 0,接着 `hist[1]` 个 1,依此类推。
**一次比较都不需要。**

于是一个 block 负责一行,分五步:

1. **整行搬进共享内存**,同时把直方图清零
   (`for (b = tid; b < 100; b += blockDim) hist[b] = 0;`)。
   后面所有步骤都从共享内存里读,全局内存**只读这一遍**。

2. **数直方图**:`atomicAdd(&hist[v], 1)`。
   原子加打在本块私有的共享内存上 —— 33.5M 次原子加要是全挤在 100 个全局地址上,
   L2 会按地址串行化,这题立刻退化(07 题实测过:22 GB/s,峰值的 2%)。

3. **排他前缀和**:`cur[v] = hist[0] + ... + hist[v-1]`,
   也就是"值 v 这一组从哪个位置开始放"。
   注意**另存一份 `cur`,不要把前缀和原地写回 `hist`**:
   第 v 个线程要读 `hist[0..v-1]`,而别人写进去的前缀和会把还没读到的
   **计数**覆盖掉(计数后面还要用)。这不是性能问题,是正确性问题。
   100 个桶用 100 个线程各扫一遍就够了,这点延迟被下面的屏障一起等掉。

4. **散射**:`o[atomicAdd(&cur[v], 1)] = v` ——
   每个元素落到"它那个值的下一个空位"上。落点由 `cur` 决定,而 `cur` 由数据决定。

5. **合并写回**:`y[i] = o[i]`。第 5 步是纯搬运,地址连续。

第 4 步为什么散进**共享内存**(`o[]`)而不是直接写全局(`y[]`)?
这是本题的第二个考点,值得单独说清楚:

> 一个 warp 的 32 个线程,写地址是这一行 4KB 里的 32 个**随机位置**。
> 合并访存时一条 store 指令只值 1 个 L1 事务(32 个线程的数据落在同一个
> 128 字节块里);散开之后,这 32 个地址落在约 28 个不同的 32 字节 sector 上,
> **一条 store 指令就值约 28 个事务**。
> 代价约等于"每写一个元素花掉一个 L1 wavefront":33.5M 次摊到 128 个 SM 上
> 接近 190µs,和 266µs 的 DRAM 时间叠在一起。

**实测:直接散到全局是 0.454 ms(34.44x),散进共享内存再搬出去是
0.242 ms(64.64x)—— 差了 1.9 倍。** 前半程已经想对了(不比较、用直方图),
但只走到一半。

注意这里并没有"消除"冲突 —— 共享内存里的散射照样有 bank 冲突。
它只是把冲突**挪到了一个便宜的地方**,并且买下了第 5 步那次完全合并的全局写:
**用 4KB 片上内存,换来 134MB 全局写的 L1 事务数少了约 28 倍。**

## 陷阱提醒

1. **`__syncthreads()` 一次都不能少,而且不能放进分支里。**
   * ①→② 之间:别人还没把这一行搬完,你就开始数了。
   * ②→③ 之间:直方图还在被别的线程加。
   * ③→④ 之间:**游标还没算完就开始散射,两个元素会抢同一个位置**
     (结果是有的位置被写两次、有的位置留着毒值)。
   * ④→⑤ 之间(如果你按解法思路第 5 步做了共享内存暂存):
     写回的时候还有元素没散完,搬出去的就不是最终顺序。

   所以四步结构是 3 次屏障,五步结构是 4 次。漏掉任何一个,症状都是
   "有时对有时错" —— 框架每个用例跑 3 遍(`verify.repeat`),racecheck 也会盯着它。

2. **直方图和游标必须是每块一份的共享内存。**
   挪到全局内存里去 `atomicAdd` 看起来更省事,但那等于把 33.5M 次原子加
   全挤在 100 个地址上,直接回到 07 题基线的 22 GB/s。

3. **`hist` 和 `cur` 要用两块内存。** 用 `cur` 原地做前缀和会把还没读到的
   `hist[b]` 覆盖掉。这不是性能问题,是正确性问题。

4. **`cols` 是运行时值,而且不是 2 的幂。** `ragged` 用例的 `cols = 1021`
   (质数、不是 32 的倍数),`tiny` 用例只有 129 —— 比 blockDim 还小。
   跨步循环 `for (i = t; i < cols; i += blockDim)` 天然能处理,
   但**共享内存里没有被写到的位置是垃圾值,不要读它们**。

5. **块内所有线程要一起进退。** `if (r >= rows) return;` 是安全的
   (整个块的 `blockIdx.x` 相同,要么全返回要么全不返回);
   但任何**按 `threadIdx.x` 分叉**的 `__syncthreads()` 都会死锁或读到半个结果。

6. **block 大小在这题值 1.46 倍。** 一行只有 1024 个元素,你要是开 1024 个线程,
   每个线程全程只干一件事,而每个 SM 最多驻留 2048 个线程 ——
   只有 2 个 block 在飞,掩盖访存延迟的能力就塌了。
   实测:block=256 是 0.242 ms,block=1024 是 0.353 ms。

## 评分说明

* **正确性决定通过与否。** 输出是整数,框架要求精确相等。
* **性能只评级,不卡关**,分 B / A / S 三档。
* 本题按**相对基线的加速比**评级。用加速比而不是带宽占比,是因为基线
  **根本没走到带宽上** —— 它的有效带宽只有 17 GB/s,拿"占峰值百分比"给它打分
  等于问一个没上场的人拿了多少分。加速比在这里的含义很干净:
  **你把趟数从 1024 降到了几趟。**

完整实测(4090,框架自动清 L2,`big` 用例 32768×1024 = 134MB 读 + 134MB 写;
`ragged` 用例 32749×1021 的加速比与它几乎一致 —— 7.56x / 66.13x):

| 实现 | 屏障次数 | 耗时 | 加速比 | 评级 |
|---|---|---|---|---|
| **参考解**(计数排序 + 共享内存暂存写回) | 4 | **0.242 ms** | **64.64x** | **S** |
| 参考解,但 block 改成 1024 | 4 | 0.353 ms | 44.21x | S |
| 计数排序,散射直接写全局(半成品) | 4 | 0.454 ms | 34.44x | A |
| bitonic 排序(55 趟) | 55 | 2.158 ms | 7.24x | B |
| 基线:奇数-偶数换位排序 | 1024 | 15.643 ms | 1.00x | — |

参考解的有效带宽是 **1107 GB/s** —— 略超标称峰值,因为计时停止的瞬间
最后一批写还在 L2 里没落盘,少算了那部分流量(01 题解释过这件事)。
换句话说:**这道题已经到墙了,再往下没有空间。**

`B / A / S` 的门槛是 **3.0x / 16.0x / 40.0x**,三条都卡在实测数字的空隙里:

* **B = 3.0** —— 高于基线,低于 bitonic 的 7.24。换掉"一趟一趟冒泡"这个结构
  就该拿到。
* **A = 16.0** —— 高于 bitonic 的 7.24,低于半成品的 34.44。
  要么写出比朴素 bitonic 更省屏障的比较排序,要么用计数排序但写路径还没优化。
* **S = 40.0** —— 高于半成品的 34.44(留 16% 余量),低于参考解的 64.64
  (门槛是它的 62%)。只有"一次比较都不做" **加上** "把散射挪到便宜的地方"
  才够得着。

**注意这条梯子的形状:换算法和修写路径是两次独立的跨越,中间没有斜坡。**
34.44x 的半成品停在 A,而 B 是留给"写了比较排序但没走到位"的人的。

(门槛为什么是 40 而不是贴着 44.21 那个数:44.21 是"参考解 + block 开 1024"
的实测值,把线划在它旁边,两三个百分点的运行间噪声就能决定一个实现是 A 还是 S ——
那种门槛是假的。40 落在 34.44 与 44.21 中间,两边都有 10% 以上的余量。
block 大小仍然是上面第 6 条提醒,但它不是评级的分水岭:
**分水岭是"有没有把散射挪进共享内存"。**)

`leet solution 12` 里有参考解。

## 思考题

1. **值域变大之后,计数排序还是好主意吗?**
   如果 `x` 里的值变成 `0..999999`(一百万个可能值),第 ②③ 步的直方图要多大?
   装得下共享内存吗?装不下的话,你会怎么改?
   (提示:两个方向。一是"每一趟只看值的一部分二进制位",那就是**基数排序** ——
   本题的计数排序正是基数排序的一趟,想清楚一趟要多少位才划算、
   一共要几趟。二是算一算:100 个桶时每个桶平均被加 10 次,100 万个桶时呢?
   **直方图本身变成了新的访存热点**,这会改变什么?)

2. **一行装不下共享内存的时候,哪里先崩?**
   本题假设一行 ≤ 1024 个元素(4KB)。如果 `cols = 10^6`(一行 4MB),
   参考解这个结构**哪一步先崩**?(提示:直方图仍然只有 100 个桶,
   所以第 ②③ 步其实完全不受影响 —— 崩的是"整行缓存"这个前提。
   那么"值 v 这一组的起始位置"就不再是块内能算出来的了,它需要一个
   **跨块**的前缀和。回头看 11 题:全局扫描是怎么把块内结果接起来的?
   这道题的"块间偏移"是什么?加进去之后,总趟数从 4 变成几?)

3. **共享内存的 bank 冲突,和全局内存的散射写,哪个更贵?**
   参考解把散射挪进了共享内存 —— 但共享内存里的散射**照样有冲突**
   (32 个线程往随机 bank 写,要排队 replay)。凭什么说这笔账划算?
   (提示:两者都是"每周期一个"的吞吐量限制,但一个 LSU 周期处理的
   单位不一样 —— 一个是 bank 访问,一个是 32 字节 sector。
   想知道差多少,自己动手:把第 ④ 步的 `o[...]` 换成 `yr[...]` 跑一遍,
   就是表里那个 34.44x 的半成品。**再想一步:** 如果值域不是 100 而是 2,
   一个 warp 里相同值的元素会落到连续的槽位上,散射还会这么贵吗?
   —— 散射的代价到底取决于什么,是"随机"本身,还是"落点的局部性"?)
