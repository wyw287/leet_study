# py01 列方向 Softmax

> 难度 ●●○○○ · 标签 `softmax` `memory-layout` `pytorch` · 考点:归约维的访存方向、PyTorch 内核的布局敏感性、接口选择对性能的影响

## 题目

给定一个 `rows × cols` 的 `float32` 张量 `x`(按行连续),对**每一列**做 softmax:

```
out[r, c] = exp(x[r, c]) / Σ_r' exp(x[r', c])
```

注意是沿 `dim=0` 归一化 —— **列方向**,不是通常的行方向。

```python
def forward(ctx):
    """ctx.x:   (rows, cols) float32 CUDA 张量,按行连续
       ctx.rows / ctx.cols: 形状

    输出两种写法都可以:
       return tensor                 惯用写法,推荐
       写进 ctx.out 后 return None    预分配缓冲,但要多一次拷贝(见下文)
    """
```

## 为什么这道题值得做

**这是纯 PyTorch 题** —— 你只能用 torch 的算子,一行 CUDA 都不用写。
但它比大多数 CUDA 题更能暴露一个人对 PyTorch 的理解层次:

| | 耗时 | 有效带宽 |
|---|---|---|
| `torch.softmax(x, dim=0)`(8192×8192) | 6.85 ms | **78 GB/s** |
| `torch.softmax(x, dim=0)`(32768×2048) | 26.31 ms | **20 GB/s** |
| 4090 峰值带宽 | — | **1008 GB/s** |

**PyTorch 自带的内核只发挥出峰值带宽的 2%~8%。** 内核没有写错 —— 错的是你
喂给它的数据布局。

## 慢在哪

`x` 是 `(rows, cols)` **按行连续**的:

- 同一行相邻元素在内存里相邻 ✓
- **同一列相邻元素在内存里相隔 `cols` 个 float** ✗

沿 `dim=0` 归约 = 每个线程沿"相隔 cols"的方向取数。取一个元素却要搬回一整条
cache line(128 字节),有效带宽直接掉到 1/32。`tall` 用例把这点放大到了极致。

> 记住这条规律:**让归约维成为访存最快的那一维。**
> 这是 PyTorch 性能分析里最常被忽略、也最容易修的一条。

## 解法思路

把"归约维不连续"这个前提**消掉**,而不是去优化归约本身。

```
x.t()                      → (cols, rows) 的视图,零成本,只改 strides
torch.softmax(…, dim=1)    → 此时归约发生在 dim=1 上
.t()                       → 转回原布局,也是零成本视图
```

关键认知:**你不需要显式调用 `.contiguous()`**。PyTorch 的 TensorIterator 会在
内部判断哪种访问模式更快并自行重排。见下。

### 实测(8192×8192)

| 写法 | 耗时 | 加速 |
|---|---|---|
| `torch.softmax(x, dim=0)` | 6.85 ms | 1.00x |
| **`torch.softmax(x.t(), dim=1).t()`** | **2.08 ms** | **3.30x** |
| 同上但先 `.contiguous()` | 2.07 ms | 3.31x |
| 自己 max/exp/sum/div 展开 | 3.80 ms | 1.80x |

`tall`(32768×2048)上差距更大:26.31 ms → 2.02 ms,**13.05x**。

注意第 2、3 行的对比:显式 `.contiguous()` **既没有更快也没有更慢** ——
PyTorch 内部做了等价的事。所以真正的心智模型不是"我要手动转置",
而是**"我要让归约发生在 PyTorch 能高效处理的维度上"**。

## 陷阱

1. **自己用 max/exp/sum/div 手动展开反而慢**(上表第 4 行,只有 1.80x)。
   因为每一步都会**物化一个完整的中间张量**(`e` 就是 268MB),访存遍数从 2 遍
   涨到 6 遍以上。`torch.softmax` 是融合过的单次内核,不要重新发明它。
   数值稳定的事交给它做。

2. **按列分块处理是错的**(我实测过)。直觉上"按列分块,让每块内部访存局部化"
   似乎能避免整体重排,但 `x[:, j:j+blk]` 依然是**不连续的视图**,
   PyTorch 拿到它照样走慢路径。实测比正解**慢 25 倍**(55ms vs 2.07ms)。
   要的是逻辑上正确的归约维,不是"看起来 cache 友好"的切片。

3. **接口选择会直接影响成绩**。往预分配的 `ctx.out` 里 `copy_` 会比 `return`
   多一次全量访存(读 268MB + 写 268MB),实测把 3.30x 压到 1.87x。
   两者都对,但 `return` 更惯用也更快。**这道题想让你注意到:多余的拷贝
   在访存瓶颈题上是要还的。**

4. **别 `ctx.out = ...`**。重新赋值会让框架看不到你的结果(框架会检测并提示)。

## 评分

| 评级 | 加速比 | 意味着 |
|---|---|---|
| B | ≥ 1.5x | 确实改变了归约的访存模式 |
| A | ≥ 2.2x | 接近正解 |
| S | ≥ 3.0x | 达到正解水平(square 上限 3.30x) |

小用例(`tiny`,37×53)不参与评级 —— 那个量级上测的是启动开销,不是内核性能。

## 思考题

1. **为什么显式 `.contiguous()` 不多不少?** 已知它在内存里真实地重排了一遍数据
   (读 268MB + 写 268MB),而结果和不加它一模一样。这笔开销去哪了?
   提示:算一下不加它时,TensorIterator 内部必须做什么。

2. **换个形状结论会变吗?** 把问题改成 `(2048, 32768)` 再想:`dim=0` 的 softmax
   会变快还是变慢?这和 `tall` 的结论矛盾吗?(建议真的跑一次验证。)

3. **还有多少空间?** 现在的最优是 2.02ms,对应约 2 遍访存的 265 GB/s 有效带宽。
   如果把 max 减法、exp、求和、除法**融合进一个内核**,只需要读一遍 x、写一遍 out
   —— 理论下限是多少毫秒?和 2.02ms 比还差多少?
   (这 3 倍多的差距,就是从"会用 PyTorch"到"会写 kernel"的那道门。)

4. **这个陷阱在真实模型里长什么样?** 想想 LayerNorm 的 `normalized_shape` 跨越
   多个维度时、以及 attention 里对 `seq_len` 做 softmax 时的情形 ——
   你会怎么提前发现这里有个布局问题?
