# 矩阵-向量乘(GEMV)

## 题目描述

给你一个 m×n 的矩阵 `a`(row-major 存放在显存里)和一个长度 n 的向量 `x`,
算出长度 m 的向量 `y`:

```
y[r] = Σ_c a[r][c] * x[c]          r = 0 .. m-1
```

`a[r][c]` 在显存里的位置是 `a[r*n + c]`。三个缓冲的分配和搬运都由框架负责,
你只写 `gemv`(kernel)和 `gemv_launch`(启动配置)。

用例里有两个大矩阵(4096×8192 和 4099×8191,都是 128MiB)和一个小矩阵
(257×129,考边界兼跑 racecheck)。

## 为什么这道题重要

GEMV 是神经网络里出现频率最高的算子之一:全连接层、注意力里的 Q/K/V 投影、
embedding 之后的加权求和,全是它。

它和 01-vector-add 一样是访存瓶颈,但**性质不一样**:01 的朴素写法就是最优写法
(带宽跑满就结束了,没有可优化的东西),而这道题的朴素写法只跑到峰值带宽的
百分之十几 —— 因为它踩了一个 01 没有的坑:**warp 内的访存模式**。
这就是这道题存在的理由:同样一句「访存瓶颈」,底下可以完全没有优化空间,
也可以有 6 倍的空间,区别在于你需不需要为**请求的形状**负责。

它的算术强度是 **0.5 FLOP/Byte**(每读进 4 个字节,只做 1 次乘加 = 2 FLOP)。
而 4090 的平衡点是 `82.6 TFLOPS ÷ 1008 GB/s ≈ 82 FLOP/Byte` —— 差 160 倍。
换句话说:**从第一个 cycle 开始,FMA 单元就一直在等数据**。这题的性能上限
100% 由带宽决定,和算力一点关系都没有 —— 但「上限由带宽决定」不等于
「随手写写就能碰到上限」,这正是下面两节要讲的事。

这个判断直接决定了优化方向。任何「少算一点」的努力都是白费的 —— 把乘加写成
FMA、展开循环、少用几个寄存器,耗时不会动一下。唯一有意义的动作是
**让同样多的字节搬得更快**。

> 对照 06-matrix-mul:那道题里 `a` 的每个字节会被复用 2000 次,所以正解是
> 共享内存分块 + 寄存器分块,**提高**算术强度。这题正好相反 —— 每个字节只被
> 用一次,**分块、共享内存、数据复用一个都不需要**,做了也不会快。
> 同一个人写这两道题应该得出完全相反的结论,这就是把它们放在一起的原因。

## 先算一笔账:那堵墙在哪

```
主力用例的数据量:  4096 × 8192 × 4B = 128 MiB (约 134 MB)
4090 的峰值带宽:   1008 GB/s
物理下限:          134 MB ÷ 1008 GB/s ≈ 133 µs
```

而同样这个用例要做的乘法是 33.5M 次 FMA,算力侧只需要 **0.8 µs**。
差了 160 倍 —— 所以这题不管你怎么写,耗时都在 133µs 上面那一段,
评级看的也就是「你离 133µs 有多近」。

## 基线慢在哪:并行度 + 请求数(两个都不在「字节数」上)

基线(`problems/08-gemv/baseline.cu`,也就是性能评级的分母)是「一个线程算一行」:

```cuda
int row = blockIdx.x * blockDim.x + threadIdx.x;
float acc = 0.0f;
for (int col = 0; col < n; ++col) acc += a[row*n + col] * x[col];
y[row] = acc;
```

它完全正确,线程内部读的还是连续地址,但有两处硬伤:

**第一,并行度。** 一个线程算一行,整个 kernel 就只有 m 个线程。
m=4096 时是 16 个 256 线程块,而 4090 有 **128 个 SM** —— 112 个 SM
从头到尾没事干。

**第二,warp 内的访存是散开的。** 同一个 warp 的 32 个线程(threadIdx.x 相邻)
读的是**相隔 n 个 float 的 32 个不同行**。一条 load 指令要拆成 32 个 32 字节的
sector,一共 1024 字节,而这一次只有 128 字节有用。

注意这里一个容易搞错的点:**DRAM 流量并没有被浪费**。每个 sector 里剩下的
7 个 float,会被同一个线程的后 7 次迭代用掉 —— 一个 warp 的活跃工作集只有
32 个 sector = 1KB,L1 装得下。所以基线的 DRAM 流量是准的(就是 128MiB),
它多出来的是**请求数**:L1 每个 cycle 只能处理 4 个 sector,同一份数据用
32 个 sector 的方式取,就比用 4 个 sector 的方式慢 8 倍。

所以基线的两个毛病都不在「搬了多少字节」上 —— 字节数从头到尾都是准的 128MiB。
毛病在另外两件事:**有没有足够的线程去占住带宽**(它只有 4096 个线程),
以及**一条 load 指令要碰多少个 sector**(它一条指令碰 32 个 sector,
而当场有用的只有 128 字节)。

这两件事各自的贡献,在「评分说明」那张实测表里是分开的:
把线程数翻 32 倍只换来 1.8x,而把访存模式改对换来 3.3x。
**先想清楚哪一个是主要矛盾,再动手改** —— 这是这道题真正的考点。

## 解法思路

关键动作只有一个:**让同一条 load 指令覆盖一段连续的地址**。

**第一步,把「算哪一行」和「算这一行的哪个位置」拆开。** 一个 warp 负责一行,
行号由 warp 号决定,行内位置由 lane 决定:

```cuda
const int lane = threadIdx.x & 31;                                  // 行内位置
const int warp = (blockIdx.x * blockDim.x + threadIdx.x) >> 5;      // 行号
for (int col = lane; col < n; col += 32) acc += rowp[col] * x[col];
```

现在一条 load 里,32 个 lane 读的是 `rowp[lane .. lane+31]` —— 连续的 128 字节,
**4 个 sector** 而不是 32 个。请求数降到 1/8。

**第二步,在一个 warp 内部把 32 个部分和加起来。** 用 warp shuffle:

```cuda
#pragma unroll
for (int off = 16; off > 0; off >>= 1)
    acc += __shfl_down_sync(0xffffffffu, acc, off);
if (lane == 0) y[row] = acc;
```

`__shfl_down_sync(mask, v, k)` 让每个 lane 拿到「lane + k」那个 lane 的 `v`;
k 从 16 一路折半到 1,五步之后 lane 0 手里就是全 warp 的和。这比「写共享内存 +
`__syncthreads` + 再读回来」快得多,因为参与归约的 32 个线程本来就在同一个 warp 里,
**硬件保证它们锁步执行**,不需要任何同步指令,也不占共享内存。

**第三步,用 grid-stride 让线程数不再等于 m。** 一个 warp 一行的话,线程数被
m 绑死了(m=257 就只有 257 个线程在干活)。让固定大小的网格反复领行号:

```cuda
for (int row = warp; row < m; row += total_warps) { ... }
```

`row` 只跟 warp 号有关,是 warp 内**一致**的,所以这个循环不会让 warp 分叉。

**顺便说清楚:为什么 `x` 不需要特殊处理。** 每个 warp 都会把整个 `x` 读一遍,
n=8192 时就是 4096 次 × 32KB = 128MB 的请求 —— 听起来很多。但这 32KB 常驻 L2
(甚至 L1),**一次 DRAM 都不会去**。所以不要为 `x` 做共享内存缓存或者寄存器缓存:
那是在给一条本来就不堵的路修立交桥。判断「该不该复用某个数据」的依据是
**它有多少字节**和**它被复用多少次**,不是「它被读了几次」。

## 陷阱提醒

- **边界要让循环条件自己兜住,不要手动加分支。**
  `for (col = lane; col < n; col += 32)` 这个写法本身就是边界安全的:col 从 lane
  开始以 32 递增,一旦 ≥ n 就停,不可能越界。n=129 时 lane 0 走 5 轮
  (col = 0, 32, 64, 96, 128),lane 1..31 各走 4 轮 —— **走的轮数不一样完全没关系**:
  少走的那几个 lane 的 `acc` 保持 0,而 0 加进和里不影响结果。
  (n < 32 时会有 lane 一轮都不走,同理。)
  反过来,自己手动去补 `if (lane < n)` 这类分支,极容易顺手把后面的 shuffle
  也圈进分支里(见下一条),或者把边界写成 `lane <= n` 而多读一个。
  能靠循环条件表达的边界,就别用手写分支表达。

- **`__shfl_down_sync` 是集合操作,32 个 lane 必须一起执行它。** 把它放进会分叉的
  分支里(`if (lane < n) { ...shfl... }`)是未定义行为:可能挂住,也可能读到垃圾。
  正确结构是「循环(可以分叉)→ 重新汇合 → shuffle(全 32 个 lane 一起)」。
  这类错**有时对有时错**,框架会把每个用例重复跑几遍来抓它(verify.repeat),
  也可以用 `leet test 08 --race` 强制跑一遍竞态检查(很慢,框架只把它挂在
  最小的那个用例上)。

- **只有 lane 0 能写 `y[row]`。** 归约完让 32 个 lane 都去写同一地址,结果不确定。

- **`row * n` 的乘法和 `row` 的范围都要想一遍。** 这题的索引不会溢出 int
  (4096×8192 = 33.5M < 2³¹),但把行指针算成 `a + (size_t)row * n` 是个不用过脑子的
  好习惯 —— 换成 5 万 × 5 万的矩阵(`row * n` 最大 2.5e9 > 2³¹),`row * n` 就会
  翻成负数,而那种 bug 的表现是「读到了别的缓冲」,极难查。

- **`m` 很小(比如 257)时网格要能处理。** 向上取整的网格里,多出来的 warp
  如果直接 `y[row] = acc` 就越界写了。grid-stride 的循环条件 `row < m` 天然兜住这一点。

## 评分说明

这题用**带宽**评级,不用加速比 —— 因为带宽是绝对指标,它直接回答「你离
1008 GB/s 那堵墙还有多远」,而且不随用例形状漂移(基线的加速比在 GEMV 上是
矩阵形状的函数:m 越大,一个线程一行的并行度越高,基线越好看。拿它当门槛
等于在给用例形状打分)。

| 评级 | 有效带宽占峰值 |
|---|---|
| B | ≥ 45% |
| A | ≥ 65% |
| S | ≥ 85% |

「有效带宽」= 框架统计的字节数(矩阵 128MiB + x + y)÷ 实测中位耗时。
每个计时迭代前框架都会把 L2 清空,所以读到的是真实的显存带宽。

三个档位不是拍脑袋定的,是把每一种实现都真写一遍测出来的(wide 用例)。
下面这张表从慢到快排,注意「改动的那一个变量」那一列:

| 实现 | 耗时 | 有效带宽 | 占峰值 | 评级 |
|---|---|---|---|---|
| 基线:1 线程 1 行(4096 个线程) | 0.863 ms | 156 GB/s | 15% | C |
| 只加并行度:warp 一行,但 lane 领行内**连续**的一段 | 0.477 ms | 281 GB/s | 28% | C |
| 参考解,网格封顶到 16 块(128 个 warp) | 0.315 ms | 426 GB/s | 42% | C |
| 参考解,网格封顶到 24 块(192 个 warp) | 0.228 ms | 588 GB/s | 58% | **B** |
| 参考解,网格封顶到 40 块(320 个 warp) | 0.162 ms | 830 GB/s | 82% | **A** |
| 参考解,网格封顶到 64 块(512 个 warp) | 0.146 ms | 917 GB/s | 91% | S |
| 参考解(4096 个 warp,不封顶) | 0.144 ms | 931 GB/s | 92% | S |
| 参考解再加 float4 | 0.144 ms | 930 GB/s | 92% | S |

这张表要横着读,两段:

**第一段(前两行):访存模式是一票否决的。** 第二行把线程数从 4096 提到 131072
(32 倍)、其它什么配置都没改,只换来 1.8 倍 —— 因为每条 load 指令还是碰 32 个
sector。而把 lane 的取数方式从「连续段」换成「跨步 32」,请求数降到 1/8,立刻
快 3.3 倍。**先修这个。**

**第二段(中间四行):在访存模式已经改对的前提下,唯一在变的是网格大小。**
从 16 块开到 64 块,带宽从 42% 爬到 91%。这说明并行度确实也有一道坎,但它很低
—— 512 个 warp 就已经贴着天花板了(4090 有 128 个 SM,每 SM 4 个块)。
反过来,如果你只开了几十个块,访存模式再漂亮也拿不到 S。

**最后一行:float4 一分钱没多拿**,因为你早就贴在 DRAM 的墙上了,少发指令救不了你。

**这题没有算法层面的空间,门槛是物理门槛。** 想拿 S 需要同时做对:合并访存
(4 个 sector 而不是 32 个)、网格铺得开(几百个 warp 以上)、以及边界处理得干净
(尾巴不满 32 的那一轮不能让 warp 分叉到 shuffle 里去)。

> 参考解(`leet solution 08`)用「一个 warp 一行 + warp shuffle 归约 + grid-stride」
> 拿到 **92% 峰值(931 GB/s,wide 0.144ms / ragged 0.145ms),评级 S**,
> 相对基线 6.0x。

## 思考题

1. **用 `float4` 让每个 lane 一次搬 16 字节,会更快吗?** 先算出「一条 load 指令
   覆盖的字节数」从 128 变成多少、sector 数从 4 变成多少,再想 L1 每 cycle 处理
   4 个 sector 这条限制会不会被撞到。**实测答案:一点没快**(wide 用例上
   0.144ms / 930 GB/s,和标量版的 931 GB/s 一模一样)—— 因为你早就贴在 DRAM
   的墙上了,少发指令救不了你。顺便,这个实验还埋着一个真陷阱:`float4` 要求
   16 字节对齐,而 `ragged` 用例的 n=8191 不是 4 的倍数,**行首根本不对齐**,
   直接 `reinterpret_cast<const float4*>` 会报 misaligned address。
   (这也是为什么那道题的用例里要专门放一个质数 n。)

2. **把 m 和 n 对调**(比如 16384×2048),基线会变快还是变慢?为什么?
   提示:基线的并行度是 m,而每个线程的工作量是 n。再去想一个更刁钻的问题:
   **如果你只有 1024 行、每行 32768 列,一个 warp 一行还够用吗?** 不够的话,
   一行要怎么分给多个 warp,又怎么把它们的部分和合起来?

3. **如果 `x` 有四列**(要同时算 4 个不同的向量,即 `Y = A · X`,X 是 n×4),
   这题的算术强度变成多少?还是访存瓶颈吗?这时 `a[r][c]` 会被复用几次,
   该不该把它搬进共享内存或者寄存器?把答案和 06-matrix-mul 的分块方案对一下 ——
   你会看到 GEMV 和 GEMM 之间那条连续的过渡带。
