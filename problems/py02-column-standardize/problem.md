# py02 列方向标准化

> 难度 ●●●○○ · 标签 `fused-kernel` `memory-traffic` `pytorch` `reduction` · 考点:数访存遍数、算子融合的边界在哪里

## 题目

给定一个 `rows × cols` 的 `float32` 张量 `x`(按行连续),对**每一列**做标准化:

```
mu_c  = (1/rows) * Σ_r x[r, c]                    有偏均值
var_c = (1/rows) * Σ_r (x[r, c] - mu_c)^2         有偏方差(除以 rows,不是 rows-1)
out[r, c] = (x[r, c] - mu_c) / sqrt(var_c + eps)
```

`eps` 是数值稳定项,本题固定为 `1e-5`。

```python
def forward(ctx):
    """ctx.x:   (rows, cols) float32 CUDA 张量,按行连续
       ctx.rows / ctx.cols: 形状
       ctx.eps:  float,数值稳定项

    输出两种写法都可以:
       return tensor                 惯用写法,推荐
       写进 ctx.out 后 return None    预分配缓冲,但要多一次拷贝
    """
```

这是一道**纯 PyTorch 题** —— 一行 CUDA 都不用写。

## 为什么这道题值得做

py01 教你的是「**归约维的内存布局**决定了归约快不快」。
这道题教你另一件同等重要、而且更常见的事:**一行 eager PyTorch 代码不等于一步计算。**

在 eager 模式下,`(x - mu) / torch.sqrt(var + eps)` 这**一行**背后是
两个中间张量、两次内核启动、四遍全量访存。写得越"清楚",遍数越多。
PyTorch 的性能分析里,第一步永远是问:

> **从输入到输出,这块数据被完整地读了几遍、写了几遍?**

这个问题一旦问出口,答案往往就自己浮现了。这也是「会用 PyTorch」到
「会调 PyTorch」之间最实用的一道门槛 —— 它不需要你会写 CUDA,只需要你会算账。

## 慢在哪:先学会数访存遍数

基线是把公式直接翻译成算子:

```python
mu  = ctx.x.mean(dim=0, keepdim=True)
var = ctx.x.var(dim=0, correction=0, keepdim=True)
return (ctx.x - mu) / torch.sqrt(var + ctx.eps)
```

每一步都对,每一步都是官方 API。现在数账 —— 单位取 **"一个 268MB 的张量走一遍"**
(8192×8192 个 float32):

| 算子 | 读 | 写 | 小计 | 中间张量 |
|---|---|---|---|---|
| `x.mean(dim=0)` | 1 | 0 | 1 | 只有 cols 个元素,忽略 |
| `x.var(dim=0, correction=0)` | 1 | 0 | 1 | 同上 |
| `x - mu` | 1 | 1 | 2 | **(rows, cols) 居中后的 x** |
| `var + eps` / `torch.sqrt` | ~0 | ~0 | 0 | cols 个元素 |
| `(x - mu) / sqrt(...)` | 1 | 1 | 2 | 输出 |
| | | | **6** | |

**6 遍访存,而这道题的理论下限是 2 遍**(读一遍 x、写一遍 out)。
中间那 4 遍全是「把中间结果落到显存、再读回来」的开销,不产生任何新信息。

关键观察:**这道题的瓶颈根本不是访存效率。** 实测基线 1.71ms 走完 1.61GB,
折合 **941 GB/s —— 峰值(1008 GB/s)的 93%**。PyTorch 的每个内核都跑得很好,
慢纯粹是因为**遍数太多**。所以这道题的加速比几乎就等于**遍数之比**,
这一点后面的实测会精确验证。

注意头两遍的性质与后面几遍不同:`mean`/`var` 是**归约**,只读不写
(输出只有 `cols` 个元素),但要沿 `dim=0` 跨步取数;后面几遍是**逐元素**
运算,访存连续,但每一遍都是完整的读 + 写。两类账要分开算,瓶颈不一样。

## 解法思路

思路只有一句话:**把遍数压下去,而不是把某个算子写快。**

### 第一步:两个归约合并成一趟(6 遍 → 5 遍)

均值与方差读的是同一块数据、走同一个访存模式。PyTorch 里有一类算子能
**一趟同时**算出两者(Welford 在线算法):

```python
var, mu = torch.var_mean(ctx.x, dim=0, correction=0, keepdim=True)
```

注意返回顺序是 `(var, mean)`,不是 `(mean, var)` —— 这是个常见的翻车点。

只省了 1 遍,但这一步的价值在于:**归约从两遍变成一遍后,剩下的账全是逐元素的。**

### 第二步:把逐元素链收敛成一趟(5 遍 → 3 遍)

`(x - mu) / sqrt(var + eps)` 是一个**仿射变换**:

```
out = x * s + b        其中 s = 1/sqrt(var + eps),  b = -mu * s
```

`s` 和 `b` 都只有 `cols` 个元素,算它们几乎不花钱;真正贵的是遍历整块
(rows, cols) 的那一次。PyTorch 有恰好这个形状的**三输入逐元素算子**
(算 `input + t1*t2` 的那种),一趟就能同时读 `x`、乘 `s`、加 `b`、写出 `out`:

```python
s = torch.rsqrt(var + ctx.eps)          # rsqrt 一趟出结果,别写 1/sqrt(...)
return torch.addcmul(-mu * s, ctx.x, s) # = (-mu*s) + x*s
```

到此为止 **3 遍访存**,而且**完全不需要任何"高级 API"** —— 只靠算账 +
找对算子。这就是纯 PyTorch 的地板。

### 第三步:别再往下追了(这一节是实测踩出来的)

你可能会想:有没有哪个现成算子的语义**几乎就是标准化** —— 输入 + 沿某一维的
均值 + 沿同一维的方差?有的,就是 `layer_norm`,它在真实模型里无处不在。

**但在这道题上它更慢。** 实测:

| 写法 | 耗时 | 加速比 |
|---|---|---|
| `var_mean` + `addcmul`(3 遍) | **0.85 ms** | **2.02x** |
| `ctx.x.t()` + `layer_norm` + `.t()`(想少走遍数) | 2.27 ms | **0.76x** |
| 同上,但显式写 `.contiguous()` | 2.27 ms | 0.76x |

原因:`layer_norm` 只在**被标准化的那一维在内存里连续**时才走融合快路径。
我们沿 `dim=0` 标准化,转置视图只是改了 strides,数据在显存里没动 ——
所以它拿到这个视图后,会自己把数据**物理重排一遍**。最后一行是证据:
你显式调用 `.contiguous()` 和完全不调用,耗时一模一样(2.270ms vs 2.274ms,
差 0.2%,在噪声内)—— **它内部做了和你显式调用等价的事**。

那次物理重排是跨步拷贝,访存效率远低于普通逐元素运算,把"少走的遍数"
全都还回去了,还倒贴。**教训:融合内核只在自己擅长的布局下才真的融合。**
"找到一个融合算子"不是终点,"它在这个形状上是否真的走融合路径"才是。

> 那这道题的终点在哪?3 遍(2.0x)是**纯 PyTorch** 的天花板 —— 要真正做到
> 2 遍,必须有一个内核在写 `out` 之前就把整列的均值方差算完,那需要 block
> 级协作。本框架的 PyTorch 科目允许你在解答里用 `torch.utils.cpp_extension.load_inline`
> 写自定义 CUDA 算子 —— 想拿满 S 之后继续往下推,这就是下一步。

## 实测(8192×8192,268MB;访存效率 ~941 GB/s,峰值的 93%)

| 写法 | 遍数 | 耗时 | 加速比 |
|---|---|---|---|
| 基线:`mean` + `var` + `x-mu` + `/sqrt` | 6 | 1.71 ms | 1.00x |
| `var_mean` + `(x-mu)/sqrt(var+eps)` | 5 | 1.43 ms | 1.21x |
| `mean` + `var` + `addcmul` | 4 | 1.14 ms | 1.51x |
| **`var_mean` + `addcmul`** | **3** | **0.85 ms** | **2.02x** |
| `x.t()` + `layer_norm` + `.t()` | 4 + 物理转置 | 2.27 ms | 0.76x |

**加速比 = 6 / 遍数,吻合到 1% 以内**(1.20/1.50/2.00 预测 vs 1.21/1.51/2.02 实测)。
当访存效率已经打到 93% 时,你唯一能改善的就是遍数 —— 这就是这道题想让你记住的账。

## 陷阱

1. **有偏 vs 无偏。** 题目要求**有偏**方差(除以 `rows`),而 PyTorch 的
   `var`/`var_mean` **默认是无偏**(除以 `rows-1`),必须显式写 `correction=0`。
   `rows=8192` 时两者只差 1.2e-4,肉眼绝对看不出来;但 `rows=37` 的 `tiny`
   用例上差 2.8%,对拍会精确地抓住你。**边界用例就是为这个准备的。**

2. **别用 Python 循环逐列处理。** `for c in range(cols)` 每一列都要启动一串内核,
   `cols=8192` 时慢到没有任何意义。PyTorch 的正确姿势永远是一次算完所有的列。

3. **`eps` 加在方差上,开方在加法之后。** `sqrt(var) + eps` 和 `sqrt(var + eps)`
   是两个不同的函数,后者才是题目要的。另外 `s = 1/sqrt(var+eps)` 别写成
   先 `sqrt` 再除法 —— 有一个算子一趟就能出结果(而且更快)。

4. **转置视图不会让归约变快**(见上一节的实测)。这点和 py01 不同:
   py01 里"转置一下"确实快了,但那是**上游内核换了一条快路径**,不是内存变了。
   这道题里同样的动作只会让你多付一次物理重排。**不要背结论,要看账。**

5. **别 `ctx.out = ...`。** 重新赋值会让框架看不到你的结果(框架会检测并提示)。

## 评分

| 评级 | 加速比 | 遍数 | 意味着 |
|---|---|---|---|
| B | ≥ 1.15x | 5 | 把两个归约合并成了一趟 |
| A | ≥ 1.45x | 4 | 逐元素链也收敛了(归约还是两趟) |
| S | ≥ 1.8x | 3 | 两笔账都算对了,达到纯 PyTorch 的地板 |

`tiny`(37×53)只有 1961 个元素,在 20µs 这个量级上测的是内核启动开销而不是访存
性能 —— 它通常低于评级下限被自动跳过(即使偶尔越线也只会拿到 C)。
整体评级取各用例中**最好**的一次,所以它不会拖累你的成绩。

S 的门槛是实测上限 2.02x 的约 89%(留 12% 余量),不是拍脑袋定的。

## 思考题

1. **理论下限真的是 2 遍吗?** 均值和方差必须在写 `out` 之前全部算出来,
   而 `out` 的每个元素又依赖整列的统计量。那么在一个内核里同时做到这两件事,
   需要什么条件?(提示:block 级协作 —— 每个 block 负责若干整列,
   先在片上把统计量归约完,再写出去。)这个问题想通了,你就理解了
   flash-attention 那一类融合内核为什么长成那个样子。

2. **`x.var(dim=0)` 内部到底读了几遍 x?** 教科书上的两遍法是"先求均值,
   再求平方偏差的均值"—— 两遍读。PyTorch 用的不是这个。去查一下
   **Welford 在线算法**,以及为什么它一遍就够;再想想,`var_mean` 把它和
   均值合并进同一个算子,为什么是件自然的事。

3. **为什么 `rows=37` 能抓住"无偏方差",而 `rows=8192` 抓不住?**
   两种定义的相对差是 `1/(rows-1)`:8192 时 1.2e-4,37 时 2.8%。
   再算一下:它落到 `sqrt` 上要除以 2,再乘到输出上。
   **这个用例的规模是刻意选的** —— 如果所有用例都是 8192×8192,
   这道题的容差还拦得住什么?容差和用例规模是一对必须一起设计的东西。

4. **`layer_norm` 在什么形状下才会真的赢?** 它的归约维默认是最后一维。
   把这道题换成"沿**最后一维**标准化"再想一遍:这时 `x` 不用转置,
   `layer_norm(x, (cols,))` 应该就是 **2 遍访存**,而 `var_mean + addcmul`
   是 3 遍 —— **同一个算子,同一份算法,只因为要标准化的那一维在内存里
   连不连续,就从"比基线慢 24%"变成"比基线快得多"。**
   这个对比比记住任何结论都有用。(理论上它能比 3 遍的写法再快约 1.5 倍;
   建议真的跑一次验证 —— 这正是"不要背结论、要看账"的实例。)

5. **把这道题的账带到别处去。** 找一个你写过的、由 5 个以上算子串起来的
   前向计算(LayerNorm、RMSNorm、attention 里的某一段),逐个算子数一遍访存,
   再和它的理论下限比。你大概会发现:**模型里大部分"算力不够"的抱怨,
   其实是访存遍数不够省。**
