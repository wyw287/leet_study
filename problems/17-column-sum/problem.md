# 按列求和

## 题目描述

给你一个 `rows × cols` 的矩阵 `x`(行优先:`x[i][j]` 在 `x[i * cols + j]`),
把每一列加起来:

```
out[j] = x[0][j] + x[1][j] + ... + x[rows-1][j]        j = 0 .. cols-1
```

换个说法:**把 `rows` 个长度为 `cols` 的向量按元素加起来,得到一个长度为
`cols` 的向量。** 张量语言叫"沿 dim 0 归约",`numpy` 里是 `x.sum(axis=0)`。

`x` 里全是 `0..99` 的整数(框架填的)。**输出是整数,而且逐位精确比较 ——
这道题没有容差。** 原因在「陷阱提醒」第 5 条,它本身就是这道题的一个知识点。

| 参数 | 含义 |
|---|---|
| `rows` | 行数,也就是**每个输出元素要吃掉的输入个数** |
| `cols` | 列数,也就是**输出的个数** |
| `max_chunks` | 你可以把行切成几段 —— 上限,不是要求 |

框架另外还给你一块 `partial`(`max_chunks × cols` 的 float,内容是垃圾、
也不参与对拍)。走"两阶段"那条路时用它;不需要就完全别理它。

## 为什么这道题重要

前面 16 道题里,**"一个输出元素 = 一个线程"这个映射从来没错过**:

- 01 向量加法:输入 `n` 个、输出 `n` 个 ⇒ 线程数和数据量同阶,正好;
- 04 归约求和:输出只有 1 个 ⇒ 一个输出由几百个线程协作产生,是归约的常识;
- 07 直方图、16 位图:输出比输入少,但少得不多,线程数仍然铺得满。

这道题的形状和它们都不一样:

```
输入:rows × cols = 131072 × 512 = 6710 万个元素
输出:cols       =                  512 个元素
```

**输出是输入的 1/131072。每个输出要吃掉一整列的 131072 个输入。**

于是那个一直没错过的映射,这次会以一种非常安静的方式失效:

> 按输出切,你只有 512 份工作。数据再多也没用 ——
> **并行度不是由"数据有多少"决定的,是由"工作被切成了几份"决定的。**

这类形状在真实代码里到处都是:`x.sum(dim=0)`、把一批梯度累加起来、
把多头 attention 加起来、按列做统计量(py02 那道题就是它的 PyTorch 版本)。
它们共同的特点是:**算起来只要一次加法,但"切"错了就慢十倍。**

## 解法思路

### 第一步:先数"在飞的东西",再谈别的

最自然的写法(也是性能基线的写法)是一个线程管一列:

```cpp
int j = blockIdx.x * blockDim.x + threadIdx.x;
if (j >= cols) return;
float acc = 0;
for (int i = 0; i < rows; ++i) acc += x[(long)i * cols + j];
out[j] = acc;
```

它慢,不是因为搬得多(每个元素只读一次,一次不多),也不是因为访存散
(相邻 lane 读相邻的列,一条 load 正好 128 个连续字节,合并得无可挑剔)。
它慢是因为:

```
cols = 512,block = 256  ⇒  2 个块  ⇒  2 × 8 = 16 个 warp
```

而这张卡上有 **8192 个 warp 槽位**(128 个 SM × 64)。你用了 16 个。
实测它就是 **9% 峰值**(3.011 ms)。

那要多少个 warp 才够?**实测:128 个块(1024 个 warp)→ 91%。**
所以正确的说法不是"线程越多越好",而是:

> **要跑满 1008 GB/s,显存里同时得有几百 KB 的请求在飞**
> (带宽 × 延迟 ≈ 1008 GB/s × 0.7µs ≈ 700 KB)。
> 16 个 warp 撑死也就几十 KB,1024 个 warp 刚好够。

而"在飞的东西"是这么来的:

```
在飞访存 ≈ 块数 × 每块 warp 数 × 每 warp 在飞的访存条数
```

三个因子都能拧,但**"一列一线程"把它们全钉死了**:块数 = cols/256,
每块 warp 数 = 8。这道题的全部工作就是把这个乘积抬上去。

### 第二步:路 A —— 一个 block 包下一整列(不用合并)

先把块做成二维的:`threadIdx.x` 是块内的列(保证合并访存),
`threadIdx.y` 是块内的**行并行度**。

```
grid = (ceil(cols/32), 1)     ← 16 个块
```

每个 `(tx, ty)` 线程沿行走 `i = ty, ty+8, ty+16, ...`,只累加自己那一份;
块内用共享内存把这 8 个部分和按列加起来;`ty == 0` 的线程写 `out`。

这一版**不需要任何跨块合并**(一列完整地属于一个 block),代码短、不用
`partial`、不用原子操作。实测 **23%**(1.18 ms)—— 比基线快 2.5 倍。

但别急着高兴,先做这道题最重要的一次计算:**这条路的天花板在哪?**

```
块数 = ceil(cols/32) = 16        ← 128 个 SM 里最多用 16 个
```

现在有个陷阱:**"16 个块"不等于"16 个 warp"。** 块大小是你自己定的 ——
把块加胖,块数还是 16,在飞的 warp 却成倍涨。实测:

| 路 A 的块形状 | 线程数 | 在飞 warp | 实测 |
|---|---|---|---|
| `(32, 4)` | 128 | 64 | 12% |
| `(32, 8)` | 256 | 128 | 23% |
| `(32, 16)` | 512 | 256 | 41% |
| `(32, 32)` | 1024 | 512 | **72%** |

**同一个算法,一行代码没改,只把块加胖,12% → 72%(6 倍)。**
这一列数字是这道题最值钱的一课:慢的不是"单阶段的算法",是**在飞的东西太少**。

但 72% 就是头了:块数被 `ceil(cols/32)` 钉死,而块大小已经用满了
(1024 是上限)。**想再往上,只有一条路:让块数本身变多,而块数只能靠
"把行切开"来变多。**

### 第三步:把行切成段,块间再合并

把 `rows` 切成 `segs` 段(段数不许超过 `max_chunks`),`blockIdx.y` 是段号:

```
grid = (ceil(cols/32), segs)      ← segs=16 就是 256 个块
```

每个块只算自己那一段行的部分和,段与段之间的结果用下面两种方式之一合并。
实测的台阶(块数 → 占峰值):

```
    16 块      32 块      64 块     128 块     256 块
    22%    →    42%   →    71%   →    91%   →    94%
```

**上升段卡在"有多少个块在跑",256 个块以后走平** —— 因为卡已经填满了,
再多的块只是排队。**拐点在"每个 SM 至少一个块"附近**,而且 64 → 128 个块
之间是个台阶(71% → 91%),不是斜坡。

### 第四步:合并那一步的账

**合并法一:`atomicAdd`。** 块内归约完直接 `atomicAdd(&out[col], 部分和)`。

- 最省事,但 ⚠️ **`out` 每轮开始前是毒值,你必须在 launcher 里先清零**
  (`cudaMemsetAsync(ctx.out, 0, sizeof(float)*ctx.cols, ctx.stream)`)。
  这一趟 memset 也要花时间,它算你的账。
- 好消息:同一个 warp 的 32 个 lane 加的是 **32 个不同的地址**(列不同),
  没有 16 题那种"一条指令 32 个 lane 抢同一个地址"的争用。实测 93%。

**合并法二:`partial` + 第二个 kernel。** 阶段一每个 `(段, 列)` 写一个部分和到
`partial[seg * cols + col]`,阶段二一个线程负责一列,把 `segs` 个部分和加起来。

- 结果完全确定(加法顺序固定),不用 memset。参考解走这条。
- ⚠️ **别让第二个 kernel 变成新的基线**:它只有 `cols` 个工作项 ——
  又回到"输出少"那一侧了。它必须**便宜**,靠的是把数据量压小:
  它的流量是 `2 * segs * cols * 4` 字节,占总流量的比例是 `2 * segs / rows`
  (**和 `cols` 无关**)。`segs = 8` 时是 0.01%,`segs = 256` 时是 0.4%。

所以 `segs` 不是越大越好:它同时决定"第一阶段有多少块"(要够)和
"第二个 kernel 有多少活"(要少)。实测 8 到 256 之间都在噪声里。

## 陷阱提醒

1. **`cols` 不是 32 的倍数时,列 tile 有尾巴。**
   `ragged` 用例 `cols = 509`,`ceil(509/32) = 16` 个 tile 覆盖 512 列 ——
   每行多出 **3 个越界列**。这些线程必须 ① 不读 `x`(越界读会读到哨兵区,
   memcheck 会报)、② 不写 `out`(越界写,哨兵区会告诉你往后越界了几个元素)。
   常见的半对写法是"读的时候判了、写的时候忘了"。

2. **行分段除不尽。** `rows = 131071`,`segs = 16` 时每段 8191 或 8192 行。
   用 `r0 = rows*seg/segs`、`r1 = rows*(seg+1)/segs` 这种算法就不会漏也不会重;
   用 `rows/segs` 再乘回去,最后一段就会漏掉几行 —— 而漏掉的那几行在 `big`
   用例上可能正好是 0(`rows` 被整除),到 `ragged` 上才炸。
   **每一个越界和漏算,都要在两个可评级用例上各验一遍。**

3. **块内按列归约必须 `__syncthreads`。** 那一列有 8 个部分和分散在 8 个 warp
   (每个 warp 的 `ty` 固定),只能用共享内存 + `__syncthreads` 归约 ——
   shuffle 跨不了 warp。少一个 `__syncthreads` 就是"读到了别人写了一半的格子",
   结果**有时对有时错**,跑一次抓不住(`repeat=3` 和 racecheck 就是为它准备的)。

4. **共享内存的 bank 冲突。** 布局写成 `sm[ty][tx]` 时,同一个 warp 的 32 个 lane
   (tx = 0..31,ty 固定)落在 32 个不同的 bank 上,没有冲突。
   写成 `sm[tx][ty]` 就变成 32 个 lane 全落在同一个 bank 上 —— **32 路冲突**,
   这一小段代码会比你想象的贵得多(03 题讲过同一件事)。

5. **为什么这题没有容差 —— 而且这不是刁难。**
   `x` 的元素都是 `0..99` 的整数,最大的和是 `131072 × 99 = 12,976,128`,
   小于 f32 能精确表示整数的边界 `2^24 = 16,777,216`。因此**每一步部分和都是
   精确可表示的整数,浮点加法在这里不产生任何舍入**。
   顺序加、树形加、`atomicAdd` 乱序加,结果都**逐位相同** ——
   换任何累加顺序都不是借口。(15 题讲过反面:那里是 `[-1,1)` 的浮点,
   有舍入有对消,所以必须给容差。)

6. **`(long)i * cols` 里的宽化不能省。** 本题的规模下 `int` 装得下
   (最大下标 6710 万),但把它写成 `long` 是一个该养成的习惯 ——
   等到 rows×cols 超过 21 亿时,`int` 会**静默**回绕成一个合法下标,
   那是最难查的一类 bug。

## 评分说明

正确性决定通过与否(逐位精确相等);性能给 S / A / B / C,不卡关。

性能用**有效带宽占峰值百分比**评级。框架算的字节数是"`x` 读一遍 + `out`
写一遍"(256MiB + 2KiB),所以 **100% 的含义是:每个输入元素恰好从显存
走了一次**。你自己多搬的那一趟(partial、memset)不会从分子里扣,
但会实打实地花掉时间 —— **它就体现在分数上**。

**门槛:B = 30% / A = 50% / S = 78%。**

实测的完整分档(4090,框架自动清 L2,big 用例 —— 同一批测出来的):

| 实现 | 块数 | 占峰值 | 评级 |
|---|---|---|---|
| 基线:一列一线程 | 2 | 9% | C |
| 路 A `(32, 4)` = 128 线程 | 16 | 12% | C |
| 路 A `(32, 8)` = 256 线程 | 16 | 23% | C |
| 路 A `(32, 16)` = 512 线程 | 16 | 41% | B |
| 两阶段 `segs=2` | 32 | 42% | B |
| 两阶段 `segs=4` | 64 | 71% | A |
| 路 A `(32, 32)` = 1024 线程 | 16 | 72% | A |
| 两阶段 `segs=8` | 128 | 91% | S |
| 两阶段 `segs=16` ← **参考解** | 256 | **94%** | **S** |
| 两阶段 `segs=32` | 512 | 93% | S |

(同一批里 ragged 用例上参考解是 92%。)

**参考解(`leet solution 17`)实测 0.285~0.287 ms / 936~943 GB/s / 93~94% 峰值
(big)、92%(ragged),拿到 S。** 另外两条完全不同的路(胖块路 A + 原子合并)
也都落在 90% 以上 —— 详见参考解里的实测表。它们唯一的共同点是
**在飞的 warp 有上千个**。(这张卡是和别人共享的,跨次测量会漂 ±3~5%,
所以上面的数字写成区间。)

阶梯的含义:

- **B(30%)**:你已经意识到"一输出一线程"这件事本身是错的,并且真的动手
  把 `rows` 切开(哪怕只切了 2 段),或者把块加胖到 512 线程以上。
- **A(50%)**:并行度这一维你填到了 64 个块上下,但离"每个 SM 都有活干"
  还有距离。
- **S(78%)**:块数上到 128 个以上。注意 71% → 91% 之间实测**没有中间档**:
  64 个块和 128 个块之间,是"一半的 SM 在干活"和"每个 SM 都在干活"的差别,
  它是个台阶,不是斜坡。

## 思考题

1. **维持同样的数据量(256MiB),把 `cols` 从 512 改成 262144、`rows` 改成 256。**
   基线还会"饿死"吗?路 A(一个块包一整列)还需要"切行"吗?
   再想想:**"一个输出一线程"这个写法,它的适用条件到底该怎么表述?**
   (提示:不是"输出多不多",而是"输出的个数换算成块数之后,和这张卡的
   SM 数是什么关系"。这题的 `cols = 512 ⇒ 16 个块` 才是病根。)

2. **`segs` 是参考解里唯一的自由参数。** 把它从 1 扫到 `max_chunks`,
   记下曲线的形状。它的**上升段**卡在什么上?**下降段**卡在什么上?
   如果让你给一个"不管 `rows` 多大都合适"的经验公式,你会怎么写?
   (`rows = 257` 的 `tiny` 用例上,你那个公式给出的段数还合适吗?)

3. **先预测,再实测:只改 lane→数据的映射,语义一个字不改。**
   让同一个 warp 的 32 个 lane 去读**同一列的 32 个不同行**(而不是相邻的
   32 列)—— 也就是把 `threadIdx.x` 和 `threadIdx.y` 的角色对调。
   你的预测是多少?**掉到 1/8?掉一半?还是基本不变?**
   跑的时候**一定要在不同的块数下各测一次**(比如 128 个块和 2048 个块)。
   跑完回答两件事:
   ① 为什么它会掉,而**不是**掉到 1/8?(算一算:一个 warp 的一条 load 落到
   几个 32 字节的 sector 上、每个 sector 里真正被用到的有几个字节、
   剩下的字节被谁捡走了?)
   ② 为什么**块数少的时候它反而好看**?这说明"我改成散读之后分数没掉"
   能证明什么、不能证明什么?

4. **`atomicAdd` 和 `partial + 第二个 kernel` 两条路,在 `tiny` 用例
   (`rows = 257`)上谁快?** 在 `big` 用例上谁快?如果答案不一样,
   那"哪个方案更好"这句话缺了什么前提?
