# py04 逐行 argmax(分类预测)

> 难度 ●●○○○ · 标签 `argmax` `sort` `memory-access-pattern` `reduction` · 考点:置换类算子与归约类算子的访存模式差异、「我要位置所以要排序」这个直觉的代价、用字节数而不是 API 名字来挑算子

## 题目

给定一个 `rows × cols` 的 `float32` 张量 `x`(按行连续),对每一行给出**最大值所在的列下标**:

```
out[i] = argmax_j x[i, j]
```

并列(同一行有多个相同的最大值)时取**下标最小者**。

```python
def forward(ctx):
    """ctx.x:   (rows, cols) float32 CUDA 张量,按行连续
       ctx.out: (rows,)      int32,需要你写入(或 return 一个新张量)
       ctx.rows / ctx.cols: 形状

    输出两种写法都可以:
       return tensor                 惯用写法,推荐
       写进 ctx.out 后 return None    预分配缓冲
    """
```

语义上这就是分类器推理的最后一步:每行是一个样本在各个类别上的得分,你要给出得分最高的类别。它也等价于「距离矩阵里找最近邻」的 top-1 检索。

## 为什么这道题值得做

前面三道 py 题教的都是「**搬了多少字节**」:py01 的归约维布局、py02 的访存遍数、py03 的物化中间张量。

这道题不一样:**两种写法读的是同一份数据、算出的答案一模一样、连字节数都一样,耗时却相差 12 倍。** 差别只在**访存模式**。

同一份 134MB 数据(`8192 × 4096` f32),四个写着同一个答案的算子:

| 写法 | 耗时 | 以输入计的有效带宽 |
|---|---|---|
| `x.argsort(dim=1, descending=True)` | **1.764 ms** | **76 GB/s** |
| `x.sort(dim=1)` | 1.764 ms | 76 GB/s |
| `torch.topk(x, 1, dim=1)` | 0.828 ms | 162 GB/s |
| **`x.max(dim=1)`**(值 + 下标) | **0.147 ms** | **912 GB/s** |
| `x.sum(dim=1)`(对照:一遍顺序读) | 0.145 ms | 924 GB/s |
| 4090 峰值带宽 | — | 1008 GB/s |

看最后两行:`sum` 和 `max` 一样快。**归约读一遍就够了,它几乎就是带宽墙本身。** 而排序只跑到了峰值的 7.5%。

再看一个形状上的对照(框架实测的加速比,取三个用例的最大值):

| 写法 | 三个用例里的最好成绩 | 评级 |
|---|---|---|
| `argsort`(基线) | 1.00x | — |
| `topk(1)`:不要顺序了,但还在「选择」 | 8.19x | B |
| 读两遍:先求 max,再回头 `==` 找位置 | 15.18x | A |
| **一遍归约 `max(dim=1)` / `argmax`** | **44.27x** | S |

## 慢在哪:排序的代价不在比较,在搬运

一次 GPU 上的 radix 排序要做这些事:

1. 把 f32 键转成可比较的 uint32(负数要翻位);
2. 按 8 位一组,把 32 位键过**好几趟**,每趟都要读进来、算前缀和定位、再写出去;
3. `argsort` 还要把**下标**跟着键一起搬 —— 要搬的数据量直接翻倍,而且下标是 int64,
   比 f32 的键还大一倍;
4. 每一趟的写回都是**置换**:相邻线程写到的目标地址不相邻,一条 cache line 只能
   写进去一部分就有用 —— 显存带宽被浪费掉一大半。

`tall` 用例(`2048 × 16384`,同样 134MB)把第 4 点放大了:那里排序耗时 6.46ms,
有效带宽只有 **20 GB/s**;而同一条路上,归约仍然是 0.146ms —— **和 `square` 一模一样**。

> 这就是本题最值得记住的一句话:
> **归约的代价只取决于「读多少字节」,与形状无关;置换的代价还取决于「搬得顺不顺」。**
> 判断一个算子的代价,先问它「要搬几遍」,再问「搬得顺不顺」。

## 解法思路

**你要的是「一个位置」,不是「一个顺序」。** 想清楚这一点,剩下的事就是去找那个
只读一遍就能给出位置的**归约**算子:

```
x.max(dim=1)      →  (values, indices) 一次归约同时给你两者  0.147ms
x.argmax(dim=1)   →  只给你位置
torch.topk(x, 1)  →  给值 + 位置,但它要做的「选择」比归约贵得多
x.argsort(...)    →  给你全部 cols 个位置 —— 你只需要其中的 1 个
```

从 1.764ms 到 0.147ms,你**没有**做任何「优化」:没有换启动配置、没有手写内核、
没有动数据布局。你只是换了一个**回答同一个问题的算子**。

这道题真正想让你带走的能力是:看到一个 API,能大致说出它要搬几遍数据。
上表里每往上一行,代价就涨一截,而涨的原因全都能用「多搬了哪些字节、搬得顺不顺」
解释清楚。

## 陷阱

1. **别把「先算出来再挑」当成免费**。比如先 `x.max(dim=1).values` 拿到最大值,
   再回头用 `x == v` 找位置 —— 这一下就变成了**两遍读**,而且第二遍还要物化一个
   `(rows, cols)` 的布尔张量。一遍能做完的事分成两遍,就是两倍的字节。
   实测:这条路的成绩是 15.18x,离一遍归约的 44.27x 差着 3 倍 —— 评级会诚实地
   把它放在 A 而不是 S。

2. **dtype**。排序/argmax 类算子返回的是 **int64**,而框架的 `out` 缓冲是 **int32**。
   本题的框架对返回的张量做了对齐,不转也能通过 —— 但**别把这个当成习惯**:
   索引也是数据,真实代码里 int64 的索引会让后续的 `gather` / `index_select`
   多搬一倍的字节,而且这种浪费藏在参数里,不看 dtype 根本发现不了。

3. **并列的规则**。「下标最小者」要写进实现里:你选的算子符不符合这条规则?
   (本题的随机填充是均匀分布,一行里出现并列最大值的概率极低,所以对拍不会暴露
   这个问题 —— 但**规则模糊**比**精度误差**更容易让人栽跟头,真实 logits 里
   并列是常事。)

4. **别用 `ctx.out = ...`**。重新赋值会让框架看不到你的结果(框架会检测并提示)。

5. **别在计时路径里同步**。`.item()`、`.cpu()`、`.numpy()`、`print` 都会强制同步,
   把 GPU 的异步流水打断,而且这段等待会计入你的耗时(框架会检测并提示)。

## 评分

| 评级 | 加速比 | 意味着 |
|---|---|---|
| B | ≥ 3.0x | 你已经不靠全排序了(比如换成了 topk) |
| A | ≥ 10.0x | 连「选择」也去掉了,但还在读两遍 |
| S | ≥ 25.0x | 一遍读完 —— 贴着带宽墙(实测天花板 44.27x) |

评级取各用例的**最大值**。`tiny`(37×53)不参与评级 —— 那个量级上测的是启动开销,
不是访存模式。

## 思考题

1. **算一遍排序的流量**。假设排序要过 4 趟,每趟读写一对 (f32 键 + int64 下标)。
   总字节数是「把 x 读一遍」的几倍?用实测的 1.764ms 反推它的有效带宽,和你算出来的
   倍数对得上吗?对不上的部分,是 cache 帮了忙,还是「写了但没写满 cache line」
   被带宽记了两次账?

2. **k 变大之后呢?** 如果要求「每行**前 8 个**最大值的下标」,`torch.topk(x, 8)`
   实测是 0.838ms —— 比排序快 2.1 倍,但比求一个最大值慢 5.7 倍。为什么它处在中间?
   提示:k 小的时候选择可以「边扫边淘汰」,k 大的时候呢?想想 k = cols 的 90% 时,
   排序还是不是错的答案。

3. **同时要值和下标,要多读一遍吗?** `x.argmax(dim=1)` 只给下标;如果你还需要那个
   最大值本身,直觉上是不是要再读一遍数据?实测 `x.max(dim=1)`(一次返回两者)和
   `x.sum(dim=1)` 一样快(0.147 vs 0.145ms)—— 这说明归约内核在**一次遍历**里
   可以同时维护多少个累加器?这个上限由什么决定(提示:寄存器/片上存储)?

4. **换一个维度会怎样?** 把问题改成对 `dim=0` 求 argmax(每列的最大值在第几行),
   在同一台机器上会更快还是更慢?先不要跑,用「访存是否连续」预测一下,再验证。
   (这条规律和 py01 是同一个,但请自己推一遍。)
