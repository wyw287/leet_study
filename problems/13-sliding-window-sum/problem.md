# 13 · 滑动窗口求和(大窗口)

## 题目描述

给定 n 个 0..99 之间的整数 `x[0..n-1]`,对每个位置 i 求**长度为 w 的尾窗**之和:

```
out[i] = x[max(0, i-w+1)] + x[max(0,i-w+1)+1] + ... + x[i-1] + x[i]
```

也就是"以 i 结尾、最多往前数 w 个"的那一段的和。数组开头那 w-1 个输出,
窗口是不满的(被裁到下标 0)—— 这是题目的一部分,不是边界 bug。

框架负责分配、搬运、计时、校验,你只写 kernel 与启动配置:

| | |
|---|---|
| `ctx.x` | `const int*`,长度 `ctx.n`,每个元素在 0..99 之间 |
| `ctx.out` | `int*`,长度 `ctx.n`,需要你写入 |
| `ctx.tmp` | `int*`,长度 `ctx.n`,**scratch**:内容不初始化、不参与对拍。用不用随你 |
| `ctx.n` | 元素个数(运行时才知道) |
| `ctx.w` | 窗口长度(运行时才知道,本题 500 上下,不是 2 的幂) |

**没有容差**:整数输出要求逐元素精确相等。所有位置都要写 —— 校验前 out 会被
填成毒值 `0x5EED5EED`,漏写一个元素就会被抓到。和也不会溢出:512 × 99 = 50688。

## 为什么这道题重要

前面十几道题里,慢的原因几乎都在**"搬得太多"**这一侧:访存没合并(03/08)、
同一份数据从显存读了两遍(09)、原子冲突(07)。

**这一道是反过来的**,而且反得比想象中更彻底:

- 它的**显存流量是满分的** —— 相邻窗口重叠 w-1 个元素,但重复的那些读全被
  L1 接住了,每个 x 元素只从显存走一次。
- 垮掉的是**另一本账:L1 的取数带宽**。

GPU 上的两本账,是这一课要记住的东西:

| 账本 | 全卡能力(4090) | 除以"每秒要过多少个输出"(带宽墙给的是 126e9) |
|---|---|---|
| 显存 | 1008 GB/s,每个输出 8 字节(读 4 + 写 4) | 正好是 1 个输出的量 |
| L1 取数 | ~1e13 条 load/s(128 SM × 32 lane/cycle × 2.5GHz 量级) | **每个输出 ~80 条 load 的配额** |

朴素实现每个输出要发 `w+1 = 513` 条 load —— 超配额 6 倍。所以它的天花板就是
带宽墙的六分之一上下(实测 8%),而它搬的字节数一点没浪费。

**"这个 kernel 慢"要先分清是哪本账。** 这题的答案是:显存那本账没问题,
是 L1 那本账被同一个元素反复取数取爆了。这也是本题唯一一句要背下来的话:

> **命中 L1 不等于免费。** L1 的带宽比显存高一个数量级,但它是有限的;
> 当每个字节被取 w 次,这笔账就会盖过显存。

(w 小的时候配额根本用不完,朴素实现直接贴着带宽墙跑 —— 这题的梯度完全来自
"窗口大"。同一个 kernel,窗口一小就从"没问题"变成"慢十倍"。)

## 基线慢在哪(先看清对手)

`baseline.cu` 是"一个线程算一个输出,把窗口里的数加一遍"。它有两个容易误判的地方:

1. **合并访问是满分的。** 同一个 warp 的 32 个线程在每个 j 上读的是连续的
   32 个 int(128 字节 = 4 个 sector)。
2. **显存流量也是满分的。** 每个 x 元素只从显存取一次,其余 w-1 次读全在
   L1 里命中(一个 warp 的活跃工作集只有 (w+32) 个 int ≈ 2KB)。

它不是"访存没写好",是**取数次数太多**:同一个元素被从 L1 里取了 w 次,
每次都要占一条 load 指令的位置。

## 解法思路

**第一步:把重复取数砍掉。** 相邻两个输出的窗口只差两个数:

```
out[i] = out[i-1] + x[i] - x[i-w]
```

每个输出的代价从 O(w) 变成 O(1)。这就是 LeetCode 上闭着眼睛写的滑动窗口。
如果故事到这里结束,这题就太简单了 —— 麻烦在于它有个副作用:

**它要求一个线程管连续的一段输出**(它得复用上一个结果)。于是同一个 warp 的
32 个 lane 在每个时刻访问的地址相隔 CHUNK 个元素,一条 load 指令被拆成 32 个
sector,每个 lane 还独吞好几条 cache line —— **08 题那个坑原样回来了**。

**实测:直接这么做,等于白改。** 每个线程管 128 个输出时是 19%,管 32 个时
是 11% —— 比基线(8%)快两倍,离带宽墙还有五倍。**"少算"和"会合"是两本独立
的账,这一改只是把亏空从"取数次数"挪到了"访存模式"。**

**第二步:选一条路,把两本账都结清。** 两条路都行,代价不同:

- **接受多一趟流量(最容易想到)。** 先算一遍全局前缀和 P 落进 `tmp`,
  再 `out[i] = P[i] - P[i-w]`。两趟都完全合并、指令数极低,但中间结果要落一次
  显存 ⇒ 流量从 8 字节/元素变成 16 字节/元素 ⇒ **物理上限就是峰值的一半**。
  前缀和用 10/11 题那套块内 scan + 跨块 carry 拼出来即可(中间值最大 1.66e9,
  int32 刚好够,再大就得 int64)。这条路演示的是:**想省掉重复计算,不一定
  非要融合 —— 也可以付一趟流量,前提是你知道这一趟值多少。**
- **把"连续"这件事从线程手里拿走,交给 warp(推荐)。** 一个 warp 领一段连续
  输出:warp 内 32 个 lane 仍然**交错**取数(合并访问保住),而"滚动"这件事由
  warp 内的**前缀和**完成 —— 第 i 个输出等于 `carry + Σ_{j≤i}(x[j] - x[j-w])`,
  那个 Σ 就是 `d[j] = x[j] - x[j-w]` 的前缀和。warp 内做前缀和只要 5 步
  `__shfl_up_sync`(10 题学的 scan,在这里派上用场)。每个输出摊到的代价:
  2 条 load + 1 条 sub + 5/32 步 scan + 1 条 add + 1 条 store ≈ 5 条指令,
  对比 80 条 load 的配额 —— 于是又回到带宽墙前面。
- 共享内存中转也能同时满足两者(块内前缀和 + 差分),只是要多一次块内往返
  和一个 `__syncthreads`;注意 bank 冲突(见陷阱 6)。

## 陷阱提醒

1. **滚动和的初值不含 i0。** 初值算的是"窗口 [max(0,i0-w+1), i0]"这个完整
   窗口,**含** i0 —— 然后把这个输出写掉,之后才进"加一个减一个"的稳态。
   含/不含搞错,第一个元素就错。
2. **前 w 个输出没有东西可减。** 只有 `i >= w` 才有 `x[i-w]`。把这段单独写成
   一个"只加不减"的循环,稳态循环里就没有分支了 —— 这题指令数就是命,
   循环里的一个 if 值不少指令。
3. **尾巴。** n 不整除"每线程/每 warp 管的输出数"时最后一段领不满,要用
   `min(n, ...)` 兜住。多写一个 = 越界(哨兵区会抓到);少写 = 毒值残留。
   用 warp 方案时,尾巴上超出范围的 lane 要让它的 `d = 0`(贡献 0、不写出),
   否则前缀和会被污染。
4. **别用 64 位下标。** `long long` / `size_t` 的地址计算在 32 位 ALU 上要多拆
   几条指令。这题 n ≤ 2^31,`int` 够用 —— 而这道题**就是**在数指令。
5. **两趟方案的中间值会到 1.66e9。** 前缀和最大 = n × 99 = 16.7M × 99 ≈ 1.66e9,
   int32 装得下(2.147e9),但只剩 23% 的余量。**这是"刚好够"而不是"安全"** ——
   换个题目参数就该换成 int64 了。
6. **共享内存版的 bank 冲突。** lane 之间相隔 CHUNK 个 int;CHUNK 是 32 的倍数
   时,32 个 lane 全部落在同一个 bank 上 —— 32 路冲突会把共享内存的好处全吃掉
   (共享内存的带宽只有 L1 的同一份,别再喂给它一个 32 倍的惩罚)。
   CHUNK 取 32k+1,或者让 lane 交错领子块。
7. **`__shfl_up_sync` 的 mask。** warp 内做 scan 时所有 lane 都必须参与,
   循环里不能有把 warp 拆开的分支 —— 否则 mask 是错的,结果"有时对有时错"。

## 评分说明

用**有效带宽占峰值百分比**评分:这题的最优解就是贴着带宽墙跑的,带宽占比直接
回答"离墙还有多远、差距是不是从 L1 取多了造成的"。评级取所有可评级用例里的
最好成绩(小用例远低于 20µs,不参与评级)。

实测梯子(4090,框架自动清 L2;big = n=16777216, w=512):

| 实现 | 用时 | 有效带宽 | 占峰值 | 评级 |
|---|---|---|---|---|
| 基线:一输出一线程,窗口加一遍 | 1.683 ms | 80 GB/s | 8% | — |
| 滚动和 + 每线程一段连续输出(CHUNK=32) | 1.187 ms | 113 GB/s | 11% | — |
| 滚动和 + 每线程一段连续输出(CHUNK=128) | 0.700 ms | 192 GB/s | 19% | — |
| 两趟全局:前缀和 + 差分 | 0.415 ms | 324 GB/s | 32% | B |
| 参考解:滚动和 + warp 交错 + shuffle scan | 0.135 ms | 993 GB/s | 99% | S |

门槛卡在实测的空隙里:

| 评级 | 带宽占峰值 | 含义 |
|---|---|---|
| B | 25% | 两本账都结清了 —— 光"少算"不够(19% 那一档就是只做了少算),光"会合"也不够(那是基线)。最低成本的达标方式是两趟方案 |
| A | 45% | 融合了一半,或者把两趟写得更紧(省掉加 carry 那一趟、用 chained scan 一个 kernel 搞定) |
| S | 80% | 只能走融合。两趟方案在物理上到不了这里:它的流量就是 16 字节/元素 |

注意梯子的形状:**11% 和 19% 是同一个坑的两个深度;19% → 32% 要换思路;
32% → 99% 之间没有斜坡** —— 要么把访存修好,要么没有。

## 思考题

1. **把 w 改成 8 会怎样?** 朴素实现每个输出只要 9 条 load,远在 80 条的配额
   之内 —— 它会直接贴着带宽墙。同一份 baseline,窗口一小就"没问题",窗口一大
   就"慢十倍"。**"这个 kernel 慢"从来不是绝对的,它取决于你把两本账一起算
   的结果。** 那么反过来:w=4096 时朴素实现大概会慢多少倍?
2. **命中 L1 到底省了什么、没省什么?** 相邻窗口的重复读全部命中 L1,
   显存那边一个字节都没多搬 —— 可时间还是花了。省下来的是**显存带宽**,
   没省下来的是**L1 的取数带宽和指令发射位**。那为什么"把这段搬进共享内存
   再算"也不解决问题?(提示:L1 和共享内存在硬件上是同一块 SRAM。)
3. **两趟方案的上限为什么恰好是 50%?** 把它的流量一笔一笔数出来
   (读 x / 写 tmp / 加 carry 读 tmp 写 tmp / 做差读 tmp×2 写 out)。
   如果省掉"加 carry"那一趟,流量是多少?再进一步:如果让每个 block 只扫
   自己那一段、跨块的 carry 用 11 题的 chained scan 在一个 kernel 里解决,
   流量还能降到多少?——**这就是从 32% 走到 45% 的那条路。**
