# 符号位图打包

## 题目描述

给你 `n` 个 `float`(值域 `[-1, 1)`),把它们压成一张**位图**:第 `i` 个元素只留
一个 bit —— 它是正数就是 `1`,否则是 `0`。

```
bits[i >> 5] 的第 (i & 31) 位  =  (x[i] > 0.0f) ? 1 : 0
```

`bits` 是一个 `unsigned int` 数组,长度 `nw = ceil(n / 32)`,框架已经算好并作为
参数给你了(不用自己 `ceil`)。位序是 **LSB 对应序号小的元素**:元素 `32w` 落在
`bits[w]` 的第 0 位,元素 `32w+31` 落在第 31 位。

**`bits[w]` 里超出 `n` 的那些位必须是 0。** 比如 `n = 262147`(`nw = 8193`)时,
`n` 落在第 8192 个 word 的第 3 位上 —— 这个 word 只有低 3 位有效,高 29 位全是 0。

输出是整数,框架**逐位精确比较**,没有容差。

## 为什么这道题重要

前面 15 道题的输出都有一个共同点:**一个输出元素至少有一个线程那么大**。
一个线程算一个 `float`、一个 `int`、一行、一个标量 —— 总之"我手里的信息够写我
负责的那个输出"。

这道题第一次打破它:

> **一个 word 里装着 32 个元素的结论,而一个线程只知道其中 1 个。**

这不是"写法不对",这是输出的物理。你没法让一个线程独立地写出一个 word ——
它手上只有 1/32 的信息。于是就产生了一个前面所有题目都不存在的问题:

**32 个线程的结论,怎么汇总成一个输出元素?**

这个问题在真实世界里到处都是,而且不止这一种形态:

- 位图 / 位集合(GPU 上的稀疏性掩码、布隆过滤器、1-bit 量化)
- 直方图(07 题:多个线程的结论汇总到同一个桶 —— 那题用的是"私有化",
  因为它有 256 个桶可以分散;**这题只有 1 个桶要抢**)
- 流压缩 / 前缀和(10、11 题)
- `torch.nonzero`、`cub::DeviceSelect` 这类"把结果挤到一起去"的操作

这道题给的是这个家族里最小的一个样本:只有 1 位宽,只有"汇总"这一个动作,
没有任何算法上的绕路。**把它的账算清楚,后面那些题才有参照。**

## 解法思路

### 第一步:想清楚输出粒度这件事

`n = 2^26` 个元素 → `nw = 2^21` 个 word。输出的元素个数是输入的 1/32。
但**线程数**是你自己决定的 —— 别被"输出元素个数"绑住。

### 第二步:最直白的写法,以及它慢在哪

一个线程管一个元素,是正数就往 `bits[i >> 5]` 的对应位上写:

```cpp
if (i < n && x[i] > 0.0f)
    atomicOr(&bits[i >> 5], 1u << (i & 31));
```

这个写法**是正确的**(原子操作保证同一 word 的 32 个位不会互相踩掉),
而且你已经能预见它的病:

**同一个 warp 的 32 个 lane 处理的正好是同一段 32 个连续元素** ⇒ 它们的
`i >> 5` 完全相同 ⇒ **32 个 lane 全部去 `atomicOr` 同一个地址**。

同一地址的原子操作在 L2 上是**串行**的:每个 lane 都要等一次完整的 L2 往返。
实测这个排队让基线只跑到 **27% 峰值**(1.019 ms,272 GB/s)。

⚠️ 走这条路必须**先清零**。框架每轮校验前会把 `out` 缓冲填成毒值
(`0x5EED5EED`),不清零的话,"一个正元素都没有"的 word 会留着毒值。
清零这一趟也是要花钱的 —— 它是原子方案的附加账。

先把这个版本写出来、跑通、记下它有多慢。**你需要一个真实的分母。**

### 第三步:投票

关键问题是:**怎么让 32 个 lane 一起凑出一个 word,而不是抢?**

CUDA 有一条 warp 级指令专门干这件事(`Warp Vote Functions`):

```cpp
unsigned int m = __ballot_sync(0xffffffffu, pred);
// m 的第 k 位 = 第 k 个 lane 交的 pred
```

于是整个 kernel 变成三句话:

1. 每个 lane 算自己的谓词 `pred = (i < n) && (x[i] > 0.0f)`;
2. 一条 `__ballot_sync` 把 32 个谓词变成一个 word;
3. 每个 warp 的 **lane 0** 把结果写进 `bits[i >> 5]`。

为什么 lane 0 的下标正好是它管的那个 word 的左端点?因为块大小是 32 的倍数,
所以一个 warp 的 32 个 lane 拿到的下标是 `base .. base+31`,而
`base = blockIdx.x * blockDim.x + warpId * 32` 一定是 32 的倍数 ——
这 32 个元素正好落在 word `base >> 5` 里。

**这不是巧合,是"线程映射必须和输出粒度对齐"的直接后果。** 如果让线程跳着
取数(比如 `i = threadIdx.x * gridDim.x + blockIdx.x`),一个 warp 的 32 个位就
不属于同一个 word,整个方案立刻垮掉。

顺带一个好处:现在每个 word 都被恰好一个 lane 0 线程**完整地覆盖写**,
所以**不需要清零**。(可以自己证一下"没有 word 会被漏掉":对任意
`w < nw`,元素 `32w` 一定存在,而 `grid*block >= n > 32w`,所以一定有线程拿到
下标 `32w`,它一定是某个 warp 的 lane 0。)

### 但是:"抢得凶"和"搬得散"是两个独立的病

上面这条路走通了会拿到 S。但在你动手之前,先把下面这件事想清楚 ——
**它是这道题最容易踩的坑,而且踩了以后你还会以为自己已经赢了:**

> 「我不用原子操作不就行了?让一个线程管一整个 word,自己拼出来再写。」

这个写法是对的,而且它彻底消灭了争用(每个线程独占一个 word,连原子都不需要)。
但它把**连续性**从 warp 手里拿走了:同一个 warp 的 32 个 lane 访问的地址相差
32 个 `float` = 128 字节,一条 load 指令要碰 32 个不同的 sector。
实测它只有 **32%** —— 比基线好一点点,离墙还差三倍。

**避开原子 ≠ 变快。** 你得同时把两件事做对:

| 病 | 症状 | 药 |
|---|---|---|
| 抢得凶 | 同一地址被 32 个 lane 轮着访问 | 让每个 word 只有一个写者(投票 / 私有化) |
| 搬得散 | 一条 load 指令碰 32 个 sector | 让相邻 lane 访问相邻地址 |

这两个病可以独立发生,也可以同时发生。**只治一个,分数基本不动。**

## 陷阱提醒

1. **`__ballot_sync` 必须全 warp 参与。**
   写成 `if (i >= n) return;` 再投票,就是"部分线程参与 barrier" ——
   未定义行为,实测会给出残缺的 word。越界的 lane 必须**走到**投票指令,
   只是交一个 `false`。正确写法是把边界写进谓词里:

   ```cpp
   const bool pred = (i < n) && (x[i] > 0.0f);   // 短路,不会越界读
   ```

   (注意 `&&` 的短路在这里是必须的:先判 `i < n` 才不会去读 `x[i]`。)

2. **尾巴位。** `n` 不是 32 的倍数时,最后一个 word 的高位必须是 0。
   投票方案天然正确(越界 lane 交的是 `false`),但如果你用"一个线程管 32 个
   元素"的循环写法,就**必须自己把没读到的位留成 0** —— 忘了就是一个
   `0xFFFFFFFF` 打进输出。

3. **`w < nw` 的保护不能省。** `grid` 是向上取整的,最后一个块里可能有整段
   越界的 warp,它们的 lane 0 的下标已经 `>= n`,`i >> 5` 可能已经 `>= nw`。
   少这个判断会写到哨兵区,框架会立刻告诉你"往后越界了几个元素"。

4. **别依赖"读越界会读到负的哨兵值"。** 哨兵区的填充值是 `-1.2345678e33`
   (负数),所以 `x[i] > 0` 对越界元素会"碰巧"给出 `false`,你的尾巴可能
   看起来是对的。这是巧合,不是正确性:`memcheck` 会抓越界读,而且网格一开大
   就会读到分配之外的地址(那时是段错误)。

5. **块大小必须是 32 的倍数。** 否则一个 warp 会横跨两个块,"lane 0 的下标 =
   word 左端点"这条推理就不成立了。

6. **`nw` 是给你的,不要自己重算。** 题面里 `ceil` 的定义和框架算的一致,
   但你自己算容易在边界上差一。

## 评分说明

正确性决定通过与否(逐位精确相等,没有容差);性能给 S / A / B / C,不卡关。

性能用**有效带宽占峰值百分比**评级 —— 框架算的字节数是"输入 + 输出各一遍"
(256MiB + 8MiB = 264MiB),所以 **100% = 你把 `x` 恰好读了一遍、把 `bits`
恰好写了一遍**。这是一个绝对的刻度,它直接回答本题唯一的问题:

> 你的读,离那面带宽墙还有多远?

注意写那头只占 3%(8MiB / 264MiB),所以"优化写"是一笔不值钱的账。

**门槛:** B = 38% / A = 62% / S = 82%。

**参考解(`leet solution 16`,`__ballot_sync` 版本)实测 0.293 ms / 945 GB/s /
94% 峰值,拿到 S。** 另外三条完全不同的路也都落在 84%~94% —— 详见参考解里的
实测表。它们唯一的共同点是"合并地读一遍、每个 word 只有一个写者"。

实测的完整曲线(4090,框架自动清 L2,big 用例)长这样:

```
   27% ──── 32% ............ 44% .......................... 84% ─ 87% ─ 92% ─ 94%
   32 路争用  搬得散        16 路争用                        不抢了,贴墙
     C          C              B                              S
```

也就是说:**C 到 B 之间要换一次思路(动争用),B 到 S 之间要再换一次
(把争用基本消掉)。中间那一大段 44%→84% 实测是空的 —— 不是门槛没设好,
而是这题的物理:16 路争用和 8 路争用之间没有中间态。**

## 思考题

1. **先预测,再实测。** 把一个线程管 1 个元素改成管 2 个、4 个、8 个
   (拼出几个位之后还是一两次 `atomicOr`),争用路数会从 32 路降到 16、8、4 路。
   你觉得分数会怎么走 —— 线性上涨?还是涨到某一档就不动了?
   **为什么"不动了"?那个拐点说明瓶颈换成了什么?**

2. **`tiny` 用例(262147 个元素、8193 个 word)上,基线和参考解差多少?**
   big 用例上两者差 3.5 倍。如果 tiny 上差距小得多,那"原子操作慢"这句话
   到底哪里说错了?正确的说法应该是什么?

3. **如果题目改成"每 32 个元素里有多少个正数"(每个 word 存一个 `0..32` 的计数,
   需要 6 位),投票方案还成立吗?`__ballot_sync` 能用上吗?**
   提示:想想 `__popc(__ballot_sync(...))` 给出的是什么(它是**每个 lane 都
   拿到同一个数**,还是一个 lane 一个数?),以及"32 个 6 位的数怎么塞进
   6 个 word"比"32 个 1 位的数塞进 1 个 word"难在哪里。
