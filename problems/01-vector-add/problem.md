# 01 向量加法

> 难度 ●○○○○ · 标签 `elementwise` `memory-bound` · 考点:线程索引、边界判断、启动配置、内存合并

## 题目

给定两个长度相同的 `float` 数组 `a` 和 `b`,计算逐元素之和写入 `c`:

```
c[i] = a[i] + b[i]        i = 0 .. n-1
```

这是 CUDA 的 "Hello World"。它简单到不需要任何算法技巧 —— 但它把 CUDA 最核心的
三件事一次性摆在你面前:**谁负责算哪个元素、怎么启动、以及什么叫访存瓶颈**。

## 你要写的接口

框架已经把数据搬到 device 上了,你拿到的是现成的 device 指针:

```cuda
__global__ void vecadd(const float* a, const float* b, float* c, int n);

void vecadd_launch(LaunchCtx& ctx);   // ctx.a / ctx.b / ctx.c 是 device 指针,ctx.n 是长度
```

分配、搬运、计时、校验、越界检测全部由框架负责,你**不需要**写 `cudaMalloc` 或
`cudaMemcpy`。请只改 `template.cu`(或 `solutions/` 下的副本)。

## 提示

1. **线程索引**:`int i = blockIdx.x * blockDim.x + threadIdx.x;`

2. **边界判断不能省**。用例里的 `n` 是 `16777259`(质数),不会被线程块大小整除。
   少了 `if (i < n)`,最后那一批线程就会越界写 —— 框架在每块缓冲前后都放了哨兵区,
   会直接告诉你「往前/往后越界了多少个元素」。

3. **启动配置由你决定**,这本身就是考点:

   ```cuda
   int block = 256;
   int grid  = (ctx.n + block - 1) / block;   // 向上取整
   vecadd<<<grid, block>>>(ctx.a, ctx.b, ctx.c, ctx.n);
   ```

4. **合并访问 (coalescing)**:相邻线程访问相邻地址,硬件才能把它们合并成
   尽量少的显存事务。`i = blockIdx.x*blockDim.x + threadIdx.x` 配合
   `grid = ceil(n/block)` 天然是合并的。反过来,如果把下标写成
   `i = threadIdx.x * gridDim.x + blockIdx.x` 就会退化成跨步访问,带宽会掉一大截
   —— 值得亲手试一次,感受差距。

## 关于评分:这道题没有优化空间

向量加法是**访存瓶颈**题:每个元素只做 1 次加法,但要搬 12 字节(读 a、读 b、写 c)。
计算完全被访存掩盖。

这意味着**最朴素的实现已经是理论最优** —— 任何"优化"都不会让它更快。所以本题不按
加速比评分(所有正确实现的加速比都是 1.0x,毫无区分度),而是按
**有效带宽占理论峰值的百分比**评分。

这道题真正的价值是给你一个**标尺**:第一次亲眼看到 `~1000 GB/s` 这个数字(4090 的
理论峰值是 1008 GB/s),记住它。后面做转置、归约、矩阵乘时,你会反复回到这个数字
来判断"我离带宽天花板还有多远"。

> 判分时框架会自动清空 L2 缓存。否则几 MB 的题目会整个驻留在 4090 的 72MB L2 里,
> 测出来的是缓存带宽(远高于显存带宽),数字毫无意义。这也意味着你看到的是真实的
> 显存带宽。

## 思考题(不影响判分)

1. 试着把线程块大小改成 32、64、1024,带宽会怎么变?为什么 256 或 512 通常最好?

2. 用 `float4` 一次读 4 个元素(即每线程处理 4 个元素),带宽能超过 100% 峰值吗?
   为什么**不能**?(提示:1010 GB/s 这种数字是怎么来的?)

3. 如果 `n = 0`,你的 kernel 还能正常跑吗?框架会怎么处理?试着把用例改小到
   `n = 1` 看看会发生什么。
