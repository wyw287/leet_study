# 行内前缀和(并行 scan 入门)

## 一、题目描述

给你一个 `rows × cols` 的行优先矩阵 `x`,对**每一行独立地**做 inclusive 前缀和
(又叫 running sum / prefix sum / scan):

```
y[r][0] = x[r][0]
y[r][c] = y[r][c-1] + x[r][c]           (0 < c < cols)
```

每一行从行首累加到行尾,**行与行之间没有任何关系**。输入全是正数(`x ∈ (0,1]`),
所以每行末尾的值约等于 `cols / 2`。

你要写的接口(见 `template.cu`):

| | |
|---|---|
| 输入 | `ctx.x`:长度 `rows*cols` 的 device 指针 |
| 输出 | `ctx.y`:长度 `rows*cols`,由你写入 |
| 规模 | `ctx.rows` / `ctx.cols`,运行时才知道 |
| 入口 | `__global__ void row_scan(...)` + `void row_scan_launch(LaunchCtx&)` |

数据分配、搬运、计时、对拍、越界与竞态检查都由框架负责,你只写 kernel 和启动配置。

## 二、为什么这道题重要

你前面做过的题——向量加法(01)、卷积(05)、矩阵乘(06)、softmax(09)——
有一个共同点:**每个输出元素都能独立算出来**。想并行?把它们摊给线程就行,
线程之间不需要说话。

前缀和不是这样。`y[r][c]` 依赖 `y[r][c-1]`,而 `y[r][c-1]` 又依赖 `y[r][c-2]`……
一直追到行首。这是一条**长度为 cols 的依赖链**。它是你遇到的第一个真正"串行"的
算子,而它偏偏又是并行计算的地基:

* **stream compaction**:把数组里满足条件的元素紧凑地挑出来(先算 0/1 前缀和,
  每个元素的新位置就是它的 exclusive 前缀和);
* **radix sort**:每一趟按一位分桶,桶内偏移就是 scan;
* **稀疏矩阵求解、多边形填充、分段统计**(每个 segment 内部独立扫)……

这些算法写不顺,基本都卡在 scan 上。所以并行计算课讲完 reduce,下一个一定讲 scan。

历史上它也是"并行前缀和"这门技术的起点:Blelloch 1990 年的论文就是讲怎么用
O(n) 的总工作量把 scan 并行化——那正是本题参考解用的思路。

## 三、基线慢在哪(先看清对手)

`baseline.cu` 是"把题目直译成 CUDA"的第一反应:**一个线程扫一行**。

```cuda
int r = blockIdx.x * blockDim.x + threadIdx.x;
float acc = 0.f;
for (int c = 0; c < cols; ++c) { acc += xr[c]; yr[c] = acc; }
```

它一点都没写错:依赖链天然满足,不需要同步,也不会有竞态。它只是慢,
而且慢的原因有两个**互相独立**的物理问题:

**① 访存不合并(coalescing 失效)。** 同一个 warp 的 32 个线程,分别在扫 32 个
**不同**的行:线程 `r` 访问 `x[r*cols + c]`,相邻线程的地址差 `cols×4 = 4KB`。
显存是按 128 字节的 cache line 取数的,而一个线程一次只用到其中 4 个字节——
**有效带宽掉到 1/32 以下**。这是 01 题里"把下标写成跨步的"那个实验的极端版本:
那里跨步 32,这里跨步 4096 字节。

**② 并行度只有 rows 个线程。** 4090 有 128 个 SM,能同时容纳十几万个线程;
这里只有 3 万多个线程在干活,每个 SM 摊到 1 个 block。更糟的是,每个线程内部是
一条 **cols 长的依赖链**(`acc += x[c]` 必须一步一步来,一次加法要等上一次的结果),
而显存延迟有 600 个周期——没有足够多的 warp 去遮盖它。

这两条必须**同时**修。只修①(比如让一个 block 扫一行、但只有线程 0 在扫),
并行度还是 rows 个线程,成绩会好一些但仍然远不如预期;只修②(让更多线程
各扫一行的一部分)而访存依旧跨行,带宽还是上不去。

## 四、解法思路

大方向:**把并行度从"行间"挪到"行内",把访问从"跨行"变成"连续"。**

**第 0 步(模板已经给出):一个 block 负责一行,合并地把整行搬进共享内存。**

```cuda
const int r = blockIdx.x;                     // 一行一个 block
for (int c = t; c < cols; c += BLOCK) row[c] = xr[c];
__syncthreads();
```

`c = t; c += BLOCK` 这个**跨步**写法是关键:同一 warp 的 32 个线程地址连续,
一次 128 字节的访问全部用上。这一步就把问题①解决了,而且整行留在了片上,
后面再怎么折腾都不再碰 DRAM。

**第 1 步:在共享内存里做 scan。两条路,任选一条。**

**路 A — Hillis-Steele(步数少,总功多)。** 让步长 `d` 从 1 翻倍到 `cols`,
每一轮做 `row[c] += row[c-d]`(`c >= d` 时):

```
d=1:  [a, a+b, b+c, c+d, ...]
d=2:  [a, a+b, a+b+c, a+b+c+d, ...]
d=4:  ...
```

`log2(cols)` 轮之后每个位置拿到的就是完整前缀和。总工作量 `O(cols·log cols)`,
关键路径只有 `O(log cols)` 步。

> ⚠️ **不能就这么原地写。** 同一轮里线程 A 可能已经改掉了 `row[c-d]`,
> 而线程 B 还要读它。两种改法:① 把结果先算进寄存器,`__syncthreads()` 之后再
> 写回原位;② 开两块共享内存乒乓(读 A 写 B,下一轮反过来)。

**路 B — 两段式(总功 O(cols),参考解用的就是它)。** 核心观察是:
**串行 scan 的代价在那条依赖链,而不在那 n 次加法。** 所以

1. 把行切成 `BLOCK` 段,第 `t` 段是 `row[t*K .. t*K+K)`,`K = ceil(cols/BLOCK)`;
2. 每个线程把自己这一段**串行**扫掉(链长从 `cols` 降到 `K`),顺便记下段总和;
3. 对这 `BLOCK` 个段总和做一次块内 scan,得到每段的 exclusive 偏移
   (它前面所有段的和);
4. 每个线程把偏移加回自己那一段,写回 DRAM。

总功 `O(cols)`,关键路径 `O(cols/BLOCK + log BLOCK)`。

**第 2 步:合并地把结果写回 `yr[]`**(还是跨步写法)。

**为什么这两条路都能拿满分?** 因为这道题的瓶颈是 DRAM:每个元素固定 8 字节
流量(读 4 + 写 4)。共享内存是**片上**的——4090 每个 SM 每周期能读写 128 字节,
128 个 SM × 2.5GHz ≈ 41TB/s,是 DRAM 峰值(1TB/s)的 **40 倍**。
路 A 多做的 `log2(cols) ≈ 10` 倍工作全落在共享内存上,折合下来还不到 1 个周期/元素,
而省掉的 DRAM 往返是几百微秒。**先搞清瓶颈在哪个部件,再去优化它**——
这句话是这道题最想教的东西。

## 五、陷阱提醒

* **`__syncthreads()` 的位置。** 原地扫描的每一步里,"读 `row[c-d]`"和
  "写 `row[c]`"必须被同步隔开。少一个不会立刻报错,而是**有时对有时错**
  (取决于 warp 的调度顺序)——对拍 `repeat=3` 就是为这种错误准备的。
* **`__syncthreads()` 不能放进"只有部分线程会走"的分支里。** 块内所有线程
  必须走到同一个同步点,否则行为未定义(通常表现为挂死)。
* **cols 不整除 BLOCK**(本题 1280 = 5×256 正好整除,但 511 不整除):
  跨步循环天然能处理,但**共享内存里没被写到的位置是垃圾值**,别去读它。
  两段式里对应的坑是"最后一段比 K 短"和"有些线程一段都领不到",都要照顾。
* **cols 不是 4 的倍数**(如 511):这时行首地址不一定是 16 字节对齐的
  (`r*cols` 个 float),**`float4` 向量化读写会直接失败或越界**。
  要么放弃向量化,要么按 `cols % 4 == 0` 分支处理。
* **cols 很大时共享内存装不下。** 动态共享内存默认上限 48KB,一行最多约
  1.1 万个 float(还要留出块内 scan 的暂存区)。本题最长 1280,不用担心,
  但你要知道再长就得改算法(分块扫,或者一个 block 处理多行)。
* **别把"扫一行"和"扫一列"搞混。** 行优先存储下,列方向的连续元素在内存里
  隔了 `cols` 个位置——这道题只要求行内,不要顺手做转置。

## 六、评分说明

**正确性决定通过与否,性能只评级(S/A/B/C),不卡关。**

性能按"相对基线的**加速比**"评级。这里的基线不是最优算法(它同时犯了
访存不合并和并行度不足两个错),所以加速比是有物理含义的:
**它直接就是你修掉了多少。**

实测(4090,框架自动清 L2;两个可评级用例都是 134MB,加速比几乎一样,
下表只列 square):

| 实现 | square 耗时 | 加速比 | 评级 |
|---|---|---|---|
| 把 scan 做在**全局内存**上(Hillis-Steele,10 趟) | 1.230 ms | 0.80x | C |
| **基线**:一个线程扫一行 | 0.983 ms | 1.00x | — |
| 半成品:搬进共享内存,但块内只让线程 0 串行扫 | 0.253 ms | 3.89x | S |
| **参考解**:块内两段式并行 scan | 0.241 ms | 4.08x | S |

**这张表里最该记住的是:它是台阶,不是斜坡。** 1.0x 和 3.9x 之间基本是空的 ——
因为 DRAM 流量被题目定死了(读 4 字节 + 写 4 字节 = 8 字节/元素),任何
"访存合并 + 并行度足够"的实现都会撞到同一堵墙:

```
268MB / 1008GB/s ≈ 270µs        ← 这道题的物理下限
```

第四行比第三行只快 5%:块内那条 `cols` 长的串行依赖链,被同一 SM 上同时驻留的
8 个 block 之间的并行度遮盖掉了。所以门槛定在 3.5x 而不是 2x ——
**中间地带只留给"修了一半"的实现**(比如只合并了读没合并写、驻留数掉下来了、
或者干脆把 scan 做在全局内存上:算法是对的,DRAM 流量却是 120 字节/元素,
比基线还慢,只有 0.80x)。

* **B = 1.5x** —— 显著超过基线,说明你至少动了结构;
* **A = 2.5x** —— 爬到了台阶中段;
* **S = 3.5x** —— 结构对了、贴着带宽墙(实测两个不同的正确实现分别拿到
  3.89x 与 3.96x,门槛留了 10% 余量)。

评级取所有可评级用例里最好的一次。参考解 `leet solution 10` 拿到 **S**。

## 七、思考题

1. **先预测,再实测:半修版能拿多少分?** 把基线改成"一个 block 扫一行、
   整行搬进共享内存,但块内只让线程 0 从头串行扫到尾(其余 255 个线程只负责搬运)"。
   访存合并了,可块内那条 `cols` 长的依赖链还在。先写下你的预测,再写出来跑一遍。
   实测是 **3.89x** —— 和完全并行的参考解(4.08x)只差 5%。
   为什么那条串行链几乎没有代价?提示:同一个 SM 上同时驻留几个 block?
   每个 block 各有一条**独立**的串行链,它们之间是什么关系?
   把账算出来:DRAM 摊到每个 SM 上是每元素约 2.6 个周期,而 8 条独立的
   串行链合起来是每元素约 0.5 个周期 —— 谁遮盖谁?
   (接着想:如果一行的长度翻 8 倍,共享内存把驻留数压到 1~2 个,这个结论还成立吗?)

2. **总功少 10 倍,为什么一样快?** 路 A(Hillis-Steele)的总功是
   `O(cols·log cols)`,路 B(两段式)是 `O(cols)`。两者实测耗时几乎一样。
   请把这个现象算清楚:共享内存带宽 / DRAM 带宽 ≈ 40,`log2(1024) = 10`——
   算完之后回答:**什么情况下路 B 才会真的赢?**
   (提示:如果每个元素不只要加一次,还要做 50 次浮点运算呢?如果这题不是
   逐元素加法,而是"扫一个 `f64` 数组"、片上流量翻倍呢?)

3. **块内 scan 怎么拼成全局 scan?** 本题一个 block 只碰一行,所以永远不需要
   跨 block 通信。现在假设要扫一个**一维大数组**(1 亿个元素,一行装不下):
   每块先算出自己的块总和,把所有块总和扫一遍得到块偏移,再把偏移加回去——
   听起来很自然,但"所有块总和的 scan"由谁来做?
   * 拆成两个 kernel(块内 scan → 扫块总和 → 加偏移):要读几遍数组?
     中间隔了一次全局屏障,L2(72MB)还留得住数据吗?
   * 能不能在**一个** kernel 里做完?每块算完自己的总和后把它写到一个全局数组里,
     然后**等**前面的块把它们的偏移公布出来(这叫 decoupled look-back)。
     代价是什么?前一块永远不结束怎么办?

   (这道题是 09 题"三趟压成一趟"的续集:那里省的是 DRAM 流量,
   这里省的是全局屏障。)
