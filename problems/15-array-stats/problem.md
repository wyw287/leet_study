# 15 一次遍历算三个统计量(和 / 最小 / 最大)

> 难度 ●●○○○ · 标签 `reduction` `fusion` `memory-bound` · 考点:显存流量账、多遍遍历的代价、跨块归约的两条路

## 题目

给你 `n` 个 `float`(值域 `[-1, 1)`),要同时算出三个统计量:

```
sum     = Σ x[i]
min_val = min x[i]
max_val = max x[i]
```

```cuda
__global__ void array_stats(const float* x, float* partial,
                            float* sum, float* min_val, float* max_val, int n);
void array_stats_launch(LaunchCtx& ctx);
```

三个输出都是**标量**(长度为 1 的缓冲),`n` 最大到 2^26 = 6710 万。

这题默认你已经会写 04 题那种"多块 + 块内归约"的求和了。**它考的是另一个东西:
你打算把这块数据读几遍。**

## 为什么这道题重要

先算一笔账,这笔账就是这道题的全部。

4090 的显存带宽是 **1008 GB/s**。输入是 2^26 个 float = **256 MiB**,
也就是说:

```
把 x 从头到尾读一遍 = 268 MB / 1008 GB/s ≈ 266 µs
```

那这些数据要"算"多久呢?6700 万次加法 + 1.3 亿次比较,总共约 2 亿次浮点运算。
4090 的 FP32 算力是 82 TFLOPS,2 亿次运算需要 **2.4 µs**。

**差 100 倍。** 这题没有任何"算得快"的空间 —— 唯一的成本是搬运。
所以你唯一要回答的问题是:

> 你把 x 读了几遍?

| 你读了几遍 | 实测用时 | 占"读一遍"的比例 |
|---|---|---|
| 3 遍(每个统计量各扫一遍数组) | 0.855 ms | 31% |
| 2 遍 | 0.572 ms | 47% |
| 1 遍(三个累加器同时更新) | 0.289 ms | **92%** |

这就是本题的评分刻度,也是它和 04 题的区别:04 题问的是"你怎么把一次求和
拆开并行",这题问的是"你要拆几次"。

注意读数:**1 遍 = 92% 而不是 100%**。差的这 8% 里,一半是收尾 kernel 的
固定开销、一半是 DRAM 跑不满标称值 —— 也就是说 92% 已经贴着物理上限了,
没有"再优化 8%"这回事。

这不是人为设计的场景。真实代码里"再加一个统计量就多读一遍数据"是极常见的
性能事故 —— 先是 mean 一个 kernel,后来要 std 再加一个,要 min/max 再加一个,
数据早就被读烂了。**能放进同一个循环里的东西,就该放进同一个循环。**

## 解法思路(不要直接抄,先想清楚为什么)

### 第一步:三个累加器,一个循环

最核心的一步,也是最简单的一步 —— 把三个统计量塞进同一个 grid-stride 循环:

```cuda
float a  = 0.f;                    // 和
float lo = __int_as_float(0x7f800000);    // +inf
float hi = -__int_as_float(0x7f800000);   // -inf
for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n;
     i += blockDim.x * gridDim.x) {
    float v = x[i];                // 只读这一次
    a  += v;
    lo  = fminf(lo, v);
    hi  = fmaxf(hi, v);
}
```

同一份数据被三个操作使用,但**只从显存来了一次** —— 它就留在寄存器里。
这一步做完,实测时间就从 0.855 ms 掉到 0.289 ms(31% → 92%)。

跨步写法(`i += blockDim.x * gridDim.x`)而不是让每个线程读一段连续区间,
是为了让同一个 warp 的 32 个 lane 每次读的地址相邻 —— 合并访存,见 01 和 08 题。

> **一个真实的发现,值得记下来。** 本题的基线之所以写成**三个 kernel**,
> 而不是一个 kernel 里的三个连续循环,是因为后者 nvcc 会**直接替你融合**:
> 三个循环读的是同一个 `__restrict__` 指针,中间没有任何东西挡得住它,
> 编译完就自动变成了本题的答案(实测融合版跑出 88% 峰值)。
>
> 两层含义:
> ① 融合这件事**该你自己显式做** —— 别赌优化器。它只在能证明无别名时才敢动,
> 一旦循环之间夹了对全局内存的读写(比如你要把 partial 写下去再读回来),
> 它就做不到了;
> ② 如果你写了三遍却发现快慢没差别,先怀疑"编译器帮我做了",去翻翻 PTX,
> 别急着怀疑硬件。

### 第二步:块内归约

每个线程手里有三个部分结果,要把一个块内 256 个线程的合起来。
共享内存树形归约是最好懂的做法,而且三个量可以**共用同一轮同步**:

```cuda
__shared__ float ss[BLOCK], sn[BLOCK], sx[BLOCK];
ss[tid] = a; sn[tid] = lo; sx[tid] = hi;
__syncthreads();
for (int k = blockDim.x / 2; k > 0; k >>= 1) {
    if (tid < k) {
        ss[tid] += ss[tid + k];
        sn[tid] = fminf(sn[tid], sn[tid + k]);
        sx[tid] = fmaxf(sx[tid], sx[tid + k]);
    }
    __syncthreads();   // ← 这个不能省
}
```

`if (tid < k)` 里的**每个** `__syncthreads()` 都必须被整个块执行到 ——
所以同步要写在 `if` 外面(上面就是这么写的)。写在里面 = 未定义行为。

### 第三步:块间归约 —— 两条路,选一条

一个块只能处理一部分数据,所以还要把几百上千个块的块内结果合起来。

**路线 A:partial 数组 + 第二级 kernel(推荐)**

每个块把自己的 `(sum, min, max)` 写进 `ctx.partial[blockIdx.x * 3 + {0,1,2}]`,
然后 launcher 再启动**一个单块** kernel,把这 `grid` 个三元组归约成三个标量。

- 优点:每个输出是**覆盖写**,不用管什么初值、也不用清零;
- 优点:块数再多也不会串行化;
- 代价:多一次 kernel 启动(几 µs,相对 266 µs 可以忽略)。

**但第二级 kernel 本身必须是并行的** —— 这一条值得单独强调,因为它能把
你融合赚到的全部赔回去:如果那个 kernel 只用一个线程去扫 partial,8192 块时
它要花 **0.47 ms,比主 kernel 的 0.29 ms 还贵**(总时间 0.762 ms,只比三趟的
基线快 12%)。而同一个串行收尾,块数封在 1024 时只花 35 µs。
串行收尾的成本是 O(块数),主 kernel 是 O(n) —— **块数越多,这个坑越深。**
老老实实让一个块(几百个线程)分头去扫,就什么事都没有。

spec 里给出的 `ctx.partial` 就是为这条路准备的,长度是 `ctx.max_blocks * 3`。

**路线 B:全局原子操作**

`atomicAdd` 对 `float` 是有的,直接加到 `ctx.sum` 上就行。
但是 —— **`atomicMin` / `atomicMax` 只有整数版本,CUDA 没有 float 版**。
想在 float 上做,得自己写 `atomicCAS` 循环,而且还有个坑:
float 的位模式当成**有符号整数**比,在负数区间是**反的**
(因为符号位在最高位:-0.5 的位模式是 0xBF000000,比 -0.25 的 0xBE800000
"更大",但数值上更小)。所以标准写法要先把负数区间翻转过来。

还有一件事:走原子路线的话,三个输出都是**累加型**的,框架在每次执行前会把
out 缓冲填成毒值(NaN)—— 不清零的话结果是 NaN。这就要在 launcher 里
`cudaMemsetAsync`,而 min 的单位元是 +inf,用 memset 是清不出来的
(它能按字节填,填不出 0x7F800000)。

**两条路都对,但路线 A 在这题上明显更省心。** 这正是"浮点没有原子 min/max"
这条事实带来的后果 —— 它不是一道八股题,它真的会改变你选哪条路。

## 陷阱提醒

- **`min` 的单位元是 `+inf`,不是 `0`。** 这题的数据里有负数,把 min 的初值
  写成 `0.f` 会把结果污染成 0(而且 sum 看起来完全正常,只有 min 错)。
  `max` 的单位元是 `-inf`,同理。
- **第二级 kernel 别只用一个线程。** 这是本题最贵的坑(实测 0.47 ms,
  比主 kernel 还贵),详见上面「路线 A」。
- **空块的 partial 也必须写。** 只要你的 grid 开得比 `ceil(n / 块大小)` 还大
  (比如图省事固定开满 `max_blocks` 块),就会有块一个元素都领不到。它们仍然要
  写下自己的三元组 —— `sum = 0`、`min = +inf`、`max = -inf`(三个单位元**不
  一样**)。如果那个块根本不写 `partial[bx*3+1]`,第二级 kernel 读到的就是这块
  内存里的旧值(框架把它清成了 0),min 又被污染成 0。这种 bug 只在"块比数据多"
  的用例上暴露,大用例上看起来一切正常。
- **漏 `__syncthreads()`。** 块内归约是"一个线程写、另一个线程读",中间必须
  同步。漏掉的后果是"有时对有时错" —— 跑一次看不出来。框架会把每个用例
  重复跑 3 次,racecheck 也能精确指出哪两个访问构成了 hazard。
- **别拿 float 的位模式直接当整数比大小**(如果你走原子路线的话)。上面解释过
  为什么负数区间是反的。
- **边界:`ragged` 用例的 `n = 67108859`,不是 2 的幂,也不被 4 整除。**
  grid-stride 的循环条件 `i < n` 天然处理了尾巴;但如果你想用 `float4`
  一次搬 4 个元素,就得单独处理末尾那 3 个 —— 而这题上 `float4` 一分钱都
  不值(见评分说明),别为它冒这个险。
- **不要用 `sum` 去"顺便"验证 min/max。** 漏掉一个块的 min 时,sum 的偏差
  小到测不出来,而 min 会差 O(1)。三个输出要各自检查。

## 评分说明

这题**只按正确性决定通过与否**(通过 = 三个输出都在容差内);
性能另给 S/A/B 评级,**不影响是否通过**。

评级用「有效带宽占峰值的百分比」,刻度是绝对的、有物理含义的:

> 框架算的字节数是「输入 + 输出各一遍」= 256 MiB + 12 字节。
> 所以 **100% 就等价于「你把 x 恰好读了一遍」**。

| 评级 | 门槛 | 含义 |
|---|---|---|
| B | 40% | 至少把三遍并成了两遍(基线只有 31%) |
| A | 70% | 读一遍了,但收尾还没并行起来 |
| S | 85% | 贴着"读一遍"这条物理上限 |

下面是实测的梯子(2026-09-29,4090,框架自动清 L2,big 用例 2^26;
这些都是真跑出来的数字,不是估算):

| 实现 | 读了几遍 | 用时 | 有效带宽 | 占峰值 | 评级 |
|---|---|---|---|---|---|
| 基线:三趟遍历 | 3 | 0.855 ms | 314 GB/s | 31% | C |
| 一趟 + **串行**收尾(8192 块) | 1 | 0.762 ms | 352 GB/s | 35% | C |
| 两趟(sum+min 一趟、max 一趟) | 2 | 0.572 ms | 469 GB/s | 47% | B |
| 一趟 + 1024 块 + 串行收尾 | 1 | 0.324 ms | 830 GB/s | 82% | A |
| 参考解(一趟 + 并行收尾) | 1 | 0.289 ms | 930 GB/s | 92% | S |
| 参考解 + float4 | 1 | 0.289 ms | 930 GB/s | 92% | S |

三个从这张表里读出来的事实:

1. **31% → 47% → 92% 之间没有斜坡**,因为"读几遍"是个整数。所以 A 这一档
   是个窄带 —— 它不区分实现风格,只回答"你把读一遍这条路走完了没有"。
   参考解(也在 `leet solution 15-array-stats` 里)是 92%。
2. **第二行是个陷阱**:它读的遍数是对的(一趟),但收尾串行,把融合赚到的
   时间又还了回去 —— 只比基线快 12%。**读一遍 ≠ 拿到分。**
3. **float4 一点用都没有**(0.289 ms 对 0.289 ms,逐位相同)。它减少的是指令数,
   而瓶颈是 DRAM 流量 —— 这正是 01 题那句"剩下的空间不在算法,在硬件"的又一次
   复现。块数也一样不敏感(128 块 = 90%)。

## 思考题

1. **如果 x 只有 4 MiB(100 万个 float),"读三遍"还会慢三倍吗?**
   提示:4090 的 L2 是 72 MB。想清楚"多遍历一遍"的成本到底由什么决定 ——
   是"读了几遍",还是"这几遍之间隔了多远"?这题的两个可评级用例为什么
   必须做得比 L2 大?

2. **把 sum 换成"平方和"(Σx²),误差分析有什么不同?**
   现在 sum 的真值约 ±4000(6700 万个 [-1,1) 的数正负相消,实测这组数据是 3500),
   而平方和约 2.2e7(全是正数,不相消)。同样是 f32 累加,哪一个更危险?
   为什么参考解要用 double 累加?(提示:相对误差和绝对误差不是一回事;
   再想想 f32 的 24 位有效数字在 2^24 = 1670 万附近会发生什么。)

3. **块间归约的两条路(partial + 第二级 kernel / 全局原子),在块数从
   128 涨到 100 万时各自会怎么变?** 提示:第二级 kernel 的代价是
   "块数 × 3 个 float 的读写 + 一次启动";原子操作的代价是"块数 × 3 次
   对同一个地址的操作",而 L2 对**同一个地址**的原子操作是串行的
   (07 题讲过这件事)。哪个先撑不住?
