# 矩阵乘:把内层循环换过来

这是一道**优化题**。给你一份**完全正确的**矩阵乘代码,把它改快。

和别的题不同:这里没有 bug 要找。下面这段代码算出来的结果一个比特都不差,
问题只在于它把时间浪费在了**访存**上。

```cpp
for (int i = 0; i < n; ++i)
    for (int j = 0; j < n; ++j) {
        float s = 0.0f;
        for (int k = 0; k < n; ++k)
            s += ctx.A[i * n + k] * ctx.B[k * n + j];   // ← 问题在这一行
        ctx.C[i * n + j] = s;
    }
```

## 为什么这道题重要

这是 CPU 性能优化里最经典、也最容易被忽略的一课:**算法的渐进复杂度没错,
常数因子却差了二十倍**。

初学者对性能的直觉几乎都建立在"做了多少次运算"上。但现代 CPU 上,一次
L1 命中大约 4 个周期,一次主存访问要 200~300 个周期 —— 差了两个数量级。
所以"做了多少次**访存**"往往比"做了多少次运算"更能决定程序快慢。

而代码里最费访存的地方,常常就是你最不会去怀疑的那几行循环。

## 慢在哪:一次访存只用得上 4 个字节

盯着最内层那个 `k` 循环,看它怎么访问 `A` 和 `B`:

| 访问 | 地址随 k 的变化 | 模式 |
|---|---|---|
| `A[i*n + k]` | 每次 +1 个 float(+4 字节) | **连续** |
| `B[k*n + j]` | 每次 +n 个 float(+1536 字节) | **跨步** |

一条 cache line 是 64 字节,能装 16 个 float。所以 `A` 那边的邻接访问是
"一次搬运,十六个元素都用到";而 `B` 那边每读 4 个字节就换一条新的 cache line,
剩下 60 个字节原封不动地被丢掉了。

**算一个乘加,搬一条 cache line,利用率 1/16。**

更要命的是硬件预取器:它能认出"顺序访问"并提前把数据拉进来,
但对 `B` 这种跨度 1536 字节的跳跃完全无能为力 —— 每一跳都得实打实地等。

出路在"换个角度复用数据":矩阵乘每个元素平均要被用 n 次(=384 次),
理论上访存完全应该被缓存吸收。所以问题不是"数据太多",而是**访问顺序
让缓存完全用不上**。

## 解法思路

先别看代码,想一个问题:

> `A[i*n+k]` 和 `B[k*n+j]` 里,哪个下标在内层循环里是"动"的?
> 如果让**两个都动**、而且都是连续地动,会发生什么?

你会发现修复只需要动**一行** —— 把某两层循环换个位置。换完之后:

- `A` 的那个值在整个内层循环里是常数 → 提到循环外,只读一次
- `B` 顺着 `j` 连续走 → 一条 cache line 装 16 个,全部用上
- `C` 顺着 `j` 连续读写 → 同样顺序

三条访存流全部变成顺序的,**而且一行额外代码都没加**。

一个容易走的弯路:把 `B` 预先转置一份,让 `B[k*n+j]` 也变成连续访问。
这确实能解决跨步问题,但代价是多了一次 n² 的读写(而且转置本身还得处理
跨步访问)。既然交换循环次序是**零额外访存**的,就没有理由绕这一圈。

## 陷阱

- **不要急着上 SIMD / 多线程 / shared memory**。这道题的瓶颈从头到尾都是
  访存模式,不是指令吞吐 —— 在跨步访问的前提下,向量化只会让"每搬一条
  cache line 用 4 个字节"变成"用 16 个字节",杯水车薪。先把访问顺序理顺。
- **别把 `C` 忘了**。交换循环次序之后 `C[i*n+j]` 会被反复累加,
  所以要先清零 —— 原来的写法是直接赋值,不需要这一步。
- **非 2 的幂的规模**(用例 `odd`,n=257)不会因为你换了循环次序就出错,
  但它会检验你有没有在别处不小心写死了 16、8 之类的常数。
- **编译选项是框架钉死的**(`-O3 -march=native`,刻意不带 `-ffast-math`)。
  改选项不算数,也没必要 —— 编译器不会帮你交换这两层循环,原因见下。

## 为什么编译器不自动做这件事

这是本题最值得记住的一点。

编译器要重排循环,必须先证明"重排不改变结果"。对整数运算它可以尝试,
但 `s += a*b` 是**浮点**累加 —— 而浮点加法不满足结合律
(`(a+b)+c` 未必等于 `a+(b+c)`)。C++ 标准不允许编译器擅自改变浮点运算的
结合顺序,所以它只能老老实实按你写的次序算。

**要放开这个限制,得显式加 `-ffast-math`** —— 那等于告诉编译器
"浮点误差我不管"。本题刻意不开:一是真实项目里开它的风险由你承担,
二是开了之后编译器会把一批本该由你想清楚的优化直接做掉,这课就白上了。

顺带一提:即使开了 `-ffast-math`,交换循环次序这种**结构性**的改动
编译器也基本不做 —— 它的循环变换能力远没有传说中那么强。

## 评分

指标是**相对基线的加速比**,门槛:

| 评级 | 加速比 |
|---|---|
| B | ≥ 3.0x |
| A | ≥ 9.0x |
| S | ≥ 15.0x |

实测:基线(n=384)79.5ms,参考解 4.0ms,**约 20x** —— 所以 S 是拿得到的,
门槛没有再压低。

**这道题必须达到 B 级才算通过。** 别的题只看正确性,性能只评级;
但这里基线本身就是正确代码,如果只看正确性,你把原代码原样交回来就算通过了,
那这道题也就没有意义了。(参考解可以用 `leet solution cpp01` 看,但先自己试。)

## 思考题

1. 交换循环次序之后,`B` 是顺序读的、`C` 是顺序读写的 —— 但 `C` 的每一行
   在内层循环里被反复读写了 n 次。如果 n 大到 `C` 的一行都放不进 L1,
   会发生什么?这时候该往哪个方向优化?(提示:`n=384` 时 `C` 的一行是 1536 字节)

2. 实测下来这道题的加速比随 n 变化**并不单调**:n=192 时约 12x,n=256 时约 23x,
   n=320 时又掉到 14x。想一想为什么。(提示:`n*4` 字节和 L2 的大小、相联度
   之间的关系;也想想 2 的幂次会不会让某些行"撞"进同一个 cache set)

3. 如果把这题的数据类型从 `float` 换成 `double`,加速比会变大还是变小?
   先用你现在的理解猜一个方向,再实际改一下测一测 —— 差异会告诉你,
   这道题的瓶颈到底是什么,以及为什么。

4. 这道题是单线程的。如果允许开 4 个线程,你觉得加速比会变成多少?
   (可以去 `leet` 之外自己测一下 OpenMP 版的 `i` 循环并行。)
   想清楚之后再看下一个问题:**如果多线程只需要 3 行代码就能拿到差不多的
   收益,那"理解 cache line"这件事还有多重要?** —— 提示:多线程也是有成本的,
   而且它和访存局部性是**可以叠加**的,不是二选一。
