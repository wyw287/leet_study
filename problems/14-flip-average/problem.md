# 八向翻转平均

> 难度 ●●○○○ · 标签 `3d` `memory-bound` `l2` `reuse-distance` `boundary` · 考点:复用距离、L2 容量、轨道、三维索引

## 题目

给你一个 `d × h × w` 的三维张量 `x`(row-major 存放在显存里,线性下标是
`(b*h + i)*w + j`)。对每一个位置,把它在「三个轴各自翻不翻转」这 8 种组合下
的对应位置求平均,写进同样形状的 `out`:

```
out[b][i][j] = (1/8) * ( x[b  ][i  ][j  ] + x[b  ][i  ][w-1-j]
                       + x[b  ][h-1-i][j  ] + x[b  ][h-1-i][w-1-j]
                       + x[d-1-b][i  ][j  ] + x[d-1-b][i  ][w-1-j]
                       + x[d-1-b][h-1-i][j  ] + x[d-1-b][h-1-i][w-1-j] )
```

三个缓冲/参数的搬运都由框架负责,你只写 `flip_avg`(kernel)和
`flip_avg_launch`(启动配置)。用例里有一个 2×8192×4096 的大张量、
一个 2×8191×4093 的质数尺寸张量(两个维度是奇数),和一个小到不参与评级的
65×33×19。

> `d=2` 不是笔误:张量的**形状**是这道题的一部分,原因见下面「瓶颈在哪」。

## 为什么这道题重要

这是**数据增强平均**(TTA)的标准形状:推理时把输入翻转出几个版本、各跑一遍、
把结果平均回去。二维图像上常见的是 4 向(左右、上下、中心对称),三维体数据
(医疗影像那一类)是 8 向。它的一个副产品是**对称化**:输出一定满足 8 重对称,
一个位置和它的 7 个镜像在 `out` 里值完全相同。

但更值得学的是它的性能结构。前面十几道题讲过的坑,这道题**一个都没有**:

- **合并访问是满分的**(01、03、08 的考点)。同一个 warp 的 32 个 lane 每次读的
  都是同一行里连续的 32 个 float。
- **sector 一个字节都没浪费**(08、13 的考点)。8 个 tap 每一个都是整行连续取数。
- **算术强度不是瓶颈**(06、09 的考点)。每个输出 8 次加法 / 8 字节访存
  = 1 FLOP/Byte,比 4090 的平衡点(约 82 FLOP/Byte)低两个数量级。
- **没有归约、没有扫描、没有原子、没有共享内存、不需要 shuffle。**

它考的是另一件事:**这些读发生在什么时候。** 这是缓存能不能救你的唯一判据,
而且它和数据规模绑在一起 —— 同一份代码,张量小的时候"没问题",大了就慢 2 倍多。
把这件事想明白,你才算真的会用 GPU 的存储层次。

## 瓶颈在哪:先把账算清楚

### 那堵墙

```
主力用例:2 × 8192 × 4096 × 4B = 268 MiB 读 + 268 MiB 写 = 536 MB 访存
4090 峰值带宽:1008 GB/s
物理下限:536 MB ÷ 1008 GB/s ≈ 532 µs
```

这 536MB 是**必要的**:输入必须读一遍,输出必须写一遍,一个字节都省不掉。
所以这道题的天花板不是"能省多少流量",而是"**你能不能让实际流量等于 536MB**"。

### 基线慢在哪:8 次读,落在 4 个不同的时刻

基线(`problems/14-flip-average/baseline.cu`)是「一个线程算一个输出,把 8 个位置
读一遍」。8 个 tap 分成四组,分布在四行上:

```
(b, i)   (b, mi)   (mb, i)   (mb, mi)        mi = h-1-i,mb = d-1-b
```

每组读两个位置:第 `j` 个和它的左右镜像 `mj`。同一组里的这两个位置在同一行内,
最多隔 `w = 4096` 个元素 = 16KB —— 缓存顺手就接住了,**这一层不用算账**。

要算的是**组与组之间**。一个元素被读到 8 次,这 8 次不是同时发生的,
而是分散在四个时刻上:

```
(b, i) ↔ (b,  mi):最多 h*w = 33.5M 个元素
(b, i) ↔ (mb, i) :恒等于 h*w = 33.5M 个元素
(mb,i) ↔ (mb, mi):最多 h*w = 33.5M 个元素
```

33.5M 个元素是什么概念?kernel 每处理一个输出平均要搬十来个字节,所以
**"隔了多少个元素"基本就等于"隔了多少流量"**:33.5M 个元素 ≈ 400MB 以上。

**L2 只有 72MB。** 于是判据变成:

| 两次访问之间隔了 | 结果 |
|---|---|
| 几万个元素(16KB~几 MB) | 还在 L2 里,重读**免费** |
| 约 4M 个元素以内(≈ 72MB 流量) | 勉强接得住 |
| 33.5M 个元素(≈ 400MB 流量) | **接不住,再走一趟显存** |

基线的账因此是:

| | 每元素次数 | 评价 |
|---|---|---|
| 写 | 1 | 满分,没有可省的 |
| 读 | 8,塌缩成 4 个时刻,**其中 3 个时刻要重新走显存** | **账在这里** |

顺带说明**形状为什么是 2×8192×4096**:它让上面的"33.5M 个元素"这个距离
稳稳超过 L2 的窗口。如果把同样的张量摊成 2048×256×128(= 同样是 268MB),
切片只有 128KB,`(b,i) ↔ (b,mi)` 这一组就落回"免费"那一档 —— 8 次读里
真正落空的只剩 1 次,基线能跑到 68%,这道题的梯度就没了。
**张量比 L2 大是必要条件,不是充分条件;决定一切的是复用距离。**

### 判据是"复用距离",不是"访问模式好不好看"

一个元素两次被使用之间,隔了多少字节的流量 —— 这个量叫**复用距离**。它的量纲
是字节,所以要和**缓存的容量**比,而不是和"访问模式像不像样"比:

- 复用距离 ≪ L2(72MB):重读基本免费。**相邻窗口重叠 511 个元素的滑动窗口
  (13 题)就是这样** —— 每个元素被读 512 次,但显存上只走一次。
- 复用距离 ≫ L2:重读就是**再走一趟显存**,缓存帮不上忙。这道题的 8 个 tap
  就是这个情形。

同一个元素被读 8 次这件事本身**不是问题**(13 题的元素被读 512 次都不怕),
问题是这 8 次之间隔了多远。

## 解法思路

盯着一个位置 `p = (b,i,j)`,它的 8 个 tap 是

```
{ (b|mb, i|mi, j|mj) }
```

现在看它的镜像位置 `(b, i, mj)` 的 8 个 tap —— 是不是**同一组**?再看
`(mb,i,j)`、`(mb,mi,mj)`…… 8 个位置,每一个的 tap 集合都等于这同一组。
原因很直接:「取镜像」在每个轴上是**独立**的动作,对三个轴各取一次镜像,
出来的就是同一个集合。

由此有两个结论,一个关于算,一个关于读:

1. **这 8 个位置的值全都相等。** 同一个集合、同一个平均值。输出是 8 重对称的
   —— 一个轨道只需要算一次。
2. **既然 8 个线程算的是同一个值、读的是同一组数据,那就让一个线程把这 8 个
   读进来**(每个只读一次),算一次,写 8 个位置。

读的次数从 8 降到 1,写的次数一次没多。访存模式一点没变:8 个读、8 个写,
每一个仍然是 warp 内 32 个 lane 连续的 128 字节。**变的只是「谁在什么时候读」。**

线程总数随之降到 1/8:让每个线程只负责「基本域」里的一个位置,它的 8 个镜像
由它自己一起写掉。基本域就是每个轴上"靠前的那一半" —— 取
`b < (d+1)/2`、`i < (h+1)/2`、`j < (w+1)/2`。**注意是向上取整**,理由见下。

这题**不需要**共享内存,也不需要 shuffle。要的东西自始至终都在寄存器里 ——
只要那个线程愿意一次多拿几个。

## 陷阱提醒

- **奇数维度:中间那一层/行/列是它自己的镜像。** `d=1021` 时 `b=510` 满足
  `d-1-b = 510`,那个位置的 8 项里有重复项。参考解的语义是**不做任何特判**:
  重复项取到的是同一个值,平均下来还是它自己。你的快版本也要保持这个语义。

- **基本域要向上取整。** `min(x, n-1-x)` 的值域是 `[0, (n-1)/2]`,大小是
  `(n+1)/2`(整数除法)。奇数 `n` 时正中间那个也在基本域里 —— 它代表的轨道
  只有 1 个或者 2 个元素,漏掉它就漏写了整层/整行。

- **重复写同一个地址:同一个线程写两次是安全的,两个线程写同一个地址就是竞态。**
  让 `mj == j` 的情形自然发生,重复的写会退化成"写两次同一个地址、同一个值",
  而写它的是同一个线程,既不是竞态也不会写错。但如果你的基本域取歪了(比如
  自己手写特判、或者把 `(w+1)/2` 写成了 `w/2`),就会有**两个不同的线程**去写
  同一个位置 —— racecheck 会报你,而且这种 bug 常常"有时对有时错"。
  校验会重复跑 3 遍,就是为了抓它。

- **别去特判边界。** 让 `mi == i`、`mb == b` 自然发生。手写特判是 bug 的来源:
  少写一次看不出来,漏写一个位置要等到对拍才暴露。

- **当心 `w` 不是 32 的倍数。** 用例里有 `w=97` 和 `w=19` 这种:`w=19` 时一个
  warp 里有 13 个 lane 是空的。让循环条件/边界判断自己兜住,别手动凑整。

## 评分说明

正确性决定通过与否,**性能只评级**(S/A/B/C),不卡关。

评级用「**有效带宽占峰值百分比**」,而不是加速比 —— 因为这道题的算术强度是
1 FLOP/Byte,天花板 100% 由带宽决定,加速比只是这个百分比的另一种写法。

| 评级 | 门槛 | 含义 |
|---|---|---|
| B | 54% | 已经把 8 次读的**多个时刻塌缩掉了一部分**(比如只让最外层成对),但还没做到"每元素只读一次" |
| A | 78% | 轨道切对了,但访存或启动配置还有浪费 |
| S | 88% | 贴到带宽墙上了 |

实测(4090,框架每次计时前清空 L2,`repeat=50` 取中位数;两个用例成绩一致,
下面是 `big` 的数字):

| 写法 | 用时 | 有效带宽 | 占峰值 | 评级 |
|---|---|---|---|---|
| 基线:一输出一线程,8 个位置各读一遍 | 1.304 ms | 412 GB/s | 41% | — |
| 只把最外层成对(8 次读塌缩成 2 个时刻) | 0.788 ms | 681 GB/s | 68% | B |
| 参考解:一线程管一个轨道(读 8 写 8) | 0.546 ms | 984 GB/s | **98%** | **S** |

也就是说 **S 是拿得到的**:参考解(`optimal.cu`)就在这个位置。

注意这张梯子的形状:**68% 到 98% 之间没有斜坡。** 要么一个元素被读 4 遍、
要么被读 1 遍,中间不存在"读 2 遍"的写法 —— 因为行内那一对 `j/mj` 天然落在
同一个时刻里,你想省也省不掉它。所以 A 这一档偏窄是这道题的物理性质,
不是门槛没设好。

## 思考题

1. **把"轨道"切小一点会怎样?** 比如只让最外层成对:一个线程管 `(b,i,j)` 和
   `(mb,i,j)` 两个位置,行内和层内的镜像还是各读各的。读的次数从 8 降到 4,
   8 次读的 4 个时刻塌缩成 2 个 —— **实测 68%,B**。为什么它到不了 S?
   (提示:剩下的那个时刻是 `(b,i) ↔ (b,mi)`,距离最大 33.5M 个元素,
   照样超出 L2 的窗口。另外想一想:为什么"一个元素被读几遍"不是关键,
   "落在几个时刻上"才是?)

2. **同一个操作,换成 4096×4096 的二维图做 4 向平均,还有优化空间吗?**
   64MiB 装得进 72MB 的 L2。先预测基线和参考解会差多少,再把用例改小实测一遍
   (题面的用例都是 268MB 这个量级,故意不给你留"装得进 L2"的样本)。
   你会看到一个反直觉的结果:**张量装得进 L2 时,这题的重读问题会自己消失,
   同一份代码不用改就是满分。** 顺便想一想:rating 为什么必须对每个可评级
   用例都成立?(提示:如果某个用例能装进 L2,写入还没落盘 kernel 就结束了,
   测出来的"带宽"会虚高到 100% 以上 —— 而评级是取所有用例里的最好成绩。)

3. **同样 268MB,把形状从 2×8192×4096 换成 2048×256×128,基线的成绩会变好
   还是变差?** 先算一算"切片"(`h*w`)有多大,再判断那三组远距离 tap 会落到
   上面表格的哪一档,然后实测验证。**实测是 68% —— 比现在的 41% 好得多。**
   结论有点反直觉:**"张量比 L2 大"是必要条件,不是充分条件。** 决定一切的是
   复用距离,而形状可以把它藏起来(这一版题最初就栽在这上面:基线的梯度
   一度只有 1.45x)。顺便想一想:如果 L2 有 1GB,这道题还需要"轨道"这个
   技巧吗?
