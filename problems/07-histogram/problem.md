# 07 · 直方图统计

## 题目描述

给定 `n` 个整数(`ctx.data`,每个都在 `0..99` 之间),统计每个值出现了多少次:

```
bins[v] = data 里值等于 v 的元素个数        v = 0 .. nbins-1
```

输出写进 `ctx.bins`,长度 `ctx.nbins = 128`。

`n` 最大约 3300 万,输入里的值只落在 `0..99` —— 也就是说
**100..127 这 28 个桶一个数都不会落进去,它们必须精确地是 0**。

你要实现两个东西:

| 名字 | 干什么 |
|---|---|
| `__global__ void histogram(...)` | 干活 |
| `void histogram_launch(LaunchCtx& ctx)` | 决定启动配置、清 `bins` |

数据已经在显存里了,`bins` 也已经在显存里了。分配、搬运、计时、对拍、越界检测
都由框架完成。

## 为什么这道题重要

前面几道题(01 向量加法、02 SAXPY、03 转置)都是**「读得够不够快」**的问题 ——
它们的朴素实现本来就贴着带宽天花板,优化空间在硬件上,不在代码里。

这道题不一样,而且不一样的地方很值得记住:

> **瓶颈可以完全不在显存,而在「往哪儿写」这件事上。**

数一下这道题的账:

* 要读的数据是 32M 个 int = **128MB**。4090 的峰值带宽 1008 GB/s,
  读一遍的时间下限是 **约 130µs**。
* 朴素写法 `atomicAdd(&bins[data[i]], 1)` 里,写地址是**由数据决定**的。
  同一 warp 的 32 个线程各读各的 `v`,写地址是散的 —— 这叫**散射写**,
  没有任何办法合并。
* 更要命的是:**同一个地址的原子操作在 L2 里是串行的**。数据落在 100 个桶里,
  3300 万个元素平均每个桶要被加 **33 万次**。就算这些桶分属不同的 L2 slice、
  彼此完全并行,每个桶那条 33 万次长的串行链也躲不掉。

结果是:**实测基线 6.2 ms,有效带宽只有 22 GB/s —— 峰值的 2%。**
慢了 40 多倍,而且慢的原因和带宽毫无关系:数据一百多微秒就读完了,是加不完。

这就是本题要教的东西:

> **冲突是稀缺资源,把它搬到便宜的地方去。**

这个思路后面会反复出现(锁、原子、伪共享、数据库的行锁……),
GPU 上它的名字叫**私有化(privatization)**,而"便宜的地方"就是共享内存。

## 解法思路

**别让 3300 万个元素去抢 100 个全局地址。让每个块先在片上攒一份自己的账,
最后只把这 128 个数并到全局去。**

三步:

1. **每个块在自己的共享内存里放一份直方图**,块内线程协作清零:

   ```cuda
   extern __shared__ int sh[];
   for (int i = threadIdx.x; i < nbins; i += blockDim.x) sh[i] = 0;
   __syncthreads();
   ```

2. **块内累加**,循环用 grid-stride:

   ```cuda
   const int stride = gridDim.x * blockDim.x;
   for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride) {
       int v = data[i];
       if (v >= 0 && v < nbins) atomicAdd(&sh[v], 1);
   }
   __syncthreads();
   ```

3. **把块内的账并到全局**:

   ```cuda
   for (int i = threadIdx.x; i < nbins; i += blockDim.x)
       if (sh[i]) atomicAdd(&bins[i], sh[i]);
   ```

原子加的总次数没变,但**打在哪儿**变了:从「3300 万次打在 100 个全局地址上」
变成「3300 万次打在每块一份的共享内存上 + (块数 × 128) 次打在全局上」。

为什么共享内存便宜?两个原因,都要记住:

* **物理距离。** 共享内存是 SM 内部的 SRAM,原子加在片上完成,延迟二三十个
  cycle;全局原子要跑到 L2 去,几百个 cycle。
* **128 份,而不是 1 份。** 4090 有 128 个 SM,每个块的共享直方图是
  **互相独立**的 —— 冲突从「全卡排一条队」变成「每个 SM 排自己的队」。

**但这只解决了一半。** 实测的块数曲线是这样的(4090,big 用例):

| 块数 | 耗时 | 有效带宽 | 占峰值 |
|---|---|---|---|
| 32 | 0.335 ms | 401 GB/s | 40% |
| 64 | 0.188 ms | 712 GB/s | 71% |
| **128**(= SM 的个数) | 0.148 ms | 904 GB/s | 90% |
| 4096 | 0.146 ms | 917 GB/s | 91% |

冲突被搬走之后,瓶颈**立刻**换成了「并行度有没有铺满整张卡」。
128 是这个曲线的拐点 —— 低于它就有 SM 在闲着,再往上加只值 1%。
「想到了私有化」和「私有化 + 把块数给够」是两件事,这是本题的第二课。

## 陷阱提醒

1. **`bins` 必须先清零 —— 而且不能在 kernel 里清。**
   框架在每次执行前把 `bins` 填成毒值 `0x5EED5EED`(整数用这个值),
   目的是精确识别"kernel 根本没写输出"。累加型输出不清零的话,
   结果是**毒值加上计数**,而且稳定地错。

   清零要放在 `launcher` 里(`cudaMemsetAsync`,512 字节,约 1µs)。
   **不要**在 kernel 里写 `if (threadIdx.x < nbins) bins[threadIdx.x] = 0;`
   加 `__syncthreads();` —— `__syncthreads()` 只保证**一个块内**的顺序,
   别的块可能早就加完了。跨块顺序需要 grid 级同步,那是另一套东西。

2. **两处 `__syncthreads()` 一处都不能少。**
   少了清零后那处,先跑下去的线程会往还没清完的共享直方图里加数;
   少了累加后那处,有的线程会把还只加了一半的账并到全局去。
   这种错**有时对有时错**,所以框架把每个用例重复跑 3 次(`verify.repeat`),
   racecheck 也会盯着它。

3. **`100..127` 号桶是本题的照妖镜。**
   数据只落在 0..99,所以这 28 个桶的正确值一定是 0。忘了清零、
   或者归并时算进了不属于自己的数据,都会在这里露馅。

4. **边界。** `ragged` 用例的 `n = 16777259` 是质数级、不整除 4。
   用 grid-stride 循环就不用单独处理"最后一批线程越界";
   但如果想上 `int4`,尾巴那 `n % 4` 个元素必须单独用标量补一遍。

5. **共享内存的 bank 冲突。** 共享内存 32 个 bank,桶 `v` 落在 bank `v % 32`
   上。随机数据下平均每个 bank 会撞上好几个线程,同 bank 的原子加要排队。
   想进一步压,可以给每个线程分一份**子直方图**(`threadIdx.x % K` 选),
   但步长必须写成 `nbins + 1` 而不是 `nbins` —— 128 是 32 的倍数,
   用 128 做步长的话所有子直方图的第 `v` 个桶还是落在同一个 bank 上,等于白分。
   (本题上这一条的收益在噪声里;桶更少、冲突更极端时它才是救命的。)

## 评分说明

* **正确性决定通过与否。** 计数是整数,框架要求**精确相等**,差一个就是错。
* **性能只评级,不卡关**,分 B / A / S 三档。
* 本题按**有效带宽占峰值(1008 GB/s)的百分比**评级 —— 因为"够不够快"的
  正确答案就是"读到接近峰值带宽"。这题是**读多写少**(读 128MB、写 512 字节),
  所以百分比衡量的基本就是"你把读取这条路用到了几成"。

完整实测(4090,框架自动清 L2,`big` 用例 n = 33554432):

| 实现 | 耗时 | 有效带宽 | 占峰值 | 评级 |
|---|---|---|---|---|
| **参考解**(私有化 + 4096 块) | **0.146 ms** | **917 GB/s** | **91%** | **S** |
| 私有化 + int4 向量化 | 0.144 ms | 930 GB/s | 92% | (与参考解在噪声内) |
| 私有化,128 块 | 0.148 ms | 904 GB/s | 90% | S |
| 私有化,64 块 | 0.188 ms | 712 GB/s | 71% | A |
| 私有化,32 块 | 0.335 ms | 401 GB/s | 40% | C |
| 朴素基线(全局原子加) | **6.2 ms** | **22 GB/s** | **2%** | 不合格 |

两个值得盯住的对比:

* 参考解相对基线快了约 **42 倍**。这么大的倍数在 01/02/03 那种"朴素即最优"的题上
  是不可能出现的 —— 它说明这题的问题根本不在带宽,而在冲突。
* 但参考解也只比"私有化 + 128 块"快 1%。也就是说,一旦冲突被搬走,
  这道题立刻退化成一个普通的访存题 —— 剩下的空间在硬件上,不在代码里。
  **`int4` 向量化只值 1.4%,在噪声量级** —— 这道题不需要你去做它。

`B / A / S` 的门槛是 50% / 65% / 80%(占峰值)。三条都卡在实测数字的空隙里:
朴素实现的 2% 离 B 差得远;B 还额外把"私有化了但只开 32 块"挡在外面;
S 要求你把"读"这条通路用上八成 —— 但只要你认出"块数得铺满 128 个 SM",
它就到手了,不需要精调。

`leet solution 07` 里有参考解。

## 思考题

1. 如果把桶数从 100 改成 **8**(数据仍然只落在 0..7),朴素基线会变快还是变慢?
   快/慢多少倍,为什么?(提示:算一下每个桶要被加多少次,以及那些串行链是
   并行走的还是排队走的 —— 桶变少,是"并行的队列变少了"还是"每条队列变长了"?
   想清楚之后再想:桶数**变多**到 4096 呢,趋势会反过来吗?)

2. 私有化之后,块的个数是越多越好吗?块数从 4096 加到 32768,哪一部分开销会
   跟着涨、涨多少?块数减到 64 又会先撞上什么墙?(提示:两个方向撞的是
   不同的墙 —— 一个和"归并阶段的原子加次数 = 块数 × nbins"有关,
   一个和"能不能掩盖住显存延迟"有关。实测曲线的拐点正好在 128。)

3. 为什么"清零"不能用 kernel 里的 `if (tid < nbins) bins[tid] = 0;` 加一个
   `__syncthreads()` 来做?请具体指出哪个块、在什么时刻会出问题。
   如果非要在 kernel 里清,你需要什么机制?(提示:这个机制在 CUDA 里叫
   cooperative groups 的 grid sync,而它要求 kernel 用
   `cudaLaunchCooperativeKernel` 启动、且 grid 大小不能超过"能同时驻留在卡上"
   的块数 —— 想想为什么要这个限制,以及本题的 131072 个块离这个限制有多远。)
