# 06 矩阵乘法(分块 GEMM)

> 难度 ●●●●○ · 标签 `gemm` `tiling` `shared-memory` `register-blocking` `reuse` · 考点:算术强度、共享内存分块、寄存器分块、边界补零

## 题目

`out = a @ b`,三个矩阵都是 `n×n`、row-major:

```
out[i][j] = Σ_{k < n} a[i][k] * b[k][j]
```

```cuda
__global__ void matmul(const float* a, const float* b, float* out, int n);
void matmul_launch(LaunchCtx& ctx);
```

`LaunchCtx` 里你能拿到的字段(设备内存的分配、搬运、计时、校验都由框架包办):

```
ctx.a    const float*  长度 n*n    左矩阵(row-major)
ctx.b    const float*  长度 n*n    右矩阵(row-major)
ctx.out  float*        长度 n*n    输出,需要你写入
ctx.n    int           矩阵边长
```

- 三个矩阵都是方阵。`n` 是**运行时参数**,不是编译期常数:用例里有 2048、1531、100。
- **`n` 不保证是 2 的幂,也不保证整除你的 tile 尺寸。** 1531 是质数,100 比一个
  tile 还小 —— 边界处理写错就会在这两个用例上现原形。
- 基线(一个线程算一个输出、每次乘加都从全局内存取数)是**完全正确且访存合并**的。
  你要做的不是「让它对」,而是「让它少读」。

## 为什么这道题重要

前五题里,数据复用是配角:01/02 根本没有复用(一个元素只参与一次计算),03 转置
每个元素读一次写一次,04 归约每个元素读一次,05 卷积终于有了复用,但那道题的
结论是「消除冗余读之后就撞上显存带宽墙,没多少空间」。

**矩阵乘法是第一个「复用好到能把显存带宽墙推走」的算子。** n=2048 时它的算术强度
可以做每字节上千次乘加 —— 这个量级下 DRAM 带宽不再是瓶颈,瓶颈转移到**片上**:
寄存器、共享内存、以及访存流水线的吞吐。

于是这道题教的东西和前五题都不一样:**瓶颈不在内存,在「你怎么把内存里的数
喂给 FMA」**。这是 GPU 优化里最重要的一个分水岭 —— 之前的题都是「少搬点字节」,
从这题开始是「每个字节多用几次」。后面所有的高性能算子(卷积、注意力、
各种融合算子)都是这个思路的变体。

## 慢在哪里

n=2048 是个 86 亿次 FMA 的问题,先把账算清楚:

| 量 | 数值 |
|---|---|
| 输出元素 | 2048² ≈ **419 万** |
| 乘加次数(FMA) | 2048³ ≈ **86 亿**(= 17.2 GFLOP) |
| 基线的每个输出要读 | a 的一整行 + b 的一整列 = **2n = 4096 个元素** |
| 基线要送进寄存器的数据 | 419万 × 4096 × 4B = **68.7 GB** |
| 真正需要搬的字节 | 3 × 16MiB = **48 MiB** |
| 比值 | 每个字节被请求了约 **1365 次** |

两条与实现无关的下限:

- **DRAM 带宽**:48MiB ÷ 1008 GB/s ≈ **50 µs**。注意这个数小得离谱 —— 三块矩阵
  加起来 48MiB,比 4090 的 72MB L2 还小,**它们整个装得进二级缓存**。
- **FMA 算力**:86亿 ÷ (128 SM × 128 FMA/cycle × 2.5GHz) ≈ **210 µs**。
  一个理想实现不可能比这更快。

而**基线的实测耗时是 3.23 ms —— 比算力下限慢 15 倍**。

慢在哪一条?候选有三个(具体是哪一条,值得你自己用 `ncu` 去称):

1. **访存指令数**:每个 warp 每轮 k 要发两条 load,合计 131072 × 2048 = **5.4 亿条**。
   每条指令换来 32 次乘加(一个 warp 一轮),而硬件每 cycle 只放行有限条。
2. **L1 到寄存器这条路的吞吐**:每 SM 每 cycle 128B = 32 个 float。
   基线的比值是「每 4 字节换 1 次 FMA」,也就是说这条路每 cycle 最多喂 32 次
   FMA,而 FMA 单元每 cycle 能吃 128 次 —— **四分之三的算力在等数据**。
3. **L2 带宽**:重复请求虽然命中 L2,但粗算下来 L2 要往 L1 送十几个 GB,
   而 L2 的读带宽也是有限的一一 3.23ms 对应约 4 TB/s,正好是 L2 的量级。

三条路的解法是同一个:**减少访存次数**。不是「少搬字节」(DRAM 那边根本没堵车),
而是让每一次访存多喂几次 FMA —— 这就是**算术强度**。

> 记住这两个数:`86 亿次 FMA`(必须做,对应 210µs)和 `68.7 GB 的取数请求`(纯浪费)。
> 优化的目标就是把这个 1365:1 的浪费压下去。

## 解法思路

### 第一步:共享内存分块

让一个线程块负责 `out` 的 `TILE×TILE` 一块。算这一块需要的输入是 `a` 的
`TILE×n` 条带和 `b` 的 `n×TILE` 条带 —— 不能一次全搬进来,所以沿 k 方向分轮:

```
for t in 0 .. n/TILE-1:            # 每一轮管 k ∈ [t*TILE, (t+1)*TILE)
    协作把 a[row0..row0+TILE)[t*TILE..] 和 b[t*TILE..][col0..)
    两块 TILE×TILE 搬进共享内存      # 越界的位置填 0
    __syncthreads()
    每个线程只从共享内存取数做 FMA
    __syncthreads()                # ← 这一处不能漏
```

一个字节从全局内存搬进来一次,就被 `TILE` 个输出复用,全局请求量降到 1/TILE。

### 第二步:寄存器分块 —— 这一步才是分水岭

让**一个线程算 `R×R` 个输出**。这一轮 k 它只需要读 `R` 个 A 值 + `R` 个 B 值,
就能做 `R²` 次 FMA:

```
读 8 个值(R=4)  → 16 次 FMA      每次访存摊到 2 次 FMA
读 2 个值(R=1)  → 1 次 FMA       每次访存摊到 0.5 次 FMA
```

访存指令数降到 1/4,「每 cycle 128B 只喂 32 次 FMA」这条上限随之抬到 128 次 ——
这才够得着 FMA 单元。`acc[R][R]`、`ar[R]`、`br[R]` 必须全部待在寄存器里,所以
**所有下标都必须是编译期常数**:内层循环要用 `#pragma unroll` 配常数边界展开。

代价很直接:`R×R` 个累加器就是 `R²` 个寄存器。R=4 是 16 个,加上操作数和地址
约 40 个,很舒服;R=8 就是 64 个累加器,加上寻址和流水线要用的临时寄存器,
很容易越过 255 的上限,溢出到 local memory(实际就是显存)—— 那时性能会**比基线
还差**。这不是理论警告,是这类 kernel 最常见的翻车方式。

### 为什么第一步单独做几乎没用(实测)

这是本题最反直觉、也最值得记住的一个结果。同一台 4090、同一个 `square`(n=2048)
用例,四个档次的实测:

| 实现 | 耗时 | 相对基线 |
|---|---|---|
| 基线:1 线程 1 输出,全部从全局读 | **3.23 ms** | 1.00x |
| 只做共享内存分块(TILE=32,1 输出/线程) | **2.89 ms** | **1.17x** |
| 分块 + 2×2 寄存器分块 | **0.99 ms** | 3.41x |
| 分块 + 4×4 寄存器分块(参考解) | **0.56 ms** | 5.74x |

**共享内存分块单独做,只快 17%。** 原因在物理层:共享内存和 L1 在芯片上是
**同一块 SRAM**,`LDS` 和 `LDG` 走同一条访存流水线,吞吐都是每 SM 每 cycle 128B。
把「全局冗余读」换成「共享内存读」,**访存指令数一条没少** —— 一个线程算一个输出时,
每个 FMA 仍要配 2 次读(从 A 取一个、从 B 取一个),上限还是 16 FMA/cycle/SM,
只有峰值的 1/8。基线本来就有 L1 和广播帮着兜底,所以两者几乎打平。

真正把性能抬起来的是**第二步**:R=2 拿到 3.4x,R=4 拿到 5.7x。
「分块」负责把数据从 DRAM 搬到你手边,「寄存器分块」才负责让你**真的少伸手**。

### 第三步:越界填 0,而不是跳过

搬运 tile 时,落在矩阵外的位置填 `0.0f` 而不是跳过:

```cuda
as[r][c] = (row0 + r < n && k0 + c < n) ? a[(row0+r)*n + k0+c] : 0.0f;
```

这样 k 方向的循环就能一路算到底,**内层一个分支都不用判**(0 乘任何数都是 0,
不影响结果)。代价是 k 方向多算了几个无效的 0;收益是内层循环干干净净 ——
而内层循环是要跑 86 亿次的地方,那里省一条指令比外面省一百条都值。

注意**写回时不能省边界判断**:越界填 0 只保护了「读」,`out` 的越界写会踩到别的
缓冲上,框架的哨兵区会当场抓到(前后各 4096 个元素)。

### 参数怎么选

参考解用的是 `TILE=64`、块内 `16×16=256` 线程、每线程 `4×4`:
共享内存 `2×64×64×4B = 32KB`,一个 SM 能驻留 3 个块;每个字节被复用 64 次。

TILE 不是越大越好:128×128 的 tile 要 128KB 共享内存,超过 4090 每 SM 100KB
的上限,一个块都放不下,occupancy 直接崩掉。**共享内存用量、寄存器用量、
复用度这三者的最优解不在同一个点上** —— 没有标准答案,自己扫一遍。

## 陷阱提醒

- **`__syncthreads()` 一次都不能漏,也不能放进分支。** 「算完这一轮再搬下一轮」
  那一处最容易漏:快的线程会把慢的线程还在读的数据覆盖掉。这种错**有时对有时错**,
  `n=100` 的小用例专门用来跑 racecheck 抓它。
- **累加器不能是运行时下标。** 写 `for (int k = 0; k < nk; ++k)`(nk 是变量)而不
  展开,`acc[R][R]` 就会掉进 local memory,性能比基线还差。用编译期常数 + `#pragma unroll`。
- **边界:1531 和 100 都不整除 64。** 最后一块 tile 在行方向和列方向都会伸出矩阵外,
  读要填 0、写要判界。只在 2048 上测过就交,会在这两个用例上崩。
- **`int` 索引会溢出吗?** 这题不会(2048² = 419 万),但 `(long long)row * n + col`
  是免费的,习惯先养成。
- **bank conflict**:`bs[k][tx*4]` 按 `float4` 读、`as[ty*4+i][k]` 是广播,两者都
  不冲突。但如果你把共享内存的行距改成别的数、或者让同一个 warp 的线程去读
  跨行的地址,就会撞上 bank conflict —— 那是纯浪费,不解决任何问题。
- **别去优化 DRAM 流量。** 三块矩阵只有 48MiB,DRAM 下限 50µs,比算力下限 210µs
  还小。在这题上讨论「省显存带宽」是没有意义的,瓶颈从头到尾都在片上。
  这是本题和前五题最大的区别。

## 评分

按**相对基线的加速比**评级(`leet test 06` 会打印每个用例的数字):

| 评级 | 加速比 | 意味着 |
|---|---|---|
| B | ≥ 1.5x | 寄存器分块真的生效了(哪怕只有 2×2)。注意:只做共享内存分块是 1.17x,拿不到 |
| A | ≥ 4.2x | 4×4 量级的寄存器分块,tile 也调得不错 |
| S | ≥ 5.2x | 贴到参考解的水平(5.74x,有效算力 30.6 TFLOPS) |

参考解的实测(4090,框架自动清 L2):

```
基线(朴素,一线程一输出)          3230 µs
参考解(TILE=64 + 4×4 寄存器分块)   562 µs   → 5.74x
```

这道题的加速比**有物理天花板**,和 05 一样:
算力下限是 210µs,而 4×4 寄存器分块下共享内存带宽只够把算力喂到 562µs 附近
(参考解已经贴到那条线上,420µs 是这条通路的理论极限)。所以 S 不是「随便调调
就能拿」,也不是「不可能拿到」——它对应的是「把片上这条通路用满了」。

小用例(总耗时不到 20µs)不参与评级 —— 那个量级上测的是启动开销和计时器抖动。
本题里 `tiny`(n=100)专职考边界与跑 racecheck,它小到 4 个线程块就干完了,
所以别拿它的数字下结论(它甚至可能比基线慢,因为基线在这种规模上并行度更好)。

容差是 `atol=1e-3, rtol=1e-4`。参考解在 CPU 上用 `double` 累加 2048 项,
很接近真值;你的 GPU 版是另一套结合顺序的 f32 累加,实测最大绝对偏差 1.45e-4 ——
比 `atol` 还有近一个数量级的余量;而错误实现(漏一块 tile、漏边界、少算一半 k)
的偏差是 O(1) 以上,分得很开。顺带一提:对拍输出里 `max_rel_err` 会报出 1.26 这样
大于 1 的数,那是因为某些输出元素**恰好接近 0**(正负项相消),除法把一点点绝对
误差放大成了很大的相对误差 —— 真正把关的是 `atol`。

## 思考题

1. **为什么只做共享内存分块只有 1.17x?** 把「基线 / 只分块(R=1)/ 分块+寄存器分块
   (R=4)」三版各自「每算一个输出要发多少条访存指令、搬多少字节」列个表。
   已知 LDS 和 LDG 共用同一条流水线、吞吐同为每 SM 每 cycle 128B ——
   这件事对这三版的性能上限分别意味着什么?为什么 R 从 1 变到 2 的收益(1.17x→3.41x)
   比从 2 变到 4 的收益(3.41x→5.74x)大得多?

2. **R 取多大?** 把 R 从 4 调到 8(每线程 64 个输出),用 `leet test 06` 看耗时。
   如果变慢了,先用 `nvcc --ptxas-options=-v` 看寄存器用量,判断是**寄存器溢出到
   local memory** 还是**occupancy 掉下来**导致的。再想想:为什么这道题的 R
   最优值,和 05 题里 `REG` 的最优值(4)会撞在同一个数上?

3. **这题的 DRAM 到底参与了多少?** 三块矩阵一共 48MiB,比 4090 的 72MB L2 还小,
   DRAM 下限只有 50µs;而基线实测 3.23ms —— 换算成「等效带宽」是 3.23ms × 1008 GB/s
   ≈ 3.3 GB,是实际数据量的 65 倍。**这说明了什么?** 提示:05 题的思考题 3 是同一个
   问题的另一面 —— 那题是「有效带宽虚高」,这题是「有效带宽虚低」,两个方向的偏差
   来自同一个硬件事实。
