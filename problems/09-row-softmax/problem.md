# 行 Softmax(把三趟压成一趟)

## 一、题目

给一个 `rows × cols` 的 float 矩阵 `x`(行优先),对**每一行**独立地做 softmax:

```
m[r]    = max over c of ( scale * x[r][c] )
y[r][c] = exp(scale*x[r][c] - m[r]) / Σ_c exp(scale*x[r][c] - m[r])
```

接口一览:

| 名字 | 类型 | 说明 |
|---|---|---|
| `ctx.x` | `const float*` | 长度 `rows*cols`,行优先 |
| `ctx.y` | `float*` | 长度 `rows*cols`,**你要写的输出** |
| `ctx.rmax` / `ctx.rsum` | `float*` | 长度 `rows`,**scratch**,想用就用(用之前必须自己写) |
| `ctx.rows` / `ctx.cols` | `int` | 矩阵尺寸,运行时才知道 |
| `ctx.scale` | `int` | 缩放系数(用例里是 1 或 100) |

你要写的是 `row_softmax` 这个 `__global__` 函数和 `row_softmax_launch` 这个启动函数。

## 二、为什么这道题值得做

softmax 是深度学习里出现频率最高的小算子之一(每个 transformer 层的注意力里都有一个),
它有个尴尬的性质:**数学上只有一行公式,工程上却逼着你在一趟里同时算出两个归约量。**

这道题是「归约」和「访存」两条线的交汇点:04 题学的块内归约在这里要用两次;
而真正的胜负手不在归约快不快 —— 在于**同一份数据你从 DRAM 里读了几遍**。
另外它还顺带教一件初学者最容易忽略的事:exp 之前必须减去最大值。

(如果你做过 PyTorch 科目的 `py01-softmax-dim0`,那题讲的是"归约维是否连续"对
torch 内核的影响;这题讲的是"怎么把多趟压成一趟"。两件事互补,不重复。)

## 三、物理瓶颈:这道题只跟 DRAM 流量有关

先算账。以 `square` 用例为例:8192 × 4096 = 33.5M 个 float = 134MB。

* **算的部分**:33.5M 次 `expf`。4090 每个 SM 每周期能出 16 个超越函数,
  128 个 SM 在 2.5GHz 下是 5.1e12 次/秒 → 约 **7µs**。
* **搬的部分**:134MB 读 + 134MB 写 = 268MB,峰值带宽 1008GB/s → 约 **266µs**。

差了将近 40 倍。所以这题**不存在"算得更快"这回事**,只看你搬了多少字节。

再看两种写法各搬多少:

| 写法 | DRAM 流量(square 用例) |
|---|---|
| 基线:三趟(max / exp 求和 / 归一化) | 134×3 读 + 134 写 = **536MB** |
| 让输入只被读一遍(怎么做到见第四、五节) | 134 + 134 = **268MB** |

按流量算,536 / 268 = **2.0**,这就是这道题的天花板 —— 不是估计,是算术。

**但实测比 2.0 还高一点**。四种写法真跑出来的结果(square 用例,框架自动清 L2):

| 写法 | DRAM 流量 | 耗时 | 加速比 | 有效带宽 |
|---|---|---|---|---|
| 基线:3 个 kernel | 536MB | 0.569 ms | 1.00x | 942 GB/s |
| 2 个 kernel(第一趟同时出 max 和 sum) | 402MB | 0.426 ms | **1.33x** | 944 GB/s |
| 1 个 kernel,但三趟都读全局内存 | 268MB | 0.246 ms | **2.31x** | 1090 GB/s |
| 1 个 kernel + 整行留在共享内存 | 268MB | 0.238 ms | **2.39x** | 1126 GB/s |

第二行的 1.33x 恰好等于 536/402,第四行的 2.39x 比 2.0 高 —— 两个数字都值得解释:

* 1.33x 精确吻合,说明这道题**只有 DRAM 流量一个机制**,没有别的因素掺和。
* 2.39x 超过 2.0,是因为基线的两趟**纯读**归约并没有跑满带宽(942 GB/s),
  而读写混合的融合版能跑到 1126 GB/s —— 后者甚至超过标称峰值 1008 GB/s,
  那是"计时停止的瞬间最后一批写还在 L2 里"的水分(01 题里解释过)。
  所以"按流量算的天花板"是个下限,不是精确预言。

**最反直觉的是第三行**:一个 kernel 里把全局内存读三遍,居然和"把行缓存到片上"
的第四行只差 3%。原因见下一节。

## 四、基线慢在哪(以及一个很容易搞错的细节)

基线是**三个 kernel**:① 求每行最大值 ② 求每行 exp 之和 ③ 归一化。
这三趟本身都写得规规矩矩(一行一个 block、跨步循环、访存合并、树形归约、同步齐全),
它唯一的问题就是:同一份 134MB 的输入被从 DRAM 搬了三遍。

你可能会想:"那我写**一个** kernel,里面把全局内存读三遍,不是一样慢吗?"

**不一样,而且差别很大。** 一个 kernel 内部对同一行的三次读,第二、三次会命中 L2:
4090 的 L2 有 72MB,而一行只有 16KB —— 在你回头读第二遍之前,它不可能被挤出去。
命中 L2 的部分走的是 L2 带宽(比 DRAM 快好几倍),几乎不花 DRAM 流量。

基线之所以真的贵,是因为**两个 kernel 之间隔着一道全局屏障**:等 ① 跑完,
整个 134MB 已经被流过去了,而 L2 只有 72MB —— ① 读进来的行早被挤干净了,
② 和 ③ 只能老老实实回到 DRAM 重新读。

一句话总结:**"多读几遍"要不要钱,取决于这两遍之间隔了多少别的工作。**
装得进 L2 的复用是免费的;装不进的复用按 DRAM 计价。这是本题最值得带走的一条物理事实,
也是"为什么优化要看数据规模"的根源。

上面第三节那张表里的第三行(2.31x)就是对这段话的实测验证:它把三趟合成一个 kernel、
**完全没有**用共享内存缓存整行,就已经拿到了 2.31x —— 因为那两趟重读全部命中 L2。
真正决定成败的是"有没有跨过全局屏障",不是"有没有用共享内存"。

(也正因如此,本题的用例规模是刻意选大的:输入必须明显大于 L2,基线的三趟才真的贵。
你把同一个 kernel 放到 8MB 的输入上跑,会发现三趟和一趟几乎一样快 —— 那不是 bug,是 L2。)

## 五、解法思路

决定性的那一步只有一句:**把三趟合进一个 kernel —— 去掉那道全局屏障。**
只要在同一行上的三次访问之间不再隔着"整个输入都流过去一遍",它们就会命中 L2,
DRAM 流量立刻从 536MB 掉到 268MB(实测 1.33x → 2.31x)。

第二步才是**把整行留在片上**(共享内存或寄存器),连 L2 的往返也省掉。
这一步在本题只值 3%,但它才是可移植的写法:数据一旦装不进 L2,它就从"优化"
变回"唯一可行的办法"。

具体做法:

1. **一行一个 block。** 行与行之间没有任何依赖,`blockIdx.x` 直接就是行号,
   不需要任何跨 block 通信。
2. **把行装进共享内存**(一行 `cols` 个 float;4096 个就是 16KB,装得下),
   或者干脆留在寄存器里。之后 max、exp、求和、归一化全在片上做。
3. **两次块内归约**:先归约出 `m`,再归约出 `sum`。这就是 04 题写过的东西,直接用。
4. **两个归约之间必须有 `__syncthreads()`** —— 第一个归约的结果正是第二个的输入。

推荐的分段(参考答案就是这个结构):

```
① 合并地把行搬进共享内存,同时用寄存器求出局部最大值   → 块内归约 → m
② 遍历共享内存:e = expf(v - m),把 e 写回共享内存,同时累加 → 块内归约 → sum
③ 再遍历共享内存:y = e * (1/sum),合并地写回 DRAM
```

第 ② 段把 `e` 写回共享内存,是为了第 ③ 段不必再算一次 `expf`。

访存账:DRAM 8 字节/元素,共享内存 16 字节/元素。看着共享内存更多,但它是片上的 ——
每周期每 SM 128 字节,128 个 SM 加起来约 41TB/s,是 DRAM 的 40 倍,
所以那 16 字节折合下来只有几微秒。

**顺手省一点 ALU**:`1.0f/sum` 只算一次,循环里用乘法。f32 除法在硬件上是
"倒数近似 + 牛顿迭代",十几条指令,别每个元素做一次。

## 六、陷阱

1. **必须先减去最大值。** `sharp` 用例(scale=100)就是为这件事准备的:
   `x` 最大到 1,乘 100 之后 `expf(100) = inf`,`inf/inf = NaN`。
   数学上减不减最大值结果一样,数值上不减就是灾难 —— 真实模型里的 logits
   量级到几十上百是常态。**注意:scale=1 的用例不减最大值也能过**,
   所以别指望测试替你发现这个错误,这是要自己养成的习惯。
2. **`__syncthreads()` 漏一个,就可能有线程读到还没写完的共享内存。**
   框架会跑 racecheck,而且每个用例重复跑 3 次 —— "有时对有时错"是能抓到的。
   特别容易漏的是**第二种**:上一次归约刚被所有线程读过的暂存区,下一次归约
   要复用它之前,也必须补一个屏障(参考答案里 `block_max` / `block_sum` 开头
   那一句就是干这个的)。实测:把那一句删掉,racecheck 报 **3 个 hazard**,
   而正确性对拍**照样通过** —— 这类竞态在实测里没翻车,别指望它替你暴露。
3. **边界**:`cols` 不整除 blockDim(`sharp` 用例 4093 = 15×256 + 253)、
   `cols` 比 blockDim 还小(`tiny` 用例 129)。跨步循环
   `for (c = t; c < cols; c += BLOCK)` 天然处理这两种情况;
   但**共享内存里没被写到的位置是垃圾值**,别去读。
4. **共享内存的大小是运行时才知道的**:用 `extern __shared__ float sh[];`
   加上启动时传入的字节数。一行 4096 个 float 是 16KB,加上归约暂存区约 17KB,
   在 48KB 的默认上限内;`cols` 上万就要另想办法(见思考题 1)。
5. **暂存区别和行数据打架**:参考答案把归约暂存区放在 `sh + cols`。

## 七、评分

* **正确性**:与 CPU 参考解(逐行、double 累加)按 `atol=1e-5, rtol=1e-4` 对拍,
  每个用例重复 3 次。不通过就不算过 —— 性能只评级,不卡关。
* **性能**:按**相对基线的加速比**评级,取所有可评级用例里的最好成绩。
  门槛是照着第三节那张实测表卡的:

  | 评级 | 加速比 | 对应的写法 |
  |---|---|---|
  | S | ≥ 2.10x | 三趟合成一个 kernel(参看实测表的第三、四行) |
  | A | ≥ 1.60x | 融合了,但没融合好(块太大、访存没合并、行缓存用错) |
  | B | ≥ 1.20x | 至少真的去掉了一趟(例如两个 kernel) |

  `leet solution 09` 可以看到参考答案,它实测 **2.39x**(0.238 ms)。
  **注意 S 并不要求你写共享内存** —— 一个 kernel 里读三遍全局内存就能到 2.31x,
  因为那几趟重读命中 L2。想拿满分,关键是"别让同一份数据跨过全局屏障被读三遍"。

* 一条有用的标尺:如果你写成**两个** kernel(第一趟同时算出 max 和 sum,
  第二趟归一化),DRAM 流量是 134×2 + 134 = 402MB,上限只有 1.33x。

## 八、三个思考题

1. **如果 `cols` 大到一行装不进共享内存(比如 100 万),还能只读一遍吗?**
   提示:能不能一边读一边维护 `(max, sum)` 这一对状态?难点在于 ——
   当你读到更大的值时,之前累加的那些 `exp` 全部作废了,怎么办?
   (这个技巧叫 online softmax,是 flash attention 的核心。)
2. **只写两个 kernel**(第一个算出每行的 max 和 sum,第二个归一化),
   DRAM 流量是多少 MB?为什么它还是比"融合成一趟"贵?
   再想一步:第一个 kernel 里如果不缓存整行,要"同时"算出 max 和 sum 有什么困难?
3. **把 `expf` 换成 `__expf`(硬件 SFU 近似,相对误差约 1e-6)会更快吗?**
   先想清楚这题卡在哪一环(第三节的账),再去测。测完再想:
   什么情况下这个替换才真的有意义?
