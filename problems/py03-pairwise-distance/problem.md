# py03 成对平方距离矩阵

## 题目

给你**一个批次** `ctx.x`,形状 `(rows, d)`,f32、按行连续(row-major)。
它由两组特征向量拼成,恒有 `rows == n + m`:

```
A = ctx.x[:ctx.n]                 # (n, d)  —— 前 n 行
B = ctx.x[ctx.n:ctx.n + ctx.m]    # (m, d)  —— 从第 n 行开始的 m 行
```

要求对**每一对** `(A[i], B[j])` 求平方欧氏距离(不开方),写进 `ctx.out`:

```
out[i, j] = Σ_d ( A[i, d] - B[j, d] )²          # out 的形状是 (n, m)
```

输出两种写法都合法:直接 `return` 一个 `(n, m)` 的张量,或者写进 `ctx.out`
(但这次拷贝本身要花一次全量访存,想清楚划不划算)。

> 为什么是「一个批次切成两半」而不是两个输入张量?因为对比学习里
> query 和 key 本来就是拼在一个张量里的 —— 真实代码就是这么排的。

## 为什么这道题值得做

成对距离是 kNN、层次聚类、DBSCAN、RBF 核、对比学习(InfoNCE)、
以及 attention 里的 `QKᵀ` 的共同内核 —— 它出现的频率高到你迟早会手写一次。

而它有一个**别的 shape 都没有的特征**:输出比输入大得多。

| | 元素数 | 字节数(n = m = 4096, d = 32) |
|---|---|---|
| 输入 | `rows × d` | 1MB |
| 输出 | `n × m` | 67MB |

输出是输入的 **67 倍**。这个形状会诱发一个非常自然的错误:既然要算
`A[i,d] - B[j,d]`,那就 `A.unsqueeze(1) - B.unsqueeze(0)` 一下,让广播去处理
下标 —— 一行写完,读起来就是公式本身。但它造出来的是一个**真实存在**的
`(n, m, d)` 张量,元素数是输出的 **d 倍**。现实里那些「程序没写错,
但一跑就 OOM」和「明明用了 GPU 还是慢 20 倍」的事故,一大半是这么来的。

所以这道题真正教的是两件事:

1. **动手之前先把中间张量的字节数算出来**。不是估,是算:每个维度乘一遍,
   再乘 4(或乘 8)。这个数字比任何 profiling 工具都先告诉你答案。
2. **用算力换带宽**。GPU 的浮点算力相对带宽是极度过剩的
   (4090:约 82 TFLOPS f32 对 1008 GB/s,比值约 80 flop/byte)。
   凡是能"多做点乘加、少搬点数据"的等价变形,在这类机器上几乎总是赢。

## 慢在哪:先算账,再写代码

基线的写法是照定义直译:

```python
diff = A.unsqueeze(1) - B.unsqueeze(0)   # (n, m, d)
return diff.pow(2).sum(dim=2)            # (n, m)
```

它在数值上完全正确,也不是"故意写烂"—— 它就是公式本身。慢的原因是**它真的
把那个 `(n, m, d)` 造出来了**。以 square 用例(n = m = 4096,d = 32)为单位数一遍:

| 步骤 | 中间张量 | 访存 |
|---|---|---|
| `A.unsqueeze(1) - B.unsqueeze(0)` | `(n, m, d)` = 2.1GB | 写 2.1GB |
| `.pow(2)` | 又一个 2.1GB | 读 2.1 + 写 2.1GB |
| `.sum(dim=2)` | `(n, m)` = 67MB | 读 2.1 + 写 0.067GB |

合计约 **8.5GB**,而真正必须搬的只有 `读 x(1MB)+ 写 out(67MB)`。
99% 的显存流量花在了一个本可以不存在的张量上。

为什么恰好是 d 倍?因为中间张量的元素数是**三个维度相乘**:`n·m·d` = 5.4 亿,
而输出只有 `n·m` = 1677 万。d 每翻一倍,垃圾流量翻一倍;n 或 m 再翻一倍,
垃圾流量翻**四**倍,而真正要写的输出只翻一倍 —— 这就是这个 shape 的危险之处。
(反过来,这也是为什么本题所有可评级用例都取同一个 d:加速比由 `d` 和
"输出被搬几遍"共同决定,d 一变,门槛就没法用一套数字卡。)

物理上的硬顶在这里:数据在 DRAM 和 SM 之间来回走,单向带宽 1008 GB/s。
8.5GB 按峰值算就是 8.4ms(实测 9.73ms —— 有效带宽约 870 GB/s,峰值的 86%),
不管你的 SM 有多闲。**搬一个字节的代价,比算一次乘加贵得多。**

## 解法思路

### 方向一:找那个"语义就是它"的算子

PyTorch 里有一类距离/相似度算子,其中有一个的语义正好是「两组向量的成对 p 范数
距离」。去 `torch` 的文档里翻一翻(关键词:distance)。它内部是一个融合内核:
输入两个小张量,输出 `(n, m)`,中间不落任何 d 维张量。

用它之前先看清两件事:它返回的是**距离**还是**距离的平方**?题目要的是平方。
补那一步的时候,注意 `a * a` 会再分配一块 67MB 的输出,而 `a.pow_(2)` / `a.mul_(a)`
是在原地改 —— 少一遍读、少一遍写,134MB ≈ 0.13ms,别浪费。

### 方向二:自己把 d 这一维"消掉"

把公式展开:

```
Σ_d (a_d - b_d)²  =  Σ_d a_d²  -  2·Σ_d a_d·b_d  +  Σ_d b_d²
```

- 第一项只跟 A 的一行有关 → `(n, 1)`(注意 `keepdim=True`,否则是 `(n,)`)
- 第三项只跟 B 的一行有关 → `(1, m)`
- 第二项是一次**矩阵乘** `A @ B.t()` → `(n, m)`

关键在于:矩阵乘的访存是「读两个小输入 + 写一个大输出」,它把 d 这一维在
片上累加掉了 —— **中间那个 d 维张量根本不需要存在**。代价是多做了 n·m·d 次乘加。
这就是用算力换带宽:FLOPs 涨了 d 倍,访存降了 d 倍,而在比值 80 flop/byte 的
机器上这是稳赚的买卖。

三个 `(n,1)`、`(n,m)`、`(1,m)` 相加靠广播对齐 —— 想清楚哪一项要 `.t()`。
另外,能不能让"减去 2 倍"和"加上两项"都在**原地**完成(`mul_` / `add_`)?
每省一遍就是 67MB 读 + 67MB 写。

### 还能再快吗:让矩阵乘顺便把两项范数也带出来

方向二写出来是这样一条链:矩阵乘写一遍输出、`mul_(-2)` 读一遍写一遍、
两个 `add_` 再各读一遍写一遍 —— **输出被搬了 5 遍**,每遍 67MB。

那么问题变成:能不能让**一次**矩阵乘就把

```
-2·(A @ Bᵀ)  +  ‖A‖²  +  ‖B‖²
```

全部算出来?提示:矩阵乘的 k 维(点积求和的长度)是**可以加长的**。
往 A 的每一行末尾追加两个数、往 B 的每一行末尾追加两个数,让点积自己
把这两项带出来 —— 追加什么,才能让 `Σ_k a'_k · b'_k` 恰好等于你要的三项之和?
(工程上这叫"把 bias 折进 GEMM",cuBLAS 的 `addmm` 只是它最常见的一个特例。
想清楚它省下的是几遍访存,你就知道这道题的天花板在哪了。)

### 方向三:非要用广播,就把它限制在 L2 里

把 n 切成若干块,每次只摊开 `(块行数, m, d)` 的差张量。块取小一点
(比如 64 行 → 64×4096×32×4B = 33MB),中间张量就整个住进 L2(4090 是 72MB),
**一次显存都不用去**。物理上这是干净利落的正确思路 —— 它就是 CUDA 里
"分块 + 片上复用"的手写版本。

但在 eager PyTorch 里要算第二笔账:每一块都要起好几个内核(减、平方、求和),
每个内核的启动开销是几微秒,块数一多,`块数 × 内核数 × 几微秒` 就会追平甚至
超过你省下来的那点带宽。实测就是这样(见下表):块取 64 行只快 1.7 倍,
块取 32 行(更彻底地留在 L2,但内核数翻倍)在最大的用例上也才 3.7 倍 ——
**物理方向完全正确,收益却被这个抽象层次的启动开销封了顶**。
这不是"分块错了",而是启动开销成了新的瓶颈。想清楚拐点在哪,比记住结论重要。

## 实测(square:n = m = 4096,d = 32,基线 9.73ms)

单位是"相对基线的加速比"。注意同一个实现在小用例上的倍数天然偏低 ——
固定开销(内核启动、Python 派发)占比更大;**而评级取各用例的最大值**。

| 写法 | square | odd | prime | 代价 |
|---|---|---|---|---|
| 基线:广播出 `(n,m,d)` | 1.00x | 1.00x | 1.00x | 4 遍 ×(n,m,d) |
| 分块塞进 L2(CH = 64) | 1.69x | 1.67x | 1.74x | 启动开销封顶 |
| 分块塞进 L2(CH = 32) | 3.70x | 1.57x | 1.67x | 同上,内核更多 |
| `cdist` + 原地平方 | 27.0x | 40.4x | 25.6x | ≈ 5 遍 ×(n,m) |
| 展开 + 原地 `mul_`/`add_` 链 | 28.4x | 45.5x | — | ≈ 5 遍 ×(n,m) |
| 范数折进矩阵乘(k = d+2) | **108.1x** | 75.8x | 39.4x | **1 遍** |

这张表能用一个式子概括,它是这道题最该带走的东西:

```
加速比 ≈ 4d / (输出被搬的遍数) = 128 / 遍数          (d = 32)
```

朴素实现的流量是 `4 遍 × n·m·d`,不物化 d 维张量的实现是 `遍数 × n·m` ——
比值就是 `4d / 遍数`。**"输出被搬几遍"是一个可以数出来的整数**,
这就是为什么先算账比先写代码有用。

## 陷阱

1. **`cdist` 返回的是距离,不是平方距离**。题目要平方。忘了平方,误差是
   `sqrt(ref) - ref` 量级,一定会被抓到;但更常见的是"补了平方但补得很贵"。
2. **展开式有数值代价 —— 这是它唯一的缺点**。`Σa²` 和 `Σb²` 都是 O(d) 量级,
   两点几乎重合时三者相减的结果接近 0,而三个 O(d) 的数各自带着 f32 的舍入误差
   (灾难性抵消)。本题 d = 32、数据在 `[-1, 1)`,绝对误差在 1e-5 量级,
   容差留了 2 个数量级余量,放心用;但如果 d 是几千、或者数据尺度很大,
   **展开式会真的算不准**,那时工程上的做法是分块、每块内部用"直接相减"。
   知道它什么时候不能用,比记住它能用更重要。
3. **切片别切错**。`A` 是前 `n` 行,`B` 是**从第 n 行开始**的 `m` 行:
   `x[ctx.n : ctx.n + ctx.m]`。写成 `x[:ctx.m]` 会得到错的 B(而且形状可能碰巧
   对得上,结果却整块错),这是这道题最阴的一个坑 —— 用 prime 用例自查一遍。
4. **广播的语义**。`A.unsqueeze(1)` 是 `(n, 1, d)`,`B.unsqueeze(0)` 是 `(1, m, d)`,
   相减得到 `(n, m, d)`。想一想:为什么不是 `(n, m, 1)`?如果直觉答不上来,
   先用小张量(`n=2, m=3, d=4`)在 CPU 上试一次,把 shape 打出来。
5. **原地算子**。`a * b` / `a + b` 都会新分配一块输出;`a.mul_(b)` / `a.add_(b)`
   是读-改-写。输出 67MB 时,每省一遍就是 0.13ms,而它们不影响可读性。
6. **别在循环里同步**。`for i in range(n): ... .item()` 或 `.cpu()` 会把 GPU
   打回串行,一次同步的开销(几十微秒)就够算完一整个块。
7. **`ctx.out` 的形状是 `(n, m)`**。两个 `unsqueeze` 的方向搞反了会得到 `(m, n)`;
   如果靠 `.t()` 补救时传错位置,错的可能是整块数据。
8. 不要写 `ctx.out = ...` 重新赋值,那样框架看不到你的结果;要 `return` 或者
   `ctx.out.copy_(...)`。

## 评分

**正确性决定通过与否,性能只评级(S/A/B/C)** —— 这题不卡性能关。

评分指标是**相对基线的加速比**(`speedup`),门槛按上表的实测定:

| 评级 | 门槛 | 意味着什么(实测对照) |
|---|---|---|
| **C** | < 1.4x | 还在物化 `(n,m,d)` 那个张量(1.00x);把它原地化只省显存、不省字节数 |
| **B** | ≥ 1.4x | 用分块把中间张量关进了 L2(实测 1.67~3.70x)—— 物理对了,但被启动开销封顶 |
| **A** | ≥ 8x | 真的把 d 这一维消掉了(实测 25~45x):`cdist`,或者展开成矩阵乘 |
| **S** | ≥ 60x | 把输出压到 1~2 遍(实测 108x):让矩阵乘顺便把两项范数也带出来 |

门槛卡在实测数字的**空隙**里,两侧都留了余量 —— 所以拿到 A 不代表你写错了,
只代表输出还被搬了 5 遍(每遍 67MB ≈ 0.065ms,这就是 A 与 S 之间的全部差距)。

两个和评分有关的细节:

- 总耗时不到 20µs 的用例会被自动跳过评级(那个量级测的是启动开销和抖动)。
- 同一个实现在小用例上的倍数天然偏低(固定开销占比大),而评级取各用例的
  最大值 —— 所以别为了某个小用例去特判,把大用例写对就好。

## 思考题

1. `n = m = 100000` 时,输出矩阵是 40GB —— 单卡根本放不下。这时候
   「距离矩阵」这个中间结果本身就成了错误的设计。如果最终目标是"每行找最近邻",
   还需要把 `(n, m)` 真的写出来吗?写出一个不需要它的方案。
2. 方向二把 FLOPs 放大了 d 倍来换访存下降 d 倍。如果 d = 4096 而不是 32,
   这笔买卖还划算吗?用 4090 的峰值数字(82 TFLOPS / 1008 GB/s)算一下
   两边各自的时间,给出"该不该展开"的分界点。
3. 展开式在两点几乎重合时会灾难性抵消。设计一个**既用展开式、又不会放大误差**
   的方案(提示:分块,块内换一种算法;再提示:什么样的输入会让误差最大)。
