# 05 二维卷积(valid 模式)

> 难度 ●●●○○ · 标签 `2d` `convolution` `stencil` `shared-memory` `reuse` · 考点:halo 边界、共享内存分块、寄存器分块、算术强度

## 题目

每个输出像素,是输入图上一块 `kh×kw` 窗口与卷积核的加权和:

```
out[oy][ox] = Σ_{ky < kh, kx < kw} image[oy + ky][ox + kx] * kernel[ky][kx]
```

```cuda
__global__ void conv2d(const float* image, const float* kernel, float* out,
                       int h, int w, int kh, int kw, int oh, int ow);
void conv2d_launch(LaunchCtx& ctx);
```

`LaunchCtx` 里你能拿到的字段(设备内存的分配、搬运、计时、校验都由框架包办):

```
ctx.image   const float*  长度 h*w       输入图(row-major)
ctx.kernel  const float*  长度 kh*kw     卷积核(row-major)
ctx.out     float*        长度 oh*ow     输出,需要你写入
ctx.h/ctx.w / ctx.kh/ctx.kw / ctx.oh/ctx.ow   尺寸参数
```

- `image` 是 `h` 行 `w` 列、`kernel` 是 `kh` 行 `kw` 列、`out` 是 `oh` 行 `ow` 列,都是 row-major。
- 尺寸关系是 `oh = h-kh+1`、`ow = w-kw+1` —— 这是 **valid 卷积**,不补零,
  所以每个输出像素的 `kh*kw` 个采样点都必然落在 `image` 内部,**不需要任何边界判断**。
  但也别去自己算 `h-kh+1`:`oh`/`ow` 已经作为参数传进来了(`spec` 的 shape 表达式
  写不出减法),一律用 `ctx.oh` / `ctx.ow`。
- `kh` / `kw` 是**运行时参数**,不是编译期常数。你的 kernel 要对任意 `kh`/`kw` 成立
  (用例里有 7×7、3×3、5×9 —— 注意最后一个不是方形核)。

## 为什么这道题重要

前四题里,数据复用顶多是「转置时一个 tile 读一次、写一次」。这道题是第一个真正的
**stencil(模板计算)**:每个输出像素要吃 `kh*kw` 个输入值,而相邻输出像素的窗口
**大量重叠**。k7 用例里,输入图只有 64MB,但要做的采样点读取是 8.2 亿次 ——
同一块数据被反复读了 49 遍。

「重复读」是 stencil、卷积、矩阵乘、注意力这一整类算子的共同母题。而这道题演示的是
一个反直觉的事实:**消除重复读之后,性能并不能无限提升** —— 你会撞上显存带宽墙,
而那道墙是物理的。学会判断「我现在是被冗余访存卡住,还是已经贴着带宽墙」,比多拿
一个 S 重要得多。

## 慢在哪里:把「访存次数」和「搬了多少字节」分开算

基线(一个线程一个输出像素)在 k7 用例上的实测数字:

| 量 | 数值 |
|---|---|
| 输出像素数 | 4090² ≈ 1673 万 |
| 乘加次数 | 1673万 × 49 ≈ **8.2 亿** |
| 采样点读取次数 | 8.2 亿次 × 4B = **3.28 GB** 的访存流量 |
| 真正需要搬的字节 | 输入 64MiB + 输出 64MiB = **134MB** |
| 基线耗时 / 有效带宽 | **341 µs / 约 393 GB/s(峰值的 39%)** |

三个天花板,先算清楚谁最矮:

- **显存带宽**:134MB ÷ 1008 GB/s ≈ **133 µs**。这是「什么都不浪费」时的下限。
- **FMA**:8.2e8 ÷ (128 SM × 128 FMA/cycle × 2.5GHz) ≈ **20 µs**。算术上绰绰有余。
- **L1 访存流水线**:8.2 亿个采样点按 warp 打包,要先发出 2560 万条访存指令;
  每条指令的 32 个 lane 各要一个 float(128B),对齐时正好是 L1 的一个 wavefront,
  而采样窗口沿 x 平移 `kx` 格之后,这 128B 就横跨两条 128B 对齐的 cache line,
  得拆成两个 wavefront —— 49 个 tap 里只有 `kx=0` 那一个是严格对齐的。
  于是合计约 **4760 万个 wavefront**;128 个 SM 每 cycle 各洗一个,至少要 **~155 µs**。

所以基线的 341µs 是这么来的:**DRAM 只需要 133µs 就能把该搬的字节搬完,剩下的时间
全花在「把同一个值从 L1 一次又一次搬进寄存器」这条路上** —— 3.28GB 的片上流量、
每个 tap 都要重算一遍地址、每次 warp 访存还要吃 1.86 倍的错位惩罚。它既不是算力
瓶颈,也不是带宽瓶颈,而是**冗余访存**的瓶颈。

> 顺带记住两个数:`8.2 亿次乘加` 和 `3.28 GB 的读取`。前者是必须做的,后者是浪费。

## 解法思路

### 第一步:共享内存分块 —— 把每像素 49 次全局读降到约 1 次

让每个线程块负责输出图上 `TILE_H × TILE_W` 的一块。它需要哪些输入?
行 `[row0, row0+TILE_H+kh-1)`、列 `[col0, col0+TILE_W+kw-1)` —— 多出来的
`kh-1` 行 / `kw-1` 列就是分块卷积里的 **halo(光晕)**,相邻 tile 之间共享的边界。

```cuda
extern __shared__ float sm[];   // 大小运行时算:kh/kw 是运行时参数
// 协作把 (TILE_H+kh-1) × (TILE_W+kw-1) 搬进来,越界的位置填 0
// __syncthreads();
// 然后每个线程只从共享内存里取自己的 kh*kw 个采样点
```

全局读的次数从「每输出 49 次」降到「每输出约 1 次多一点(halo 的代价)」,
而且共享内存按 bank 寻址,32 个连续 float 恰好铺满 32 个 bank,没有错位惩罚。

### 第二步:寄存器分块 —— 这一步才是分水岭

**只做第一步,收益很有限。** 原因是:共享内存和 L1 在芯片上是同一块 SRAM,
LDS 和 LDG 走的是同一条访存流水线,吞吐都是每 SM 每 cycle 128B。
你只是把「全局冗余读」换成了「共享内存读」,**访存指令数一点没少**,
上面那条 L1 访存流水线的天花板(~155µs)原封不动。

真正的加速来自让**一个线程算多个相邻的输出**:x 方向连续算 `RX` 个,
那么一个 kernel 行里读 `RX + kw - 1` 个连续值,就能算出这 `RX` 个输出的这一行贡献:

```
读 10 个值(RX=4, kw=7)→ 28 次 FMA      每读 1 个值摊到 2.8 次 FMA
读 49 个值(不分块)     → 49 次 FMA      每读 1 个值只摊到 1 次 FMA
```

`RX` 取 4~8 比较合适:窗口 `RX+kw-1` 个值要待在寄存器里,太大就溢出到 local memory
(那比共享内存还慢)。累计值也用寄存器数组 `acc[RX]`,内层循环要
`#pragma unroll` 展开 —— `kw` 是运行时值,不展开的话 `v[i+c]` 是动态下标,
编译器会把整个窗口甩到 local memory 里,性能直接回到基线水平。

### 第三步(可选):把这条通路再压一点

- **向量化共享内存读**:把窗口按 `float4` 读(行距取 4 的倍数,行内起始偏移也是
  4 的倍数,对准 16B)。同样是 128B/cycle 的吞吐,但指令数降到 1/4。
- **写合并**:让一个 warp 在同一个 unrolled 步上写**连续**地址。如果每个线程写
  自己那 `RX` 个连续输出,一个 warp 的一次 STG 会散成好几条 cache line;
  值得把 tile 摆成「一个 warp 正好铺满一行」的形状。
- **tile 形状**:halo 的冗余在行方向是 `(TILE_H+kh-1)/TILE_H`,列方向是
  `(TILE_W+kw-1)/TILE_W`。`kh=7` 配 `TILE_H=8` 时行冗余高达 1.75×,而
  `kw=7` 配 `TILE_W=64` 时列冗余只有 1.09× —— 两个方向**不平衡**,贵的那个
  方向(行)拖了后腿。所以原则是:让两个方向的冗余大致相等(方形 tile),
  再在共享内存预算允许的范围内把 tile 整体做大。`TILE_H=8` 这种「又矮又胖」
  的形状恰好踩在坑里(行冗余 1.75×),而 `TILE_H=32` 又会吃掉太多共享内存、
  减少每 SM 的驻留块数 —— 这是个真实的取舍,不是单调的。

## 陷阱提醒

- **halo 必须判边界**。`row0+r < h`、`col0+c < w` 不成立的位置填 0。
  越界写会被框架的哨兵区当场抓到(前后各 4096 个元素);越界读更麻烦,
  可能读到别的缓冲上,结果错得毫无规律。
- **`__syncthreads()` 不能漏,也不能放进分支**。放进分支里,同一个块的不同线程
  走不同路径就会死锁或者读到没填完的数据。
- **动态共享内存的字节数要算对**:`extern __shared__` 的大小只能从启动参数给
  (第三个 `<<<>>>` 参数),写错了要么编译报错要么越界踩别人。
- **输出侧也要判边界**:最后一行/一列的 block 会伸出 `oh`/`ow`,算出来的 `ox`/`oy`
  要判过再写。
- **`int` 索引会溢出**。这个题的规模还够用(`4096×4096 = 1670 万`),但写
  `(long long)oy * ow + ox` 是免费的,习惯先养成。
- **bank conflict**。共享内存一行 `[TILE_W + kw - 1]` 个 float,如果行距是 32 的
  倍数,同一列的元素会全撞到同一个 bank。行距留点 padding(或者用 `float4` 读)
  就能避开。
- **别指望 k3 用例也能加速**。见下一节。

## 关于 k3 用例(照镜子用的)

同样是 4096² 的图,换成 3×3 核:采样点读取的冗余从 49 倍掉到 9 倍。
基线实测 **127µs / 约 1.05 TB/s —— 它已经跑满显存带宽了**(甚至超过了 1008 GB/s
的标称峰值,原因见思考题 3),分块 + 寄存器分块只能拿到 **1.18×**。

这个用例(以及 `ragged`、`tiny`)想告诉你两件事:

1. **分块的价值完全取决于复用度**。`kh×kw` 越大,重复读越多,分块越值钱。
   3×3 卷积在 4090 这种卡上,朴素实现几乎就是最优实现。
2. 判断优化方向的第一步永远是**算下限**:当基线和显存带宽下限只差 1.2× 时,
   再怎么调 tile 都是徒劳的。

## 评分

按**相对基线的加速比**评级(`leet test 05` 会打印每个用例的数字):

| 评级 | 加速比 | 意味着 |
|---|---|---|
| B | ≥ 1.5x | 共享内存分块做对了,重复的全局读基本消除 |
| A | ≥ 2.3x | 再加上寄存器分块:一个线程算多个输出,共享内存读也被摊薄 |
| S | ≥ 2.9x | 贴到显存带宽墙(k7 上约 119µs,有效带宽 ≈1.1 TB/s) |

**S 是一个物理上限,不是随手定的门槛。** k7 上基线 341µs、显存下限 133µs,
而结构完整的解实测 119~123µs —— 已经略低于标称下限(超出峰值的那部分是测量现象:
停止计时的瞬间,最后一批写还躺在 L2 里没落盘)。**这题不存在 4x 的解**,
把 tile 调到天上去也没有:134MB 的必经流量就是 133µs。

> 小用例(总耗时不到 20µs)不参与评级 —— 那个量级上测的是启动开销和计时器抖动。
> 本题里 `tiny`(31×49 个输出)专职用来考边界与跑 racecheck。

容差是 `atol=1e-4, rtol=1e-4`。参考解在 CPU 上用 `double` 顺序累加,很接近真值;
而你的 GPU 版是 49~81 个 `float` 乘加的另一种结合顺序,实测绝对偏差在 `3.8e-6` 量级 ——
比 `atol` 还有一个多数量级的余量,而错误实现(漏 halo、少乘一项)的偏差是 O(1) 的,
一样抓得住。

顺带解释一个容易吓到人的现象:对拍输出里 `max_rel_err` 可能报出 3.5 这种大数。
那是因为卷积的输出**本来就可能接近 0**(正负项相消),除法把一点点绝对误差放大成了
很大的相对误差。判据是 `|got-exp| <= atol + rtol*|exp|`,期望值接近 0 时
`rtol` 项不顶用,真正把关的是 `atol` —— 这也正是这道题必须同时给 `atol` 的原因。

## 思考题

1. **为什么只做共享内存分块不够?** 把「基线 / 只分块 / 分块+寄存器分块」三版
   各自每算出一个输出要发出多少次访存指令、搬多少字节列个表。LDS 和 LDG 的
   吞吐一样,这件事对第一版和第二版的性能意味着什么?

2. **tile 该多高多宽?** `TILE_H` 从 8 调到 32,行方向的 halo 冗余从
   `(8+6)/8 = 1.75×` 降到 `(32+6)/32 = 1.19×`;但共享内存用量涨 4 倍,
   每 SM 驻留的线程块数变少。用 `ncu`(或自己二分)找出 k7 用例上最好的形状,
   并解释为什么它最好 —— 注意共享内存用量、寄存器用量、和 halo 冗余这三者的
   最优解不在同一个点上。

3. **实测的 119µs 比「显存下限」133µs 还小,这可能吗?** 提示:框架每次计时迭代
   前会清空 L2,但 `cudaEventRecord` 停表时,写出去的数据还在 L2 里(写回是
   懒的)。由此想想:什么样的访存模式会让「有效带宽」虚高?反过来,
   如果你要测的是一段真实的端到端流水线,这个差别会带来什么后果?
