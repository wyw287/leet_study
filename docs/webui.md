# leet web —— 本地 web 界面

把 `leet` 的刷题循环搬到浏览器里。**独立工具,不 import 框架代码。**

```bash
leet web                    # http://127.0.0.1:8765
leet web --open             # 顺便把浏览器打开
leet web --port 9000

# 调试这个模块本身时可以单独跑(自己找仓库根和 leet,不经过命令行):
.venv/bin/python src/leetstudy/webui/server.py
```

零依赖 —— 只用 Python 标准库(外加本来就在 venv 里的 PyYAML)。前端是单个
HTML 文件,原生 JS,没有构建步骤。

源码在 `src/leetstudy/webui/`(`server.py` + `index.html`),是框架的一个子包,
但**刻意不 import 框架的其它部分** —— 见下。

## 它能做什么

- 浏览题库(按科目分组、显示完成状态与最佳评级)
- 读题面(含表格、代码块、引用)
- 在线编辑解答、保存(语法高亮在浏览器里实时算,没有防抖;**带补全**:语言关键字 +
  CUDA 词表 + 文档里已经出现过的标识符;**括号自动配对**)
- 一键 `test` / `bench`,**实时看输出**
- 看判题结果:逐用例的误差、guards、耗时、带宽、加速比、评级、框架生成的中文提示
- 看参考解

## 题面渲染

**服务端用 `markdown-it-py` 渲染**,和 Pygments 一样 —— 它也是 `rich` 的依赖,
**已经在 venv 里**,所以零新增依赖、不碰 CDN。

之前是前端一个手写的正则渲染器,只覆盖了「题面看起来会用到」的子集 ——
嵌套列表、表格对齐、转义这些边界全靠猜。CommonMark 的规则比看上去多得多。
换成真库之后,围栏代码块还能直接交给 Pygments,于是题面里的 ```cuda / ```python
和编辑器、参考解页**共用同一套配色**。

几个决定:

- **preset 用 `commonmark` 且不开 `html`** —— 题面里的 `<div>` 之类会被转义成
  文本。本项目题库的题面由出题规范约束、不该嵌 HTML,所以这个限制是对的
  (顺带躲开了 XSS 面)。
- **没标语言的围栏不进高亮**(题面里有 90 多处,多是公式和输出样例)。它们仍是
  一个等宽代码块,只是不上色。
- 渲染出来的 `<pre>` 会被加上 `class="hl"`,复用编辑器那套配色规则 ——
  不必再生成一份 CSS。
- 拿不到 markdown-it-py 时 `_render_markdown()` 返回 `None`,前端退回用
  `<pre>` 显示原文 —— 难看但不会白屏。

代价:每次打开题目多约 11 ms(实测 18 份题面平均)。本地工具,无所谓。

### 目录(带当前位置)

题面普遍有 7~8 个章节(最长的 8 节、6000+ 字),所以加了目录。

**正文 : 目录 = 3 : 1,整块居中**(总宽 880px,实测正文 597 / 目录 199)。
一开始写的是「正文限 76ch + 目录固定 186px、左对齐」—— 结果是目录挤在正文边上、
右边空出一大片,比例看着就不对。改成按比例分 + `margin:0 auto` 居中,留白均分到
两侧。窄于 1024px 就藏起目录、正文占满。

- 章节**直接从渲染好的 `<h2>` 抓**,服务端不必再为目录多返回一份数据
- 锚点用 `sec-N` 而不是从标题生成 slug —— 标题里有中文和标点,slug 既丑又容易撞
- **滚动时高亮当前章节**(监听的是 `main`,它是滚动容器而不是 `window`)
- 滚到底会把最后一节点亮 —— 否则最后一节永远够不到那条判定线,
  人已经在看了、目录里却还停在上一节
- 少于 3 节就不显示目录(纯属占地方)
- 标题带 `scroll-margin-top:132px`:不留的话点目录跳过去会被吸附的顶栏压住

**样式上值得单独说的两处**:

- **表格** —— 题面里 259 行、17/18 份都有,是最值得投入的。裸 `<table>` 没法
  同时要圆角和横向滚动,所以 `wrapTables()` 会给它套一层 `.tw` 壳。
- **题面开头的 `<h1>` 被隐掉了** —— 它和页面顶部的题目名是同一个东西
  (18 份里 13 份只差个编号前缀,而编号在头部 meta 行里已经有),留着会让人
  以为有两个标题。

## 语法高亮

分两块,**故意用了两套实现**:

| 位置 | 用什么 | 为什么 |
|---|---|---|
| 参考解页 / 题面里的代码块 | **服务端 Pygments** | 只读,没有延迟问题;而且服务端渲染的 HTML 不依赖 JS |
| **解答页(编辑器)** | **浏览器里的 CodeMirror 6** | 要打字,就必须零延迟 |

### 编辑器为什么换成了 CodeMirror

最初用的是「**透明 textarea 叠在高亮 `<pre>` 上**」:输入防抖后把源码 POST 到
`/api/highlight`,拿回 HTML 更新底层。这个方案能跑,但有个治不好的毛病 ——

**可见的文字是 `<pre>` 画的,而它要等服务端往返才更新。** 服务端高亮做不到零延迟,
所以打字时必须让 textarea 显示自己的纯色文字、停下再切回彩色 `<pre>`。每次触发都是
一次整块的「纯色 ⇄ 彩色」切换。防抖从 180ms 一路调到 900ms 仍然"闪得受不了" ——
这是**方案的固有取舍**,不是参数没调好。900ms 已经到"只有真的停下来想才变色"了,
再调就等于放弃打字时的着色。

CM6 把上色搬到浏览器里同步做,这个取舍直接消失:打字时颜色始终在,没有防抖,
没有状态切换,也没有那套"两层字形度量必须逐项对齐否则光标错位"的脆弱约束
(那套约束要求 font / line-height / padding / tab-size / white-space / wrap
在两层上**完全一致**,还要 `fitEditor()` 按内容撑高)。

一并作废的还有:`syncScroll`(把 textarea 的滚动位置同步给 `<pre>` —— 最初那个
「滚动条动了、字不动」的 bug 源头)、`hlLast`/`hlSeq` 的过期响应丢弃、
以及 `hl-on` 那个状态类。

### 配色不许自己写死

编辑器的 HighlightStyle 里**没有一个是硬编码的颜色**,全部绑到 `--py-*` CSS 变量。
那些变量由 `server.py` 的 `_theme_vars()` 从 Pygments **自己生成的 CSS 里反解**
出来(正则抠 `.hl .k{color:#008000}` 这种)。于是:

- 编辑器、题面、参考解页共用一份配色定义,换 Pygments 主题时三处一起变
- 变量名到 token 的对应表在 `server.py` 的 `_CSS_VARS`,一眼能查

有两个坑值得记下来:

**① 普通标识符故意不设规则。** Pygments 的 `default` 主题也没给 `Name` 上色,
不设规则正好同样是继承正文色(`--py-base`)。原型阶段给它们指定了一个颜色,
用户一眼就看出"变量名怎么变绿了"。

**② `nb` 必须和 `k` 分开。** 亮色主题下两者都是 `#008000`,合成一类看不出来;
但深色主题下它们不是一个颜色,合起来 `threadIdx` 就会跟着关键字走。
所以 CUDA 模式把内建词单独归为一类。

**③ 基准正文色也要一起反解。** 主题会在 `.hl` 上设 `color`(dracula 是
`#f8f8f2`),编辑器不跟着设的话整屏代码会比参考解页暗一档(`#e6e8ea` vs
`#f8f8f2`),看着像失焦。所以 `--py-base` 单独导一个。

#### 深色主题为什么是 dracula 而不是 monokai

实测扫了 7 个现成的深色主题,**没有一个做到四类 token 两两可辨**:

| 主题 | k 关键字 | kt 类型 | nb 内建 | o 运算符 | 撞色 |
|---|---|---|---|---|---|
| monokai | `#66D9EF` | `#66D9EF` | `#A6E22E` | `#FF4689` | **k = kt** |
| native | `#6EBF26` | `#6EBF26` | `#2FBCCD` | `#6EBF26` | **k = kt = o** |
| gruvbox-dark | `#FB4934` | `#FB4934` | `#FE8019` | `#FB4934` | **k = kt = o** |
| material | `#BB80B3` | `#BB80B3` | `#82AAFF` | `#BB80B3` | **k = kt = o** |
| one-dark | `#C678DD` | `#E5C07B` | `#E5C07B` | `#56B6C2` | kt = nb(且 `n` 是红的) |
| solarized-dark | `#859900` | `#B58900` | `#268BD2` | `#859900` | k = o(且整体低对比) |
| **dracula** | `#FF79C6` | `#8BE9FD` | `#8BE9FD` | `#FF79C6` | kt = nb,k = o |

monokai 的 `k = kt` 最碍眼:那意味着 `__global__` 和 `void` 同色,而这两个恰恰
是 CUDA 里最常并排出现的。dracula 把 k 和 kt 分开了(粉 / 青),剩下两处撞色
撞在别处。

所以最终是 **dracula + 三个覆盖**(`server.py` 的 `_DARK_OVERRIDES`):

| 改什么 | 原值 | 改成 | 为什么 |
|---|---|---|---|
| `nb` 内建 | `#8BE9FD` | `#50FA7B` | 和 `kt` 撞色,`int i = blockIdx.x * …` 整行同色 |
| `o` 运算符 | `#FF79C6` | `#BD93F9` | 和 `k` 撞色,而 operator 在语料里出现 1042 次 |
| `c` 注释 | `#6272A4` | `#828FC2` | 对 `--code-bg` 只有 **3.9:1**,低于 WCAG AA |

第三条是**本项目特有的**:题面和参考解的内容基本都在注释里,注释读着累等于整个
工具读着累。dracula 原色是给代码配的,不是给讲义配的。提亮只是改明度、保色相,
实测对比度到 5.8:1。

改完之后实测对比度(对 `--code-bg`):

| | 注释 | 关键字 | 类型 | 内建 | 数字 | 运算符 | 名字 |
|---|---|---|---|---|---|---|---|
| monokai | 5.6 | 11.0 | 11.0 | 11.7 | 6.4 | 5.6 | 17.0 |
| **dracula+覆盖** | **5.8** | 7.6 | 13.1 | 13.2 | 10.6 | 7.5 | 17.0 |

覆盖**不破坏「颜色只定义一次」**:它发生在 `_theme_vars()` 里,而 `--py-*` 正是
编辑器、题面、参考解页共用的那一份,三处依然一致。破的只是「必须原样照抄
Pygments 主题」—— 而那本身不是目的。

> ⚠️ 只改 `--py-*` 是**不够**的:参考解页和题面里的代码块是**服务端渲染好的
> HTML**,用的是 Pygments 原样输出的 `.hl .nb` 这类类名,它们不读变量。
> 所以 `_override_rules()` 会把同样的颜色再写成 `.hl .nb{…}` 追加在 `dark`
> 之后(同级选择器、后来者胜)。漏了这一步,编辑器里 `threadIdx` 是绿的面
> 参考解页还是青的 —— 正是这套设计要避免的「三处不一致」。

⚠️ 那几个色值是照 dracula 的调色板挑的,**换主题时要一起换**。

### CUDA 模式是怎么写的

CodeMirror 6 没有现成的 CUDA 模式,但**不需要从零写 tokenizer**:用
`@codemirror/legacy-modes` 的 `clike`(`cpp` 模式),在它前面拦一层 ——
识别出整个标识符,命中 CUDA 词表就返回对应样式,否则把 `stream.pos` 还原、
原样交还给 clike。

自写的部分只有**一张词表加两条改判规则**(`vendor/src/cuda-mode.js`,95 行):
- 词表分三类 —— 类型(红)/ 内建(绿 `nb`)/ 其余关键字(绿 `k`)
- `float*` 里的 `*`:clike 把它也算进类型(返回 `"type"`),Pygments 是按运算符
  着色的,这里改判
- `state.tokenize` 非空时不拦(注释/字符串/预处理指令里再认关键字会把注释里的
  `atomicAdd` 也点亮)

### 补全

两路来源,**并列而不是替换**:

| | 来源 | 覆盖什么 |
|---|---|---|
| ① | 模式的 `languageData` | 语言关键字 + CUDA 词表 |
| ② | CM6 自带的 `completeAnyWord` | 文档里**已经出现过**的标识符 |

**① 是白捡的**:三个模式的 `languageData` 里本来就带关键字表(clike 的 C++、
python 模式的 Python),「CM6 的 `autocompletion()` 会自己去读。我们只是把
CUDA 词表也挂上去 —— 而且**和上色共用同一份数据**(`vendor/src/cuda-mode.js`
里那张按语义分组的表),加一个词只需要加一行,不会两边漂移。分组名直接成了
下拉右侧的说明:「块内/设备同步」「原子操作」「运行时 API」。

**② 是一行**:`EditorState.languageData.of(() => [{autocomplete: completeAnyWord}])`。

> ⚠️ **不能用 `autocompletion({override: [...]})`。** 那个参数是**替换**而不是
> 追加 —— 一旦给了它,CM6 就不再读 `languageData`,① 整个消失,只剩你自己列的
> 那几个源。正确做法是把 ② 也作为一条 languageData 挂进去:CM6 的
> `languageDataAt` 会**收集全部** provider,两路并存。

**② 是词形匹配,不是语义补全。** 它能把 `ctx`、`block`、`n` 这些你写过的名字
补出来,但**不认识类型** —— 打 `ctx.` 之后不会列出 `LaunchCtx` 的成员字段。
那需要真正的语义分析(知道 `ctx` 是 `LaunchCtx`),而 CM6 用的是流式分词器,
拿不到这个信息。要做的话得自己解析 `spec.yaml` 生成结构体定义,是另一个量级的
工程。

**两路之间不去重,这是明确接受的行为。** 打 `blo` 时 `blockDim` 会出现两次:
一次来自 CUDA 表(带「内建变量」说明),一次来自 `completeAnyWord`(文档里
出现过 `blockDim.x`,没说明)。想过三个办法,选了最省事的:

- 自己扫文档、合并成一路 —— 能去重,但要多写 20 行,还得自己维护
- 把内建从静态表里删掉 —— 新文件(还没写过 `threadIdx`)就补不出来了
- **接受重复** ← 现在的选择

重复项的说明文字不一样,看起来更像"两个来源"而不是"坏了"。

**代价**:bundle 346 → 383 KB,113 → 125 KB gzip(+12 KB)。

### 括号自动补全

打 `(` 自动补 `)`,光标停在中间;打 `)` 会跳过它;退格一次删掉一整对。
用的是 CM6 自带的 `closeBrackets()` + `closeBracketsKeymap`。

**括号表不用我们写** —— `clike`(cuda 继承它)和 `python` 两个模式各自在
`languageData` 里声明了(圆括号/方括号/花括号/单引号/双引号,python 还多三引号),
CM6 自己会读。注意 `<` **不在**表里,所以 CUDA 的 `<<<grid, block>>>` 不受影响。

> **它在注释和字符串里也会补。** CM6 的 `insertBracket` 只看下一个字符是不是
> 空白或 `)]}:;>`([源码][ins]),不查语法树。
>
> 量过这个项目的注释:你实际编辑的 `solutions/` 里,注释中平均**每 4 行就有一个
> `(`**(177 个)。看起来像个问题,但实际不碍事 —— 补上右括号之后打 `)` 会跳过它,
> **敲键数和手写完全一样**,还不会漏;唯一多花的情况是"打了 `(` 又不想要",
> 而那时退格一次会成对删掉,也还是一下。所以没为它写自定义 handler。

[ins]: https://codemirror.net/docs/ref/#autocomplete.insertBracket

还有一个**验证上的坑**:`closeBrackets` 挂在 `EditorView.inputHandler` 上,
**只响应真实 DOM 输入**,`view.dispatch()` 触发不了它 —— 所以自检里那套
程序化打字验不了它,得单独测。实测三种模拟方式里只有
`document.execCommand("insertText")` 能触发(手造 `beforeinput` 事件不行)。

### 实测:和 Pygments 的逐字符一致性

验证方法写在 `docs/` 之外(是一次性的):把同一份源码分别用 CM6 和服务端 Pygments
渲染,然后逐字符取 `getComputedStyle().color` 对比。

```
solutions/01-vector-add/solution.cu   340 个字符,1 处差异
```

那一处是 `#include "ctx.h"` 里的文件名:clike 把整行当一个 token,而 Pygments 把
文件名单独染成注释色。为它拆 token 不划算。

### ⚠️ 编辑器包要**从 API 那个源**加载

`vendor/codemirror.js` 是提交进仓库的打包产物(构建方法见 `vendor/BUILD.md`),
346 KB / 113 KB gzip。前端可以单独部署(见下),那时页面旁边并没有 `vendor/` 目录,
所以:

- 脚本里 `import(API + "/vendor/codemirror.js")`
- **`<link rel="stylesheet">` 的 href 也必须按 API 拼**,不能写成
  `href="/api/highlight.css"`

第二条踩过:根相对的 `<link>` 在单独部署时会指向前端自己那个源,静默 404 ——
**页面照常打开,没有任何报错,只是所有代码变成黑白的**。这个 bug 是被自检里
「token 颜色 == `--py-*` 变量」那一条抓出来的,而且第一版自检还漏判了:
变量为空时两边都取到"继承来的正文色",三个检查全部"通过"。**假绿灯比红灯危险。**

加载失败不致命:退化成纯文本 `<textarea>`,照样能编辑、保存、判题。

### 保存

**保存的逻辑没有变。** 写盘发生在三处:

- 点「保存」
- **切走时自动保存**(换题目、换标签页、跑 test/bench 之前)
- 关标签页时如果还有未保存改动,弹提醒(浏览器的 `beforeunload` 没法可靠地
  做异步保存,所以这一处只能拦一下)

"有没有改动"是**和盘上那份内容比**出来的(`isDirty()`),不是布尔标志 ——
用标志踩过坑:最初的初始化代码里派发过一次合成的 `input` 事件来设置显示状态,
于是"刚打开一道题"就被标记成改过了,关页面时无端弹提醒。
比内容还能顺带正确处理"改了又改回去"(那不算脏)。

编辑器换掉之后这一条**一字未改**,只是取值的地方从 `$("#ed").value` 换成了
`editorText()`(CM6 实例或退化 textarea,两者取其一)。

### 自检

`index.html` 的改动没有自动化测试覆盖,验收是靠一个一次性的调试页:它把仓库里
真实的 `index.html` 读出来,**只做加法**(注入错误捕获 + 一段自检脚本)生成副本,
在真浏览器里驱动它并截图。自检覆盖:题库渲染 / 编辑器挂载 / 高亮 span /
配色变量已导出 / **每个高亮色都来自配色表** / 改动进文档 / 未保存标记的加与清 /
保存发出的内容 == 文档内容(**`fetch` 被拦下来,PUT 只记录不发出 —— 否则会真的
覆盖 `solutions/` 下的解答**)/ Tab 缩进 / Esc 后 Tab 放行 / **打字能触发补全下拉**。

补全那几条按科目分开断言:CUDA 题查补全里有没有 `float2/3/4` 和「CUDA 类型」
说明;非 CUDA 科目反过来查说明文字**全为空**(证明它们来自模式自带的关键字表,
没走我们的词表)。第一版没分,于是在 Python 题上报"没有 CUDA 向量类型" ——

## 设计:为什么是「以用户身份调 CLI」而不是 import 框架

框架的内部 API(`judge.Verdict`、`subjects.Subject` …)可以随便改,只要
`leet` 命令还能用,这个界面就不用跟着动。

通常这种做法的脆弱点是**解析给人看的终端输出**。这里不存在那个问题,因为
web 需要的数据全都有文件级的结构化通道:

| 数据 | 来源 |
|---|---|
| 题目定义 | `problems/*/spec.yaml` |
| 题面 | `problems/*/problem.md` |
| 完成状态 | `progress.json` |
| 判题结果 | `build/*/last_verdict.json` |
| 解答源码 | `solutions/*/solution.*` |

所以规则是:**数据一律读文件,只有「动作」才走 CLI**。

`spec.yaml` 是唯一直接依赖的框架数据格式 —— 但它是出题文档里公开的契约
(「唯一驱动代码生成的文件」),比 import 内部类稳定得多。

> 唯一一处硬编码:参考解的文件名(`optimal.cu` / `optimal.cpp` / `optimal.py`)
> 按科目做了个三行的映射表。代价是加新科目要在这里补一行;收益是完全不依赖
> 框架的 Python API。

## 为什么是串行任务队列

`leet test` 要 11~21 秒(CUDA 上下文初始化就占 4.4 秒),`bench` 更久。所以
HTTP 请求不能同步跑任务 —— 提交进队列,前端轮询进度。

**单工作线程**是刻意的:框架的 `build/<题号>/`、`progress.json` 都是单份的,
同一道题并发跑两次会互相覆盖编译产物。串行执行把这个问题从根上消掉。

## 任务进行中的反馈

`leet test` 要 11~21 秒。**只把按钮置灰等于没反馈** —— 所以点下之后:

- 被点的那个按钮变成「⟳ 判题中…」(转圈 + 文字),并加 `.running` 让它带强调色。
  不加这个强调的话,正在跑的那个按钮反而比旁边被禁用的主按钮更不显眼
- 工具栏右侧出现进度行:`运行中 · 4.2s` / `排队中 · 0.8s`,每 100ms 刷新
- 结束后按钮文字还原,toast 报「完成 · 用时 12.3s」

计时器是**独立于轮询**的:轮询 700ms 一次(够拿到状态),但秒数要每 100ms 动一下
才看得出"它在动"。两者职责不同,别合并。

## 安全

这个工具的本质是**执行任意学习者代码**(nvcc/g++ 编译并运行解答)—— 那就是
RCE by design。所以:

- **默认只绑 `127.0.0.1`**。要换地址用 `--host`,但先想清楚。
- 能触发的动作是**白名单**(`test` / `bench` / `start` / `solution`),
  界面传什么都不能越出这几个。
- 题号会做路径穿越校验,只接受题库里真实存在的目录名。
- **写盘全代码只有一处**:`server.py:511` 的 `path.write_text`(PUT 解答)。
  路径由 `_solution_path()` 拼 —— `solutions/<题号>/` 下**已存在**的
  `solution*` 文件,前端一个字节的路径都传不进来。题号本身也过 `_safe_id()`
  (只允许 `[A-Za-z0-9_.-]+`,且必须是 `problems/` 下真实存在的目录),挡掉穿越。
- `/vendor/codemirror.js` 是唯一一条静态文件路由,路径**写死在代码里**,
  不接任何参数,所以没有穿越的余地。
- **CORS 是白名单,不是 `*`**。这条要认真对待:这个 API 能写文件、还能让框架
  编译并执行它们。放 `*` 等于任何网页都能拿你的机器当编译器跑任意代码。
  `_ALLOW_ORIGINS` 默认是空列表(一个源都不放),要用 `--allow-origin` 显式加
  (可重复给多个),并且响应里带 `Vary: Origin`。

## 已知限制

- **单用户**。并发请求会排队,但 `progress.json` 之类的共享状态没有跨进程锁。
- **判题缓存的版本**:`last_verdict.json` 带版本号,框架改动其结构时会失效。
  旧缓存在界面上会显示不出评级 —— 重新 `test` 一次就有。
- 只覆盖**做题**循环。出题(`leet new`,8~40 分钟)和 `validate` 没有接进来。
- **编辑器包 346 KB(113 KB gzip)**。同源部署时它和页面一起从 localhost 出,
  感知不到;真要放到远程去用,这个体积值得再压(可以按科目拆包,
  `python`/`cpp` 两个模式只在打开对应科目时才 import)。
- **补全不做语义分析**:`ctx.` 之后不会列出结构体成员,跨文件的符号也补不出来
  (见上面「补全」)。
- **括号自动补全在注释和字符串里也会生效**(CM6 的既定行为,理由见上)。如果实际
  用起来碍事,可以写个查语法树的 `inputHandler` 把它关掉 —— `insertBracket`
  是导出的,大约十行。
- **编辑器的高亮和「参考解」页不是同一份实现**(一个在浏览器、一个在服务端),
  共用的是**配色变量**而不是渲染结果。所以理论上存在"同一份代码两边略有出入"
  的可能 —— 实测 340 字符的样本差 1 处(见上面「逐字符一致性」)。
